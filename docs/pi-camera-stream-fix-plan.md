# Raspberry Pi 카메라 영상 송출 장애 수정 계획서

작성일: 2026-11-15 (Asia/Seoul)  
상태: 2026-11-15 09:04 KST 재검증 — 복구 미완료, Pi 송출 대상 미변경 확인

## 1. 목표와 적용 기준

DEB로 설치된 Edge를 유지하면서 Pi Camera 영상이 데스크톱 서버의 MediaMTX에 도착하고 CCTV 관리 화면에서 재생되도록 복구한다. 이번 작업은 운영 설정과 필요한 방화벽 규칙을 수정하는 것으로 한정한다.

영상 및 Edge 관리 통신은 직결 이더넷을 사용하고, Pi의 인터넷 연결은 기존 Wi-Fi를 유지하는 구성을 기준으로 한다. Wi-Fi를 통한 다른 기기의 서버 접속 주소 변경은 별도 작업이다.

성공 기준은 다음과 같다.

- Pi에서 `192.168.50.1:8554`로 TCP 연결할 수 있다.
- MediaMTX의 `cam-001`이 `ready=true`, 영상 트랙 `H264`를 보고하며 수신 바이트가 계속 증가한다.
- 관리 화면에서 Pi 영상이 3분 이상 연속 재생되고, 10분 관찰 동안 송출 프로세스의 반복 종료가 없다.
- 기존 데스크톱 카메라, Pi 로컬 녹화, 서버 녹화 및 Edge 관리 통신이 정상이다.

## 2. 확인된 장애 근거

아래 값은 진단 시점의 관측이다. 적용 직전에 현재 상태를 다시 확인한다.

| 항목 | 확인 결과 |
|---|---|
| Pi 계정 / 장치 | `phoenix` / `bull-sa-jo`, `edge-001`, `cam-001` |
| Pi 직결 주소 | `eth0`, `192.168.50.2/24` |
| 데스크톱 직결 주소 | `이더넷`, `192.168.50.1/24` |
| Pi / 데스크톱 Wi-Fi 주소 | `10.205.13.143` / `10.205.13.1` |
| 잘못 사용된 서버 주소 | `192.168.1.10`, VirtualBox Host-Only Ethernet Adapter |
| Pi 송출 설정 | `central_publish`, `central_host="192.168.1.10"`, TCP 8554 |
| Pi의 송출 대상 경로 | `192.168.1.10 via 10.205.13.19 dev wlan0` |
| 서버 포트 공개 | `192.168.1.10:8554 -> mediamtx:8554` |
| 서버의 Pi 영상 경로 | `source=null`, `ready=false`, `bytesReceived=0` |
| Pi 카메라 / 로컬 녹화 | 캡처 실행 중, 약 2.6 MB 크기의 TS 조각이 계속 생성됨 |
| Edge 관리 통신 | `http://192.168.50.2:8003` 상태 조회 성공 |
| 데스크톱 카메라 | 같은 MediaMTX에서 `local-camera` 정상 수신 |

Pi 로그는 송출 시작 메시지 뒤 약 20초 후 아래 오류를 기록하고 프로세스를 반복 재시작한다.

```text
publishing camera cam-001 to rtsp://192.168.1.10:8554/cam-001
publisher failed: Could not open resource for reading and writing.
central publisher exited with code 1; local backup continues
```

서버 로그에는 다음 메시지가 반복된다.

```text
no one is publishing to path 'cam-001'
```

원인은 Pi의 송출 대상과 서버의 RTSP 수신 바인딩이 모두 VirtualBox 주소로 설정된 것이다. Pi는 해당 목적지로 Wi-Fi 기본 경로를 선택하며 연결이 시간 초과된다. 직결 주소에도 서버 RTSP가 바인딩되지 않았다. Pi에서 직결 주소의 TCP 접속도 시간 초과됐으므로, 주소 수정 후 Windows 방화벽 허용 여부를 별도로 검증해야 한다.

## 3. 수정 범위

### 필수 설정 변경

| 위치 | 항목 | 기존 값 | 변경 값 |
|---|---|---|---|
| Pi `/etc/ai-cctv-edge/config.toml` | `[rtsp].central_host` | `192.168.1.10` | `192.168.50.1` |
| 서버 `C:\ProgramData\AI_CCTV\config\compose.env` | `RTSP_BIND_ADDRESS` | `192.168.1.10` | `192.168.50.1` |
| 같은 파일 | `RTSP_PUBLIC_HOST` | `192.168.1.10` | `192.168.50.1` |
| 서버 `C:\ProgramData\AI_CCTV\config\config.yaml` | `server.rtsp_bind_address` | `192.168.1.10` | `192.168.50.1` |

RTSP 포트는 8554를 유지한다. `config.yaml`도 함께 맞춰 운영 설정과 GUI·진단 도구가 서로 다른 주소를 사용하지 않게 한다.

카메라 ID, 게시 자격증명, Edge 운영 토큰, 녹화 경로와 등록 DB는 유지한다. Pi 재페어링, DEB 재설치, 서버 재설치 및 데이터 초기화는 필요하지 않다. `PUBLIC_BIND_ADDRESS`, `PUBLIC_BASE_URL`은 이번 RTSP 복구에서 변경하지 않는다. 현재 데스크톱 관리 API 접속을 유지하기 위한 범위 결정이다.

### 조건부 변경

- Windows 방화벽에 해당 통신을 허용하는 규칙이 없으면 직결 인터페이스의 TCP 8554 수신 규칙을 추가한다.
- 범위는 로컬 주소 `192.168.50.1`, 원격 주소 `192.168.50.2`, 인터페이스 `이더넷`으로 제한한다.
- 직결 네트워크의 실제 프로필을 확인하고 해당 프로필에 규칙이 적용되도록 한다. 방화벽 전체 비활성화는 사용하지 않는다.
- 기존 데스크톱 카메라 Publisher가 이전 RTSP 주소를 사용하면 새 주소로 재시작한다.

## 4. 적용 순서

### 1단계: 현황 기록 및 백업

1. 양쪽 직결 IP와 링크 상태를 다시 확인한다. Pi에서 `ip route get 192.168.50.1` 결과가 `eth0`인지 확인한다.
2. 실행 중인 Compose 프로젝트, 적용 중인 env 파일, GPU·push 오버레이, 활성 서비스와 데스크톱 카메라 실행 상태를 기록한다.
3. 수정 대상 설정 파일 3개를 시각을 붙여 각 장치의 보호된 위치에 백업한다. 파일 권한과 소유자를 보존한다. 비밀번호·토큰이나 설정 파일 전체 내용을 저장소에 복사하지 않는다.
4. 현재 방화벽 규칙과 두 카메라의 수신 상태를 기록한다.

검증: 백업 존재 여부와 복구 경로를 확인한다. 설치 도우미의 재설치·초기화 경로는 실행하지 않는다.

### 2단계: 서버 수신 설정 적용

1. `compose.env`의 RTSP 바인딩·공개 호스트와 `config.yaml`의 RTSP 바인딩을 표의 값으로 수정한다. 다른 키와 파일 권한은 유지한다.
2. 필요한 경우 앞서 정의한 범위의 방화벽 규칙을 추가한다. 새 규칙의 이름을 기록해 롤백 시 식별할 수 있게 한다.
3. 기존 Compose 프로젝트와 env·오버레이를 그대로 사용해 `mediamtx`, `external` 컨테이너를 재생성한다. `external`은 변경된 `RTSP_PUBLIC_HOST`를 재로딩해야 한다.
4. `config.yaml`을 읽기 전용 bind mount하는 `data`와 실행 중인 `preprocessing`도 재생성해 파일 교체 방식에 따른 이전 설정 잔류를 방지한다. 중지돼 있던 선택 서비스는 새로 켜지 않는다.
5. 백엔드가 준비된 뒤 `nginx`를 재시작해 재생성된 컨테이너 주소를 반영하고 API 준비 상태를 확인한다.

포트 매핑과 컨테이너 환경변수 변경은 `docker compose restart`만으로 반영되지 않는다. 기존 이미지로 `up -d --no-build --force-recreate`를 사용하며, 실행 명령은 기존 `ComposeAdapter`가 만드는 프로젝트·env·오버레이 구성을 기준으로 한다. 전체 스택 `down`이나 볼륨 삭제는 사용하지 않는다.

이 단계에서는 MediaMTX 연결과 서버 녹화가 일시 중단되며, 재생성 대상 서비스도 잠시 사용할 수 없다. Pi는 송출 실패 중에도 기존 로컬 녹화를 유지한다.

검증: 호스트의 `192.168.50.1:8554` 수신과 컨테이너 포트 매핑을 확인하고, Pi에서 해당 포트에 TCP 연결한다. Pi 접속이 실패하면 바인딩·방화벽·직결 경로를 해결한 뒤 다음 단계로 진행한다.

### 3단계: Pi 송출 대상 적용

1. `/etc/ai-cctv-edge/config.toml`의 `[rtsp].central_host`만 `192.168.50.1`로 변경한다.
2. `sudo systemctl restart ai-cctv-edge`로 캡처·송출 프로세스에 적용한다.
3. 같은 설정을 읽는 `ai-cctv-edge-control`, `ai-cctv-edge-recovery`도 재시작해 구성 일관성을 유지한다.
4. 새 로그의 송출 대상이 `rtsp://192.168.50.1:8554/cam-001`인지 확인한다.

Edge 재시작 동안 Pi 캡처·로컬 녹화에 짧은 공백이 발생한다. 서비스가 다시 실행된 뒤 로컬 녹화 파일 증가를 확인한다.

### 4단계: 기존 클라이언트 재연결

1. 데스크톱 관리 화면에서 Pi 영상을 다시 연다. 서버가 반환하는 RTSP 호스트가 새 주소인지 확인한다.
2. 실행 중이던 데스크톱 카메라 Publisher의 재접속을 확인한다. 이전 주소를 유지하면 새 서버 주소를 사용하는 기존 관리 흐름으로 재시작한다.
3. 새 공개 주소 변경이 필요한 Wi-Fi 클라이언트가 있다면 이번 유선 복구 결과를 확인한 뒤 별도 적용 범위를 정한다.

## 5. 실장비 검증 및 완료 판정

| 검사 | 완료 기준 |
|---|---|
| Pi 경로 | `ip route get 192.168.50.1`이 `eth0`, 출발지 `192.168.50.2`를 표시 |
| Pi → 서버 TCP | `192.168.50.1:8554` 연결 성공 |
| 서버 MediaMTX | `/v3/paths/list`의 `cam-001`이 `ready=true`, `tracks`에 `H264` 포함 |
| 실제 데이터 수신 | 10초 간격의 두 조회에서 `cam-001.bytesReceived` 증가 |
| Pi 송출 안정성 | 10분 동안 게시 성공 유지, 반복되는 resource 오류·프로세스 종료 없음 |
| 실시간 재생 | CCTV 관리 화면에서 3분 이상 연속 재생 |
| HLS | 현재 인증 경로를 통해 플레이리스트·영상 세그먼트를 받아 재생 가능 |
| 서버 녹화 | 60초 조각 설정을 고려해 2분 이상 관찰하고 완료된 녹화 파일과 DB 등록 확인 |
| Pi 로컬 녹화 | 크기가 0보다 큰 완료 TS 조각이 계속 생성됨 |
| Edge 관리 | 기존 `192.168.50.2:8003` 상태 조회 및 8002 복구 서비스 정상 |
| 기존 데스크톱 카메라 | `local-camera`도 `ready=true`, 수신 바이트 증가 및 재생 가능 |
| 재접속 | 위 검사 통과 후 Edge를 한 번 재시작하고 송출·녹화 자동 복구 확인 |

상태 API의 `online=true`나 컨테이너 healthcheck 통과만으로 완료 처리하지 않는다. 이번 장애에서도 Pi가 `online`을 보고했지만 실제 서버 수신은 0바이트였다.

실패 시 최초로 실패한 계층부터 조사한다. TCP 실패는 경로·바인딩·방화벽, TCP 성공 후 게시 실패는 Pi 로그와 MediaMTX 인증 로그, 게시 성공 후 재생 실패는 클라이언트 URL·인증·HLS 로그를 확인한다. 인증 실패가 실제로 확인되기 전에는 게시 자격증명을 회전하지 않는다.

## 6. 롤백

서버 API가 준비되지 않거나 기존 카메라 기능이 회복되지 않으면 변경한 파일을 각 장치의 백업으로 복원한다.

1. 서버의 `compose.env`, `config.yaml`을 복원하고 같은 Compose 프로젝트·오버레이로 변경 대상 컨테이너를 다시 재생성한다. 백엔드 준비 후 `nginx`를 재시작한다.
2. Pi의 `config.toml`을 복원하고 Edge 및 관리·복구 서비스를 재시작한다.
3. 이번 작업에서 추가한 방화벽 규칙만 제거한다. 기존 규칙은 유지한다.
4. 실행 중이던 데스크톱 카메라를 기존 주소로 재연결하고 Pi 로컬 녹화를 확인한다.

롤백은 변경 전 상태로 되돌리는 절차다. 변경 전부터 발생하던 Pi 중앙 송출 장애까지 해결하는 것은 아니므로, 실패 검사와 로그를 기록해 다음 조치에 사용한다.

## 7. DEB 재설치 및 후속 코드 개선 판단

이번 설정 복구에는 DEB 재설치·재빌드가 필요하지 않다. 설치된 프로그램이 정상적으로 캡처와 녹화를 수행하고 있으며, 설정 파일과 서비스 재시작으로 통신 대상을 바꿀 수 있다.

다음 항목은 별도 후속 개선 후보이며 이번 필수 복구의 완료 조건에 포함하지 않는다.

| 후보 | 조사·수정 방향 | 검증 기준 | 배포 영향 |
|---|---|---|---|
| 잘못된 주소 선택 방지 | 서버 설치·페어링 입력에 선택된 어댑터와 Pi로의 경로를 표시하고, 실제 Pi → 서버 접속 확인을 추가하는 방안을 검토 | 여러 물리·가상 어댑터 환경에서 직결 주소 선택 및 연결 실패 안내 확인 | 서버 변경. Pi 진단 API를 추가하면 Edge도 변경 |
| 송출 상태 오표시 | `publisher.py`의 PLAYING 상태 확인만으로 실제 RTSP 게시 성공이 보장되는지 조사하고, 게시 확인 또는 서버 수신 상태와 구분해 표시 | 도달 불가능한 서버를 대상으로 수신 확인 전 성공 표시가 나타나지 않고, 정상 대상에서는 성공 표시 | Edge 코드를 수정하면 새 DEB 빌드·업데이트 필요 |

코드 개선을 진행할 때는 위 실패 상황을 재현하는 회귀 검증을 추가한다. 설정만 변경하는 이번 작업은 실장비 수신·재생·녹화 결과로 검증한다.

### 원인 판단

1. **확인된 주원인:** 서버만 직결 주소로 변경됐고 Pi의 송출 대상 변경은 전원 꺼짐으로 수행되지 않았다. Pi는 재부팅 뒤에도 저장된 VirtualBox 주소로 게시를 반복한다. SSH 연결과 로컬 녹화가 정상이어도 서버 영상은 수신되지 않는다.
2. **별도 확인된 미복구 상태:** 데스크톱 카메라 Publisher가 실행되지 않는다. 앞선 MediaMTX 재생성·주소 변경 시점의 연결 중단과 관련됐을 가능성이 있으나, 종료 원인은 이번 관측만으로 확정할 수 없다. 이전 주소를 재사용하는지와 재시작 시 오류를 확인해야 한다.
3. **현재 근거가 없는 변경:** 방화벽 추가 개방, 게시 자격증명 회전, DEB 재설치 및 재페어링. Pi에서 새 주소의 TCP 접속이 이미 성공하므로 우선 시행하지 않는다.

### 후속 적용 순서

#### 1. Pi 송출 대상 변경

SSH 접속 후 원본 설정을 Pi 안에 소유권·권한을 보존해 백업하고, `[rtsp]`의 `central_host`만 변경한다. 비밀번호와 토큰은 출력하거나 저장소에 복사하지 않는다.

```bash
sudo cp -a /etc/ai-cctv-edge/config.toml /etc/ai-cctv-edge/config.toml.bak-$(date +%Y%m%d-%H%M%S)
sudo sed -i '/^\[rtsp\]/,/^\[/s/^central_host = "192\.168\.1\.10"$/central_host = "192.168.50.1"/' /etc/ai-cctv-edge/config.toml
sudo grep -E '^(mode|central_host|central_port|camera_id) *=' /etc/ai-cctv-edge/config.toml
sudo systemctl restart ai-cctv-edge ai-cctv-edge-control ai-cctv-edge-recovery
sudo journalctl -u ai-cctv-edge -n 30 --no-pager
```

확인: 실제 설정과 신규 게시 로그가 `192.168.50.1:8554/cam-001`을 가리켜야 한다. Edge 재시작 중 로컬 녹화에 짧은 공백이 생긴다. 서버 설정과 컨테이너는 이미 적용되어 있으므로 이 단계에서 다시 재생성할 필요가 없다.

#### 2. Pi 게시 성공 여부로 조사 분기

- MediaMTX에서 `cam-001.ready=true`, H264 트랙과 10초 간격으로 증가하는 `bytesReceived`를 확인한다.
- 새 주소에서 TCP가 다시 실패하면 그때 경로·바인딩·방화벽을 재검사한다.
- TCP는 성공하지만 게시가 실패하면 같은 시각의 Pi와 MediaMTX 로그에서 인증 거부, 경로 불일치, 중복 Publisher, GStreamer 오류를 확인한다. 인증 거부가 확인된 경우에만 자격증명 불일치를 조사한다.
- 수신은 정상인데 화면이 실패하면 서버가 반환하는 재생 주소, 외부 인증 경로, HLS 플레이리스트와 영상 세그먼트 응답을 순서대로 확인한다.

#### 3. 기존 데스크톱 카메라 송출 복구

설치된 관리 흐름에서 `720p HD Camera` 송출을 다시 시작한다. 이미 등록된 카메라 ID와 자격증명을 유지하고 새 서버 주소 `192.168.50.1:8554`를 사용한다. 관리 앱이 이전 주소를 메모리에 유지하면 설정을 다시 읽어야 한다. 구주소가 남은 화면에서 서버 설정 전체를 재적용하지 않는다.

확인: Publisher/FFmpeg 프로세스 실행, MediaMTX `local-camera.ready=true`, 수신 바이트 증가 및 화면 재생. 실패하면 해당 재시작에서 나온 종료 코드와 자격증명을 가린 오류를 기록한다. 버퍼 포화가 계속 관측되면 장치 중복 점유, 입력 해상도·FPS, 인코더 처리량을 조사한 후 필요한 항목만 조정한다.

#### 4. 최종 완료 검증

두 카메라가 수신된 뒤 5절의 완료 기준을 적용한다. Pi 게시를 10분 관찰해 반복 종료가 없는지 확인하고, 관리 화면에서 3분 이상 연속 재생한다. HLS 플레이리스트·세그먼트 응답, 완료된 서버 녹화 파일과 DB 등록, Pi 로컬 TS 생성, 인증된 Edge 상태 조회를 확인한다. 마지막으로 Edge를 한 번 재시작하고 송출·녹화 자동 복구를 확인한다. 통과하지 못한 항목이 있으면 복구 완료로 표시하지 않는다.

후속 적용 실패 시 6절의 롤백 기준을 따른다. Pi 설정만 되돌려야 하는 경우 해당 Pi 백업을 복원하고 세 서비스를 재시작한다. 서버의 정상적인 직결 바인딩은 Pi 게시 실패만을 이유로 이전 VirtualBox 주소로 되돌리지 않는다.
