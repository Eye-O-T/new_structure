# 사람 감지 바운딩 박스·이벤트 표시 복구 작업 계획

작성일: 2026-11-03, Asia/Seoul  
상태: 코드 변경 및 설정 복구 적용, 카메라 현장 검증 대기  
대상: 서버 관리자의 “감지·식별 켜기” 이후 Desktop에 사람 박스와 출현·퇴장 이벤트가 표시되지 않는 문제

## 1. 목표와 판단 기준

올바른 YOLO 모델로 사람 감지를 복구하고, 검출 결과가 Data와 External을 거쳐 Desktop의 박스·이벤트로 표시되는 것을 확인한다. 같은 종류의 모델 설정 오류는 기동 전에 설명 가능한 오류로 차단한다.

완료 기준:

- 기본 감지 플러그인이 YOLO 모델을 정상 로드하고, 시험 카메라 작업자의 `model_ready=true`를 확인한다.
- 송출 중인 시험 카메라가 `/cameras/enabled`에 포함되고 전처리 작업자가 생성된다.
- 사람이 보이는 구간에 신선한 `/objects` 응답과 유효한 박스 좌표가 반환되며 Desktop에 표시된다.
- 추적 ID가 있는 새 사람이 출현하면 `person_appeared`가 저장·표시되고, 설정된 사라짐 유예 시간 이후 `person_disappeared`가 저장·표시된다.
- 상반신 시험 장면에서도 박스와 출현·퇴장 이벤트를 확인한다. 실패하면 모델 검출 실패, 추적 ID 미발급, 전송 실패, 화면 표시 실패를 구분하고 복구 미완료로 기록한다.
- 감지 경로에 PAR 번들을 지정하면 모델 용도가 잘못됐다는 오류를 확인할 수 있다.
- 카메라 송출이 없는 대기 상태와 실제 감지가 동작하는 상태를 진단에서 구분한다.

## 구현 현황 — 2026-11-03

- 안전한 정적 체크포인트 검사로 파일명을 바꾼 PAR 번들도 기본 YOLO 감지 모델 선택에서 거부한다. 올바르지 않은 `.pt` 전체를 임의로 역직렬화하지 않는다.
- 기존 `preprocessing-on` 경로에서 알려진 PAR 번들이 선택됐을 때만 설정을 `yolo11n.pt`로 마이그레이션한다. 원래 `compose.env`는 `compose.env.bak`으로 보존했다.
- 설치 전 모델 검사에서 알려진 PAR 번들을 차단한다. 격리 작업자는 알려진 모델 용도 오류를 `MODEL_FORMAT_INVALID`로 보고한다.
- Preprocessing 준비 상태에서 카메라 작업자 0명을 `idle`로 표시하고, External 진단도 `idle`을 허용한다.
- 회귀 테스트 19개 통과, `git diff --check` 통과.
- 실제 설치 설정은 `MODEL_FILE=yolo11n.pt`, `INFERENCE_DEVICE=auto`, GPU 미요청이다. Preprocessing과 External만 빌드·재생성했고 두 컨테이너 및 Data·MediaMTX·nginx가 healthy다.
- Preprocessing은 `/models/yolo11n.pt`를 선택하고 Data 연결과 Identity가 준비된 상태다. 활성 카메라 작업자는 0명이므로 실제 모델 초기화·감지 프레임은 아직 확인되지 않았다.
- External 진단 함수에서도 `data=ready`, `preprocessing=idle`, 작업자 0명으로 구분되는 것을 확인했다.
- 저장된 설정에는 로컬 카메라 장치가 지정돼 있지 않고, 시험 송출 중인 카메라도 없다. 전신·상반신 바운딩 박스, 이벤트 전달 및 RTSP 인증은 카메라 송출 후 검증해야 한다.

근거 코드:

- `server/compose.yml`: `MODEL_FILE`을 Preprocessing의 `MODEL_PATH`로 전달.
- `server/services/preprocessing/processors/detection/yolo.py`: YOLO 로딩 및 추적 ID 없는 결과 제외.
- `server/services/preprocessing/app/pipeline.py`: 모델 준비 실패 시 추론 건너뜀, 좌표 발행·이벤트 생성.
- `server/services/data/app/api/cameras.py`: 활성 카메라 중 `stream_requested`가 참인 항목만 반환.
- `server/installer/models.py`, `server/operations/compose.py`: 현재 감지 모델 검사는 확장자·크기 또는 존재 여부 중심.
- `server/services/preprocessing/app/main.py`: 작업자 없는 상태에서도 준비 상태가 `ready`일 수 있음.

모델별 올바른 역할:

| 역할 | 모델 | 연결 위치 |
| --- | --- | --- |
| 사람 위치 감지·추적 | `yolo11n.pt` | Preprocessing의 `MODEL_FILE` → `MODEL_PATH` |
| 인물 재식별 | `osnet_x0_25_msmt17.onnx` | `IDENTITY_MODEL_PATH` |
| 사람 크롭의 속성 분석 | `par_serving_exp3.pt` | Analysis의 `PersonAttributeAnalyzer`, 기본 경로 또는 `PAR_MODEL_PATH` |

## 3. 작업 범위

이번 작업에는 감지 설정 복구, 기본 YOLO 경로의 PAR 오지정 차단, 모델 실패 원인 전달, 감지 상태 진단, 실제 표시 검증을 포함한다.

추적 ID 없는 박스에 임시 ID를 붙이는 기능, 신뢰도 임계값 변경, 추적기 교체, 송출·녹화 정책 분리, GPU 전환, PAR 분석 기능 활성화는 포함하지 않는다. 정상 YOLO로 복구한 뒤에도 상반신 장면만 실패하면 실제 검출·추적 결과를 근거로 별도 수정 범위를 정한다.

기존 미커밋 변경을 유지하고 이번 원인에 직접 연결되는 부분만 수정한다. PAR 설치·분석 자체는 `docs/analysis-model-integration-plan.md`의 별도 범위이며, 이 문서의 과거 적용 기록을 현재 운영 설정으로 간주하지 않는다.

## 4. 실행 순서

### 1단계 — 기준 상태 기록과 감지 설정 복구

작업:

1. 실제 사용하는 Compose env 경로, 감지 플러그인, 모델 경로, 컨테이너 이미지, 카메라 송출·녹화 상태를 다시 확인한다. 인증값은 출력하지 않는다.
2. 설정 파일을 백업하고, 준비된 `yolo11n.pt`의 존재·크기·출처를 확인한다. 모델을 검사하기 위해 제한 없는 역직렬화 코드를 새로 도입하지 않는다.
3. 기본 YOLO 플러그인을 사용하는 경우 `MODEL_FILE=yolo11n.pt`로 복구한다. PAR 파일과 재식별·분석 설정은 보존한다.
4. 기존 설치 env와 Compose 구성을 사용해 Preprocessing만 재생성한다. 환경변수 변경은 단순 restart로 반영되지 않으므로 컨테이너를 다시 만든다. 설정만 바꾼 경우 이미지 재빌드는 생략하고, 코드 변경 반영이 필요할 때 해당 이미지만 빌드한다.
5. 실행 컨테이너가 `/models/yolo11n.pt`를 선택했는지 확인한다.

검증:

- 모델 로딩에서 `KeyError: 'model'`이 사라진다.
- 기존 Data·External·MediaMTX 및 저장 데이터가 유지된다.
- 카메라가 꺼져 있다면 작업자 0명을 정상 대기로 기록하고, 모델 추론 성공 판정은 실제 시험 단계에서 수행한다.

### 2단계 — 모델 오지정 차단과 실패 원인 전달

대상:

- `server/installer/models.py`
- `server/operations/compose.py`
- `server/services/preprocessing/processors/detection/yolo.py`
- `server/services/preprocessing/processors/detection/isolation.py`
- `server/services/preprocessing/app/pipeline.py`

작업:

1. 기본 YOLO 감지 경로에서 PAR 번들을 거부하는 최소 검증을 추가한다. 파일명에만 의존하지 않고 안전한 정적 메타데이터 검사로 알려진 PAR 형식을 구분한다.
2. 설치 시 선택과 “감지·식별 켜기”의 기동 전 검사에 같은 판정 기준을 적용한다. 이미 잘못 저장된 설정도 기동 전에 발견해야 한다.
3. 정적 검사를 모든 YOLO 형식의 완전한 호환성 검증으로 취급하지 않는다. `.onnx`·`.engine` 및 교체 플러그인의 기존 지원 범위를 불필요하게 제한하지 않는다.
4. 격리 프로세스가 모델 준비 실패를 보고할 때 정제된 오류 코드와 예외 종류를 전달한다. 부모 작업자 상태와 진단에서 “모델 용도 불일치”와 일반 로딩 실패를 구분한다.
5. 임의의 예외 원문·전체 스택·인증 포함 URL을 사용자 응답에 전달하지 않는다. 기존 오류 전달 경로를 우선 사용한다.
6. 사용자가 지정한 임의 모델을 자동으로 다른 파일로 바꾸지 않고, 올바른 설정 위치와 필요한 조치를 안내한다.

검증:

- 이름을 바꾼 PAR 번들도 기본 YOLO 경로에서 차단된다.
- 올바른 모델 선택과 기존 플러그인 경로가 유지된다.
- 모델 준비 실패가 단순 `startup_error`로만 소실되지 않는다.
- 테스트 오류에 포함된 가짜 인증값이 상태·진단 응답에 노출되지 않는다.

### 3단계 — 대기·감지·장애 상태 진단 정리

대상:

- `server/services/preprocessing/app/main.py`
- `server/services/preprocessing/app/supervisor.py`
- `server/services/external/app/diagnostics.py`
- 필요할 때 해당 진단을 표시하는 Desktop 코드

작업:

1. 기존 `worker_count`, 카메라 목록, `model_ready`, 프레임·좌표 전송 상태를 사용해 서비스 준비와 실제 감지 동작을 구분한다.
2. 송출 요청이 없는 경우에는 “감지 대상 카메라 대기”로 설명한다. 작업자 0명이라는 이유만으로 정상 대기를 장애 처리하지 않는다.
3. 송출 대상이 있는데 갱신 주기 이후에도 작업자가 생성되지 않거나 모델·프레임이 준비되지 않으면 해당 원인을 표시한다.
4. HTTP 200 또는 Docker `healthy`만으로 감지 정상 표시를 하지 않는다. 기존 HTTP 상태 코드와 응답 계약은 가능한 한 유지한다.

검증:

- 카메라 없음·송출 중지: 대기로 구분.
- 송출 중·모델 로딩 실패: 모델 장애로 구분.
- 모델 정상·RTSP 입력 실패: 영상 입력 장애로 구분.
- 모델·프레임·좌표 전송 정상: 감지 동작 상태로 구분.

### 4단계 — 시험 카메라 입력과 RTSP 확인

작업:

1. 시험할 카메라 한 대를 정하고 기존 송출·녹화 상태를 기록한다. 기존 UI의 시작 절차를 사용해 시험 영상을 송출한다.
2. `enabled=true`, `stream_requested=true`와 실제 송출 여부를 확인한다. 현행 코드에서는 송출 요청과 녹화 설정이 함께 바뀌므로 시험 종료 시 원래 상태를 복원한다.
3. 카메라 목록 갱신 이후 작업자 생성, `model_ready=true`, 최근 프레임 수신을 확인한다.
4. RTSP 401이 지속되면 같은 시각의 Preprocessing·MediaMTX·External 로그를 대조해 인증 거절, 송출 상태, 연결 실패를 구분한다. 과거 로그만 보고 인증키를 재발급하지 않는다.
5. 입력과 모델이 정상화되기 전에는 임계값·추적 정책을 변경하지 않는다.

검증:

- 시험 카메라가 `/cameras/enabled`에 포함된다.
- 해당 작업자가 생성되고 프레임 수신 시각이 계속 갱신된다.
- 반복 RTSP 401과 `inference_stream_lost`가 해소된다. 해소되지 않으면 원인과 로그 시각을 기록하고 표시 성공으로 판정하지 않는다.

### 5단계 — 박스·이벤트 전달과 상반신 장면 검증

작업:

1. Desktop 모니터를 먼저 연 뒤 사람이 새로 들어오는 장면을 만든다. 현재 이벤트 폴러는 시작 시점 이후 이벤트를 조회하므로 기존 이벤트 부재와 생성 실패를 혼동하지 않는다.
2. 전신이 보이는 기준 장면과 상반신만 보이는 장면을 같은 카메라에서 각각 확인한다.
3. 각 장면에서 모델 준비, 검출 수, 추적 ID, 좌표 PUT 성공, `/objects` 신선도, 화면 표시를 순서대로 확인한다.
4. 출현 이벤트의 Data 저장과 External 조회, Desktop 타임라인 표시를 확인한다. 같은 추적 ID가 계속 보이는 동안 출현 이벤트가 반복되지 않는 현행 동작을 유지한다.
5. 사람이 화면에서 사라진 뒤 설정된 유예 시간을 지나 퇴장 이벤트가 표시되는지 확인한다.
6. 상반신 장면만 실패하면 검출 여부와 추적 ID 유무를 확인한 뒤 필요한 후속 수정 범위를 제시하고 복구를 미완료로 기록한다. 앞선 가짜 박스 재현만으로 실제 장면의 추적 실패를 확정하지 않는다.

검증:

- 사람이 보이는 구간에 `objects`가 비어 있지 않고 `stale=false`이다.
- 관측 시각 기준 3초 유효 기간 안에 좌표가 조회되며 원본 영상 크기 내 유효한 박스로 표시된다.
- 출현·퇴장 이벤트의 카메라와 추적 세션이 일치하고 새 이벤트가 타임라인에 표시된다.
- 상반신 장면의 성공 여부와 실패 시 중단 단계가 기록된다.

## 5. 회귀 검증

코드 수정 전에 현재 관련 테스트의 기준 결과를 기록하고, 변경한 동작을 검증하는 최소 회귀 테스트를 추가한다.

| 검증 대상 | 위치·방법 | 확인 내용 |
| --- | --- | --- |
| 모델 오지정 | 설치 모델 검증·전처리 테스트 추가 | PAR 오지정 차단, 파일명 변경에도 같은 판정, 기존 모델·플러그인 지원 유지 |
| 기동 전 검사 | `server/tests/test_operations_compose.py` | 잘못 저장된 모델 선택 거부와 올바른 설정 통과 |
| 격리 오류 전달 | 전처리 테스트 추가 | 준비 실패 코드 전달, 인증값 비노출 |
| 감지 진단 | 전처리 준비 상태 테스트 및 `server/services/external/tests/test_preprocessing_diagnostics.py` | 정상 대기·모델 장애·실제 감지 상태 구분 |
| 화면 좌표 | `server/setup/install_helper/tests/test_overlay.py` | 기존 좌표 변환·stale 처리 회귀 없음 |
| 실제 동작 | 4·5단계 현장 검증 | 프레임 → 감지 → 좌표 → 이벤트 → Desktop 표시 |

가짜 결과를 사용하는 단위 테스트와 실제 모델·카메라 검증 결과는 따로 기록한다. 상반신 장면의 정확도는 단위 테스트 통과만으로 보장하지 않는다.

## 6. 복구와 결과 기록

- 설정 백업과 변경 항목을 기록하고, 시험 중 바뀐 카메라 송출·녹화 상태를 원래대로 복원한다.
- 코드 배포에서 문제가 생기면 이번 변경 파일과 해당 서비스 이미지만 되돌린다. 기존 미커밋 변경을 일괄 되돌리지 않는다.
- 최초 백업에는 잘못된 `MODEL_FILE`이 들어 있으므로 백업 전체를 무조건 복원하지 않는다. 감지 경로는 검증된 YOLO 설정을 유지하고 나머지 값만 필요한 범위에서 복원한다.
- 인증키 재생성, DB 초기화, 녹화·이벤트 삭제, 전체 서버 재설치는 복구 방법으로 사용하지 않는다.
- 최종 결과에는 변경 파일, 실행 모델·장치, 회귀 테스트 결과, 카메라 작업자 상태, 전신·상반신 표시 결과, 이벤트 저장·조회 결과, 남은 RTSP 오류를 기록한다.

실행 순서: **YOLO 설정 복구 → 오지정 차단·오류 전달 보완 → 상태 진단 보완 → 카메라 입력 검증 → 박스·이벤트 및 상반신 장면 검증**.
