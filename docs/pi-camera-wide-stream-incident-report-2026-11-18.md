# Pi Camera Wide 영상 송출 장애 종합 보고서

> 이후 12:12 KST에 영상 부재가 재발했다. 이 문서의 복구 완료 표시는 앞선 복구 시점의 기록이며, 최신 조사 상태는 [재발 조사 보고서](pi-camera-wide-stream-recurrence-2026-11-18.md)를 따른다.

- 작성일: 2026-11-18, 한국 표준시(KST, UTC+9)
- 대상: Raspberry Pi Edge `edge-001`, 카메라 `cam-001` / `raspi_01`, Windows AI CCTV 서버
- 최종 상태: **실시간 영상 복구 — 사용자 재생 확인 완료. Edge 재발 방지 코드 수정 및 재시작 안정성 검증은 남아 있음.**
- 근거: 서버 운영 로그·DB·설정·컨테이너 조회, 사용자 세션의 제어판·관제 앱 확인, 사용자가 제공한 Pi 로그와 소켓 조회 결과, 복구 후 사용자의 “된다” 확인
- 이 문서는 [최초 조사 및 재조사 기록](pi-camera-wide-stream-investigation-2026-11-18.md)을 최종 복구 결과까지 통합한 보고서다. 보고서 작성 단계에서는 서비스를 추가 변경하거나 재시작하지 않았다.

## 1. 결론

이번 장애는 카메라 인식 여부만으로 설명되지 않는 **송출 경로의 복합 문제**였다.

1. **서버 제어판의 HTTP 네트워크 적용 결함:** HTTP 모드에서도 TLS 인증서를 처리해 오류가 발생하고 IP 설정이 이전 값으로 복원됐다. 화면의 새 입력값과 실제 운영 설정이 달랐다.
2. **직결 네트워크 주소 설정 문제:** 서버 RTSP가 VirtualBox 주소 `192.168.1.10`에만 열려 있었다. 이를 직결 이더넷 주소 `192.168.50.1`로 적용한 뒤에도 Pi에는 이전 송출 목적지 `192.168.1.10`이 남아 있었다.
3. **최종 복구를 막은 Edge 내부 소켓 경로 불일치:** 오래된 `cam-001.h264.sock` 파일이 남아 있는 동안 실제 캡처는 `cam-001.h264.sock.0`에서 수신 대기했다. Publisher는 고정된 원래 경로를 읽으므로 캡처 영상을 받지 못했다.

서버 적용 결함을 코드로 수정하고, 주소 정합성을 맞추도록 안내한 뒤, Edge 서비스를 중지해 남은 소켓을 정리하고 다시 시작하는 절차를 제공했다. 마지막 절차 후 사용자가 영상 재생 성공을 확인했다.

**현재는 운영 복구 상태다. Edge가 잔존 소켓에서 자동 복구하도록 하는 영구 수정은 아직 수행하지 않았다.**

## 4. 문제별 원인과 해결 상태

### 4.1 HTTP 모드의 IP 변경이 TLS 오류로 롤백됨 — 수정 완료

제어판에서 RTSP Bind IP를 입력한 후 실제 적용을 실행하자 다음 오류가 발생했다.

```text
TLS certificate does not exist or is not a file: C:\ProgramData\AI_CCTV\certs\tls.crt
```

`validate_network_settings()`는 HTTP 모드에 TLS 인증서를 요구하지 않았다. 그러나 이후 `apply_network_settings()`가 `_replace_tls_material()`을 무조건 호출해 제어판에 채워진 기본 인증서 경로를 검사했다. 파일이 없어 실패하면 env와 YAML이 원래 값으로 복원됐지만 화면의 새 입력값은 남아 있었다.

수정한 내용:

- [네트워크 적용 코드](../server/operations/network.py): TLS 파일 스냅샷·교체를 HTTPS 모드에만 수행하도록 조건 추가.
- [네트워크 회귀 테스트](../server/setup/install_helper/tests/test_network_settings.py): 기본 TLS 파일이 없는 HTTP 환경에서도 RTSP IP 변경이 적용되는 사례 추가.
- 수정 전 동일 오류로 테스트가 실패하는 것을 확인했고, 수정 후 관련 테스트 **7개 통과**. HTTPS 검증, Compose 검증 실패 롤백, 서비스 시작 실패 롤백도 통과했다.
- `git diff --check` 통과. 제어판과 관제 앱을 새 코드·설정을 읽도록 다시 실행했다.

이 수정은 현재 작업 폴더의 소스와 소스 실행 환경에 반영됐다. 별도 배포 실행 파일 재빌드·릴리스는 수행하지 않았다.

### 4.2 서버·Pi의 RTSP 주소 정합성 — 서버 적용 완료, Pi 변경 안내 후 재생 복구

최초 서버 운영 설정과 실제 Docker 포트 매핑은 모두 `192.168.1.10:8554`였다. 물리 직결 주소 `192.168.50.1:8554`로의 호스트 TCP 연결은 Windows 오류 10061로 거절됐다.

서버 변경 후 확인한 값은 다음과 같다.

```text
RTSP_BIND_ADDRESS=192.168.50.1
RTSP_PORT=8554
RTSP_PUBLIC_HOST=192.168.50.1
RTSP_PUBLIC_PORT=8554
```

실제 Docker 포트 매핑도 새 주소로 변경됐으며 TCP 연결에 성공했다. 이후 제공된 Pi 설정은 여전히 다음과 같았다.

```toml
camera_id = "cam-001"
mode = "central_publish"
central_host = "192.168.1.10"
central_port = 8554
```

따라서 Pi의 `[rtsp].central_host`도 `192.168.50.1`로 맞추도록 안내했다. 최종 설정 파일을 다시 읽어 검증하지는 않았으므로, 보고서에는 이를 직접 확인된 적용값으로 기재하지 않는다. 사용자는 후속 소켓 정리 절차 후 영상 복구를 확인했다.

최초에는 서버와 Pi 양쪽에 같은 이전 주소가 들어 있었다. 따라서 모든 시점의 장애를 단순한 주소 문자열 불일치 하나로 설명하지 않는다. 직결 구성에서 사용할 수신 주소 문제와, 서버 변경 후 Pi에 남은 이전 목적지를 구분해야 한다.

### 4.3 오래된 소켓과 실제 LISTEN 소켓 경로가 다름 — 수동 정리로 복구, 영구 수정 대기

사용자가 제공한 11:26 조회 결과의 핵심은 다음과 같다.

```text
cam-001.h264.sock    파일 시각 10:40
cam-001.h264.sock.0  파일 시각 11:26

LISTEN /run/ai-cctv-edge/cam-001.h264.sock.0
users: ai-cctv-edge, pid=3563
```

원래 `.sock`은 파일만 남아 있고 해당 경로의 LISTEN 프로세스는 조회되지 않았다. 실제 캡처는 `.sock.0`에서 대기 중이었다. 반면 [Publisher](../edge/src/ai_cctv_edge/publisher.py)는 `/run/ai-cctv-edge/cam-001.h264.sock`을 고정 경로로 읽는다.

즉, **캡처가 영상을 제공하는 소켓과 Publisher가 접속하는 소켓이 달랐다.** 이는 다음 반복 실패와 서버의 게시자 부재를 설명한다.

```text
gst_poll_remove_fd: assertion 'fd->fd >= 0' failed
RuntimeError: GStreamer publisher could not enter PLAYING state
central publisher exited with code 1; local backup continues
```

약 30초 간격의 반복은 [Edge 감독 루프](../edge/src/ai_cctv_edge/runner.py)의 Publisher 재시도 간격과 부합한다. 이 로그만으로 로컬 녹화 파일의 완전성까지 보장되지는 않는다.

오래된 소켓이 최초에 남은 이유는 확인되지 않았다. 강제 종료, 비정상 종료 또는 정리 누락 중 하나를 확정 원인으로 기재하지 않는다.

### 4.4 초기화 실패의 상세 오류가 로그에서 사라짐 — 개선 필요

현재 Publisher는 `set_state(PLAYING)`이 실패하면 일반 RuntimeError를 발생시킨다. GStreamer bus에 쌓인 원래 오류를 읽기 전에 예외로 빠지므로, 실제 실패 요소·소켓 경로·운영체제 오류를 확인하기 어렵다. 예외 상태 파일에도 예외 종류만 기록하는 경로가 있다.

이 때문에 첫 로그만으로 주소 문제와 내부 소켓 문제를 구분하기 어려웠고, 파일·LISTEN 상태를 추가 조회해야 했다. 상세 진단 보강 코드는 아직 수정하지 않았다.

## 5. 실제 복구 절차와 재발 시 대응

이번에 사용자에게 제공했고 이후 영상 복구 확인을 받은 절차는 다음과 같다.

```bash
sudo ai-cctv-edge stop
sudo rm -f -- /run/ai-cctv-edge/cam-001.h264.sock /run/ai-cctv-edge/cam-001.h264.sock.0
sudo ai-cctv-edge start
```

이 명령은 해당 카메라의 런타임 소켓을 정리한다. 카메라 ID가 다른 장치에는 그대로 적용하지 않는다. **재발 시에는 먼저 서비스가 중지됐고 해당 소켓을 사용하는 프로세스가 없는지 확인한 뒤 정리한다. 실행 중인 소켓은 삭제하지 않는다.**

확인 명령:

```bash
systemctl is-active ai-cctv-edge
sudo ss -xlpn | grep -F 'cam-001.h264.sock'
```

정리 전에는 Edge 서비스가 inactive이고 해당 소켓의 LISTEN이 없어야 한다. 다시 시작한 뒤에는 `.0`이 아닌 원래 `cam-001.h264.sock`에서 LISTEN하는지 확인하고 관제 화면에서 실제 재생을 확인한다. 이번 최종 복구 후의 소켓 재조회 결과는 별도로 받지 않았다.

## 6. 현재 검증 수준

| 항목 | 상태 | 근거·한계 |
|---|---|---|
| 서버 HTTP 설정 적용 결함 | 수정·테스트 완료 | 회귀 재현 후 7개 테스트 통과 |
| 서버 RTSP 실제 주소 | 적용·접속 확인 완료 | Docker 매핑과 TCP 연결 확인 |
| 로컬 카메라 송출 | 서버에서 복구 확인 | H264 게시, ready=true, 수신 바이트 확인 |
| Pi 실시간 영상 | 사용자 복구 확인 | 소켓 정리 안내 후 “된다” 응답 |
| Pi 최종 설정 파일·소켓·수신 바이트 | 복구 후 재조회 미실시 | 앞선 진단 결과와 사용자 재생 확인을 구분 |
| Pi 중앙 녹화 신규 파일·DB 등록 | 복구 후 미검증 | 실시간 재생 성공만으로 완료 판정하지 않음 |
| Pi 로컬 녹화 연속성·파일 무결성 | 복구 후 미검증 | 과거 복구 파일과 로그는 있었으나 최종 연속성 시험 없음 |
| 정상 종료 후 재시작·Pi 재부팅 | 미검증 | 재발이 없다고 보장할 수 없음 |
| Edge 잔존 소켓 자동 정리 | 미구현 | 이번에는 수동 정리로 복구 |
| 장시간 연속 재생 | 미검증 | 복구 후 지속 관찰 수치 없음 |

서버의 healthy 상태, 시작 API의 HTTP 200, 카메라 인식 성공은 각각 프로세스·요청·입력에 대한 결과다. 실제 송출·재생·녹화 성공과 동일하지 않다.

인증 문제도 주원인으로 확정되지 않았다. 조사 당시 현재 서버 읽기 계정으로 RTSP DESCRIBE를 수행하면 Pi는 404, 로컬 카메라는 200이었다. `action=read credential_mismatch` 경고만으로 Pi 게시 자격증명을 잘못됐다고 판단하거나 재발급하지 않았다.

## 7. 재발 방지 작업안

다음은 **미실행 후속 작업안**이다. 이 보고서 작성으로 Edge 코드를 추가 변경하지 않았다.

| 우선순위 | 작업 | 범위·구현 원칙 | 완료 기준 |
|---|---|---|---|
| P0 | 캡처 시작 전 잔존 소켓 처리 | 기존 카메라 실행 잠금을 확보하고 이전 캡처·Publisher가 종료된 상태에서 해당 카메라의 잔존 소켓만 정리. 활성 리스너나 다른 소유자가 있으면 삭제하지 않고 명확히 실패 처리 | 잔존 `.sock`이 있는 조건에서도 수동 rm 없이 원래 경로로 캡처·Publisher 연결 |
| P0 | 종료·재시작 정리 순서 확인 | Publisher와 캡처의 종료·대기·GStreamer NULL 전환 및 소켓 수명 확인. 정상 종료와 오류 경로 모두 검증 | 반복 stop/start·서비스 restart·Pi 재부팅 후 경로 불일치 및 중복 Publisher 없음 |
| P1 | Publisher 초기화 오류 기록 | PLAYING 실패 시 GStreamer bus 오류를 읽어 요소·경로·오류 원인 기록. 인증값은 가림 처리 | 소켓 없음·권한 오류·RTSP 연결 실패를 로그에서 구분 가능 |
| P1 | 제어판 적용 결과 명확화 | 적용 실패·롤백을 명시하고 실제 저장값을 다시 표시. 입력 검증 성공과 실제 적용 성공을 구분 | 실패 후 화면과 운영 설정의 차이를 사용자가 오인하지 않음 |

기존 [카메라 실행 잠금](../edge/src/ai_cctv_edge/runner.py), [캡처 종료 처리](../edge/src/ai_cctv_edge/capture.py), [소켓 생성 파이프라인](../edge/src/ai_cctv_edge/pipeline.py)을 활용해 최소 범위로 수정한다. 실행 중인 소켓을 주기적으로 무조건 삭제하는 방식은 사용하지 않는다.

검증은 격리된 테스트와 Pi 실장비에서 나눠 수행한다. 실장비에서는 새 게시 세션의 H264 트랙, 시간차를 둔 수신량 증가, 화면 변화, 중앙 녹화 등록까지 확인한다. 비정상 종료 상황은 운영 녹화 중 임의로 재현하지 않고 별도 시험에서 검증한다.

Edge 영구 수정 후에는 ARM64 DEB 빌드·설치와 실장비 검증이 필요하다. 이번 수동 복구를 위해 DEB 재설치나 게시 자격증명 변경을 요구하지는 않았다.

## 8. 종료·재시작 운영 메모

관제 창을 닫아도 송출·녹화 요청은 유지된다. 서비스를 종료하려면 별도 중지 명령을 사용한다.

Pi 종료:

```bash
sudo ai-cctv-edge stop
sudo poweroff
```

Windows 서버 서비스 중지:

```powershell
.\ai_cctv.ps1 cli stop
```

정상 종료 후 전원을 분리하는 방식으로 운영한다. 다만 종료·재기동 반복 시험은 아직 수행하지 않았으므로, 이번 복구만으로 다음 기동 때 잔존 소켓 문제가 재발하지 않는다고 보장하지 않는다.
