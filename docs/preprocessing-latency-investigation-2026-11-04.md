# Preprocessing 지연·이벤트 미생성 조사

조사일: 2026-11-04, Asia/Seoul. 운영 설정·서비스 재시작·카메라 기동 없이 로그와 저장 데이터, 운영 이미지의 카메라 없는 추론을 확인했다.

## 확인한 운영 상태

- Preprocessing은 GPU 이미지로 healthy이지만 `/health/ready` 본문은 degraded다. 현재 worker_count=0, Data 연결 정상, event outbox pending/rejected/waiting=0이다.
- 등록된 local-camera는 enabled=true, stream_requested=false, recording_enabled=false, offline이다. 컨테이너를 켜는 것만으로 이 상태의 카메라 작업자가 생성되지는 않는다.
- 오늘 13:11:13, 13:12:17, 13:13:21에 `inference failed; video monitoring and model retry continue`가 기록됐다. 모델 설정 디렉터리 경고도 각 재생성 때 반복됐다.
- 오늘 저장된 새 이벤트는 ID 7의 inference_stream_lost 한 건이다. 발생 13:13:24.834, 저장 13:13:25.477로 약 0.643초다. 오늘 person_appeared 이벤트는 없다. 따라서 오늘 증상의 주요 실패는 타임라인 조회 이전에 발생했다.
- nginx 로그에서 Desktop은 초기 최신 30건 조회와 after_event_id=6 증분 조회를 실제 사용했고 200 응답을 받았다. 이전 발생시각 기반 폴러가 실행되는 상황으로 보이지 않는다. 다만 이 로그만으로 UI 렌더링 성공은 입증할 수 없다.

## 카메라 없는 실제 GPU 추론 측정

운영 이미지와 같은 GPU·모델·10초 process 제한·30초 startup 제한을 사용했다. 격리 프로세스와 직접 호출을 각각 측정했다. 실제 카메라는 열지 않았고, 사람 이미지 시험은 이미 저장된 이벤트 5의 원본 스냅샷을 사용했다. 시험은 Data 이벤트를 생성하지 않는다.

| 입력/실행 | 모델 준비 | 첫 프레임 | 이후 프레임 | 검출 |
| --- | ---: | ---: | ---: | --- |
| 검은 1280×720, 격리 | 7.084초 | 6.878초 | 0.128 / 0.071초 | 0 |
| 검은 1280×720, 직접 | 5.718초 | 5.795초 | 0.071 / 0.127초 | 0 |
| 기존 사람 이미지, 격리 | 13.430초 | 7.458초 | 0.103 / 0.071초 | 1 |
| 기존 사람 이미지, 직접 | 11.330초 | 6.420초 | 0.110 / 0.071초 | 1 |

GPU 자체와 사람 검출 경로는 동작했다. 사람 이미지의 격리 실행에서 모델 준비와 첫 프레임 합계는 약 20.888초였다. 이 값은 카메라 연결·좌표 HTTP·UI 표시·대표 이미지 저장 시간을 포함하지 않는다. 현재 상반신 영상의 정확도 또는 운영 중 실패 재현으로 해석하지 않는다.

## 원인과 증거 수준

1. **확인: GPU 초기 준비가 실시간 첫 프레임에 포함된다.** `YoloTracker.__init__`는 YOLO 파일을 읽고 실행 장치를 정하지만 GPU 추론 준비를 완료한 상태로 만들지는 않는다. `_serve`는 첫 GPU 추론 전에 ready를 보낸다. 첫 실제 프레임에서 추가 6~7초가 측정됐다. 모델 재생성 때마다 초기 비용이 다시 발생한다.
2. **확인: 첫 감지 좌표가 표시 전에 만료될 수 있다.** Data `get_live_objects`는 observed_at 기준 3초가 지나면 objects=[]/expired로 반환한다. 첫 추론만 7.458초였으므로 캡처 때 기록한 관측 시각을 사용하는 첫 좌표는 서버에서 이미 만료된다. 이후 최신 프레임 처리까지 성공해야 박스가 나타날 수 있다.
3. **강한 의심, 미확정: 초기 추론과 10초 제한·30초 재시도가 반복 실패를 만든다.** 실제 실행은 DETECTION_MODEL_TIMEOUT_SECONDS=10, MODEL_RETRY_SECONDS=30이다. 오늘 실패 간격은 약 64초로, 모델 준비·첫 추론 실패·30초 재시도 경로와 부합한다. 그러나 카메라 없는 시험에서는 첫 추론이 10초 이내에 끝나 시간초과 자체는 재현되지 않았다. 운영 실패가 TimeoutError인지 모델 내부 예외인지는 현재 로그로 확정할 수 없다.
4. **확인: 실패 원인을 확인할 관측 정보가 소실된다.** 자식 프로세스의 process 예외는 kind=error만 보내며 부모는 DETECTION_MODEL_FAILED로 바꾼다. pipeline은 error_code를 logging extra에 담지만 현재 출력에는 나타나지 않는다. 작업자가 제거되면 /status에서도 당시 timings와 오류가 사라진다. 실패한 추론의 시간도 성공 이후에만 기록되는 현재 timing 경로에 남지 않는다.
5. **확인: 오늘 출현 이벤트는 생성·저장되지 않았다.** 박스/출현 전환은 tracker.process가 성공한 뒤에 처리되므로 앞 단계가 실패하면 둘 다 생기지 않는다. outbox 적체 또는 ID 증분 API 누락이 오늘 문제의 주원인이라는 증거는 없다.
6. **확인: RTSP 401은 마지막 추론 실패 뒤에 발생했다.** MediaMTX 송출 종료는 13:13:24, RTSP 401은 13:13:26 이후다. 이 순서로는 앞선 세 차례 추론 실패를 RTSP 인증 오류만으로 설명할 수 없다. 송출이 중단된 현재 상태에서는 영상도 다시 처리되지 않는다.

Matplotlib/Ultralytics는 쓰기 불가 설정 디렉터리에서 /tmp로 폴백했다. 시험에서도 같은 경고 후 추론이 성공했으므로 경고 자체를 감지 실패의 직접 원인으로 단정하지 않는다. 재생성마다 설정·캐시 초기화 비용은 줄일 필요가 있다.

## 수정 우선순위

1. process 예외의 정제된 유형·오류 코드, 실패 소요시간, 요청 단계와 카메라를 반드시 로그·상태에 남긴다. 중지된 작업자의 최근 진단도 보존한다.
2. GPU 준비/첫 추론과 정상 프레임 추론의 시간 제한을 구분한다. 준비 완료 뒤 ready를 알리고, 준비에 사용한 추적 상태는 초기화한다. 단순히 모든 프레임의 제한 시간을 크게 늘리는 것으로 대체하지 않는다.
3. 준비 완료 후 최신 캡처 프레임을 선택해 관측 시각이 오래된 첫 박스를 발행하지 않도록 한다. 3초 만료 정책을 무작정 늘리거나 occurred_at을 저장 시각으로 바꾸지 않는다.
4. writable 설정·캐시 경로를 명시하고, 재준비를 반복하는 실제 오류를 위 진단으로 분류한다.
5. 같은 저장 이미지에서 전체 CameraWorker 경로의 좌표 발행·관측 후보 확정·이미지 저장을 재현한 뒤, 허용된 실시간 카메라에서 첫 표시와 정상 갱신을 각각 측정한다. 현재 현장 검증 보류는 유지했다.

진단 재현 스크립트: `server/tools/diagnose_detection_latency.py`. 이번 조사에서는 생산 동작 코드를 수정하거나 운영 서비스를 재시작하지 않았다.
