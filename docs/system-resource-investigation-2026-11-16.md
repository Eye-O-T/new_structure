# CPU·메모리 사용량 및 시스템 지연 진단

- 진단일: 2026-11-16, 약 09:50~09:57 KST
- 대상: 현재 Windows 호스트와 실행 중인 AI CCTV Docker 서비스
- 수행 범위: 프로세스, 성능 카운터, 컨테이너 상태, 서비스 진단 API, 관련 소스 읽기. 운영 설정 변경·서비스 종료·재시작은 수행하지 않았다.

## 결론

현재 지연의 가장 강한 원인은 **영상 처리·관리 화면·데이터 처리가 동시에 실행되면서 발생하는 CPU 포화**다. 전체 CPU는 연속 세 표본에서 100%, 99%, 100%였다. 컨테이너에 CPU 상한이 없어 호스트의 응답성을 보호하지 못한다.

메모리 사용량도 높지만, WSL 점유분의 상당 부분은 **회수 가능한 Linux 파일 캐시**다. 측정 중 심한 페이징이나 메모리 부족 종료는 관찰되지 않았다. 이 상태를 곧바로 메모리 누수로 판단할 근거는 없다. CPU 부하를 먼저 줄이고 WSL의 최대 메모리와 캐시 회수 상태를 함께 관리하는 것이 적절하다.

GPU 전환은 이미 적용되어 있다. 두 카메라의 YOLO 실행 장치는 `cuda:0`, OSNet은 `CUDAExecutionProvider`로 보고되었다. 전날 작성된 CPU 운영 기록은 현재 상태와 다르므로 이번 판단의 기준으로 사용하지 않았다.

Docker CPU의 100%는 논리 CPU 한 개 수준이다. 예를 들어 418%는 약 4.18개 CPU 상당이며, Windows 작업 관리자 전체 CPU 418%라는 뜻이 아니다. 논리 CPU 8개 기준으로 단순 환산하면 약 52% 규모다. 서로 다른 시점의 Windows·Docker 표본은 합산하지 않았다.

성능 카운터·Docker 명령 자체도 부하를 만든다. 일부 표본에 WMI·진단용 sandbox 프로세스가 포함되었으므로 모든 100% 사용을 서비스 탓으로 돌리지는 않는다. 다만 여러 Docker 표본과 관리 앱의 지속 부하는 별도로 확인되었다. 디스크 지연 카운터는 정수화된 출력에 한계가 있어 지연시간 0ms를 보장하는 근거로 사용하지 않았다.

## 원인과 개선 대상

### 1. CPU 상한 부재 — 확인

실행 중인 전처리·데이터·분석·MediaMTX의 `NanoCpus`, `CpuQuota`는 모두 0이었다. 전처리에는 4GiB 메모리 상한과 `cpu_shares: 512`가 있지만 CPU 하드 상한은 없다. 데이터·분석에는 개별 메모리 상한도 없다.

[`server/compose.yml`](../server/compose.yml)의 `cpu_shares`는 컨테이너 사이 상대 가중치다. Windows UI를 위한 CPU 용량을 보장하거나 최대 CPU 사용량을 제한하지 않는다. 하드 상한에는 `cpus` 또는 CPU quota가 필요하다. [Docker 자원 제한 문서](https://docs.docker.com/engine/containers/resource_constraints/)

### 2. 추론 FPS와 별개로 계속되는 디코딩·복사 — 코드 경로 확인, 비용 비율은 미측정

실제 분석 설정은 카메라당 5fps이며 두 카메라가 동작한다. 그러나 [`camera_capture.py`](../server/services/preprocessing/app/camera_capture.py)는 RTSP를 계속 `capture.read()`하여 최신 한 장을 남긴다. [`pipeline.py`](../server/services/preprocessing/app/pipeline.py)의 분석 FPS 제한은 프레임을 읽은 뒤 적용된다. 따라서 분석 FPS만 낮추어도 원본 영상 디코딩 비용이 같은 비율로 줄지는 않는다.

관리 앱의 [`video_worker.py`](../server/desktop/admin/video_worker.py)도 스트림을 디코딩하고 매 프레임 RGB 변환·바이트 복사를 한다. 전처리와 화면 표시가 같은 영상을 각각 디코딩한다. GPU 추론이 정상이어도 이 경로에는 CPU 비용이 남는다. 현재 코드에는 해당 열기 경로의 하드웨어 디코딩 요청이 보이지 않지만, 실제 디코더별 CPU 비율은 프로파일링 전이다.

[`isolation.py`](../server/services/preprocessing/processors/detection/isolation.py)는 격리된 탐지 프로세스와 Pipe로 데이터를 교환한다. 서비스 진단에서 IPC p95는 카메라별 약 51~64ms, 전체 추론 p95는 약 231~263ms였다. 프로세스 격리를 유지하면서 전송 크기·복사 비용을 줄일 여지가 있다.

최신 프레임 교체 카운터는 프레임 누적 메모리 누수를 뜻하지 않는다. 현재 구조는 오래된 영상을 버리며 최신 프레임을 유지한다. 관리 앱의 큐도 크기 30으로 제한되어 있다.

### 3. 데이터 API와 녹화 복구의 동시 실행 — 확인, 함수별 기여도는 미확정

데이터 서비스에서 API 프로세스와 복구 자식 프로세스가 함께 실행 중이었다. 별도 3초 표본에서는 API 프로세스가 한 CPU 기준 약 68%, 복구 자식은 약 4%였다. 따라서 데이터 서비스 부하 전체를 복구 작업만의 문제로 단정할 수 없다.

복구 큐는 `indexing=1`, `waiting_for_recovery=8`, `completed=89`였고, 약 2분 뒤에도 같은 개수였다. 복구의 가장 오래된 대기는 약 502초에서 626초로 증가했다. 장기 정체 여부는 추가 관찰이 필요하다. 정상 완료된 AI 작업 외에 과거 녹화 복구가 병행되는 상태다.

로그에는 실시간 객체 PUT, 카메라·사용자·세션 조회와 작업 claim이 반복된다. 관리 앱은 코드상 객체를 0.2초, 이벤트를 0.5초 간격으로 조회한다. 카메라 2대의 주기 조회가 인증 확인과 내부 API 호출로 이어진다.

개선 후보는 [`cameras.py`](../server/services/data/app/api/cameras.py)의 카메라 응답마다 호출되는 [`has_active_recording_file()`](../server/services/data/app/storage/recordings.py)다. 이 함수는 녹화 디렉터리를 순회하고 파일 상태를 확인한다. Windows 경로를 bind mount한 상태에서 반복 파일 조회는 비용을 키울 수 있다. 이 함수가 CPU의 몇 %를 쓰는지는 아직 측정하지 않았다.

### 4. WSL 파일 캐시와 Windows 앱의 동시 메모리 점유 — 확인

WSL 내부 cache/buffers 약 7.4GiB가 호스트의 큰 WSL 작업 집합을 설명한다. 파일 캐시가 녹화·복구·모델 로딩 중 어느 작업에서 얼마나 생겼는지는 이번 표본만으로 구분할 수 없다.

`C:\Users\gksrn\.wslconfig`는 없었다. WSL 내부 총 RAM 약 11.63GiB는 기본 메모리 한도인 호스트 RAM 약 50%와 부합한다. 자동 회수 설정이 없다는 이유만으로 회수 기능이 꺼져 있다고 판단해서는 안 된다. 현재 공식 문서의 `autoMemoryReclaim` 기본값은 `dropCache`다. 지속 부하 중 즉시 회수되는지도 별도로 관찰해야 한다. [Microsoft WSL 설정 문서](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)

Windows 프로세스군 작업 집합은 VS Code 14개 약 2.23GiB, ChatGPT 15개 약 1.17GiB, codex 6개 약 654MiB였다. 이 수치는 공유 메모리가 중복 포함될 수 있어 단순 합계가 실제 물리 사용량과 같지는 않지만, 개발 도구 동시 실행도 가용 RAM을 줄인다.

## 권장 적용 순서

아래 수치는 측정 결과에서 정한 **시험 시작값**이며, 운영 성능을 검증한 최종값이 아니다. 이번 진단에서는 적용하지 않았다.

| 순서 | 조치 | 목적·주의점 |
|---|---|---|
| 1 | 불필요한 관리 영상 창·개발 창을 닫고 같은 장면으로 재측정 | 서비스 중단 없이 UI·개발 도구 기여도 분리. 영상 창을 닫는 동작이 로컬 송출까지 중단하는지 먼저 확인 |
| 2 | 전처리 `cpus: 2.5`, 분석 `cpus: 1.0`을 별도 override로 시험 | AI가 호스트 CPU를 계속 소진하는 것을 제한. 모델 지연·좌표 stale 증가 시 상한을 완화하거나 복원 |
| 3 | WSL 한도를 먼저 RAM 10GB, 논리 CPU 6개로 시험 | 현재 약 12GB/8개에서 줄여 Windows 여유 확보. 논리 CPU 감소는 물리 코어의 독점 예약을 보장하지 않음 |
| 4 | 분석 FPS 5 → 3 시험 | 추론·IPC·후처리 부하 감소. 이동 추적·빠른 등장/이탈을 실제 영상으로 확인. 원본 디코딩 부하는 별도 개선 필요 |
| 5 | 데이터 API 호출·파일 탐색을 프로파일링하고 녹화 상태 조회 캐시 적용 | 데이터 CPU를 줄이는 직접 개선. 녹화 시작·종료 시 캐시 무효화와 짧은 유효기간 필요 |
| 6 | 복구에 작업 간 간격·처리 예산을 추가하고 실시간 API와 자원 분리 | 복구가 실시간 처리를 압박하지 않도록 함. 현재 코드는 작업이 있으면 연속 실행하므로 poll interval 증가만으로는 작업 사이 휴식이 생기지 않음 |
| 7 | 저해상도·저FPS 분석용 서브스트림 또는 검증된 하드웨어 디코딩 적용 | 디코딩·복사량 자체 감소. 원본 녹화 품질은 유지하고 분석 좌표를 원본 크기로 변환 |
| 8 | DB·고빈도 스냅샷 저장소의 Linux 파일시스템/전용 volume 이전 검토 | Windows bind mount 비용 완화. 백업·복원·호스트 도구 호환성을 확인한 뒤 별도 변경으로 진행 |

데이터 컨테이너 전체에 낮은 CPU 상한을 즉시 걸면 복구와 함께 API도 느려진다. 데이터는 프로파일링과 복구 분리를 우선하고, 상한을 도입할 경우 API 지연을 함께 검증한다. Windows bind mount보다 Linux 파일시스템의 bind mount가 효율적이라는 근거는 [Docker WSL 권장사항](https://docs.docker.com/desktop/features/wsl/best-practices/)에 있다. 이번 표본에서 디스크 자체의 포화가 확인된 것은 아니다.

### 적용 예시

별도 Compose override 예시다. 배포 도구가 실제 사용 중인 기본 Compose·GPU override·환경 파일에 이 파일을 추가해야 한다. 아래 조각만으로 운영 스택을 재생성하지 않는다.

```yaml
services:
  preprocessing:
    cpus: 2.5
  analysis:
    cpus: 1.0
```

현재 전처리 4GiB 메모리 상한은 우선 유지한다. 약 2.79GiB라는 단일 시점 사용량만 보고 한도를 낮추면 모델 초기화나 사람 증가 시 피크를 감당하지 못할 수 있다.

분석 FPS는 실제 로드되는 `C:\ProgramData\AI_CCTV\config\config.yaml`의 `inference.analysis_fps`를 대상으로 한다. 재시작 시 읽는 설정이며, 적용 전에 파일을 백업한다. 현재 Compose에는 `ANALYSIS_FPS` 환경변수 전달 항목이 없으므로 호스트 `.env`에 이 값만 추가해서는 적용되지 않는다. 이 설정 변경은 서비스 재시작과 함께 별도 작업으로 진행한다.

WSL 설정의 최초 시험값은 다음과 같다. 기존 파일이 생겼다면 덮어쓰지 말고 병합한다.

```ini
[wsl2]
memory=10GB
processors=6
swap=3GB
```

자동 캐시 회수는 먼저 실제 동작을 관찰한다. 필요 시 `[experimental]`의 `autoMemoryReclaim=dropCache`를 명시할 수 있지만, 기본값과 같으므로 이를 새로 적는 것만으로 개선을 기대하지 않는다. WSL 설정 반영에는 VM 재시작이 필요하다. 녹화·복구를 정상 종료한 유지보수 시간에 Docker Desktop 종료 → WSL 종료 → Docker Desktop 및 기존 배포 절차로 서비스 재시작 순서로 진행한다. `wsl --shutdown`은 모든 WSL 배포를 종료한다. [Microsoft 설정 반영 안내](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)

10GB에서 부하 시험을 통과하고 추가 메모리 확보가 필요하면 8GB를 다음 후보로 시험한다. RAM 축소로 swap·OOM이 증가하면 10GB 또는 이전 값으로 복원한다. 캐시를 주기적으로 강제 삭제하는 방식은 권장하지 않는다.

## 검증 및 되돌리기

변경을 한 번에 모두 적용하지 않고 항목별로 비교한다. 첫 단계는 5분, 최종 구성은 30분 동안 같은 카메라 수·해상도·관리 화면 배치로 측정한다. 빈 장면과 사람 등장·이동·이탈, 속성 분석 작업과 복구 동작을 포함한다.

1. 변경 전 실제 Compose 파일 목록·환경 파일·컨테이너 이미지 ID·설정 파일을 기록하고, 수정할 파일만 백업한다. DB·영상 파일은 그대로 보존한다.
2. 전체 CPU 평균 80% 이하, 지속적인 95% 이상 구간 해소, Windows 가용 RAM 5GiB 이상을 최초 목표로 삼는다. 이 값은 개선 검증 목표이며 현재 달성한 수치가 아니다.
3. 프레임 나이·좌표 stale 비율·모델 timeout·실시간 PUT timeout 증가량, 실제 등장·이동·이탈 표시를 비교한다. health가 ready인 것만으로 성공 판정하지 않는다. 이번에도 ready 상태에서 약 2초 PUT timeout 로그가 있었다.
4. 녹화 segment 연속성, 복구 completed 증가, pending 대기시간, 분석·인물 연결 성공을 확인한다. CPU 감소와 함께 기능 처리량도 유지되어야 한다.
5. Windows 페이징과 WSL swap 추이, OOMKilled·재시작 횟수를 함께 확인한다. 단일 순간의 낮은 메모리만으로 성공 판정하지 않는다.
6. 서비스 지연·누락·복구 정체가 악화되면 마지막 변경 파일을 복원하고 동일한 이미지·환경·Compose 조합으로 해당 서비스만 재생성한다. WSL 한도복원은 유지보수 재시작이 필요하다.

추가로 필요한 증거는 데이터 API의 함수별 CPU 프로파일, 실행 중인 디코더별 사용량, 사람 수 증가에 따른 메모리 피크, 장시간 증가 추이다. 코드 개선 후보는 현재 작업 디렉터리의 소스를 기준으로 하며, 운영 이미지와 소스의 완전한 일치까지 검증하지는 않았다. 이번 진단으로 CPU 포화와 큰 WSL 캐시는 확인했지만, 특정 함수 하나의 독점 원인·메모리 누수·열 스로틀링까지 확정하지는 않았다.
