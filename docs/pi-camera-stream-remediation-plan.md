# Pi Camera 영상 송출 복구 실행 계획서

작성일: 2026-11-15 (Asia/Seoul)  
상태: 부분 복구 — Pi 송출·녹화 검증 완료, 데스크톱 카메라 복구 대기  
근거: 같은 날 09:03~09:05 KST에 수행한 SSH·서버 재검증

## 1. 목표 및 작업 권한

DEB로 설치한 Pi Edge를 유지하면서 `cam-001`의 영상을 직결 Ethernet으로 데스크톱 서버에 전달하고, 관리 화면 재생 및 양쪽 녹화를 복구한다. 함께 중단된 기존 데스크톱 카메라 `local-camera`도 복구한다.

사용자는 **이 대화 세션에 한해 Pi SSH 접속을 허용**했다. 접속 대상은 `phoenix@192.168.50.2`이며, 이미 확인된 호스트 키를 검증해 사용한다. SSH 허용을 이후 세션으로 일반화하지 않는다. 기존에 제공된 인증 정보는 접속에만 사용하고 문서·저장소·로그에 기록하지 않는다.

계획 작성 뒤 사용자가 작업 실행을 요청했다. 아래는 적용 절차이며 실제 결과는 8절에 기록한다.

## 2. 확인된 사실과 원인

| 구분 | 마지막 검증 결과 | 의미 |
|---|---|---|
| Pi 전원·접속 | 전원 복구 후 SSH 접속 성공 | 앞선 접속 불가는 전원 꺼짐으로 설명됨 |
| Pi 직결 경로 | `192.168.50.1 dev eth0 src 192.168.50.2` | 직결 인터페이스 선택 정상 |
| Pi → 서버 RTSP TCP | `192.168.50.1:8554` 연결 성공 | 현재 관측에서 경로·수신 포트 차단은 주원인이 아님 |
| 서버 RTSP 설정 | env·YAML·포트 매핑과 external 공개 호스트 모두 `192.168.50.1` | 앞선 서버 설정 변경은 적용됨 |
| Pi 송출 설정 | `central_host="192.168.1.10"` | Pi 설정 변경이 아직 수행되지 않음 |
| Pi 송출 로그 | 이전 주소로 시도하며 약 20초마다 resource 오류 반복 | 잘못된 목적지로 송출을 계속 시도 |
| 서버 `cam-001` | `ready=false`, 트랙 없음, 수신 0바이트 | 실제 영상이 서버에 도착하지 않음 |
| Pi 캡처·녹화 | 약 10초 간격으로 2.6 MB 정도의 TS 조각 생성 | 카메라와 로컬 녹화는 작동 |
| Pi 관리·복구 | 8002·8003 health 응답 정상, 관련 서비스 active | 관리 통신의 기본 연결은 정상 |
| 서버 컨테이너 | 실행 중인 6개 서비스 healthy | 프로세스 상태 정상. 영상 수신·재생 성공과는 별도 |
| 데스크톱 카메라 | enabled이나 Publisher/FFmpeg 없음, 서버 수신 0바이트 | 송출 프로세스 재시작 필요 |
| 데스크톱 로그 | DirectShow 버퍼 포화·프레임 드롭 기록 | 종료 원인은 미확정. 재시작 결과로 추가 판단 |

**주원인은 Pi에 남은 이전 송출 주소다.** `192.168.1.10`은 데스크톱의 VirtualBox 어댑터 주소이며, 직결 수신 주소 `192.168.50.1`과 다르다. 서버 변경만 적용된 상태에서 Pi가 재부팅돼도 저장된 이전 주소는 유지된다.

데스크톱 Publisher 중단 원인은 별도로 확인한다. 서버 재생성·주소 변경에 따른 연결 종료 가능성이 있으나, 현재 로그만으로 확정하지 않는다. Pi HLS 원본의 HTTP 404도 게시 스트림 부재와 일치하므로, 이를 독립적인 HLS 결함으로 단정하지 않는다.

## 3. 수정 범위와 영향

| 대상 | 필요한 작업 | 영향 |
|---|---|---|
| Pi `/etc/ai-cctv-edge/config.toml` | `[rtsp].central_host`를 `192.168.50.1`로 변경 | Edge 재시작 중 캡처·녹화에 짧은 공백 |
| Pi systemd | Edge·control·recovery 서비스 재시작 | 관리·복구 API 일시 중단 |
| 데스크톱 Publisher | 현재 설정을 다시 읽고 `192.168.50.1:8554/local-camera`로 재시작 | 데스크톱 영상 연결 재개 |
| 서버 | 실제 수신·재생·녹화 확인 | 현재 주소가 유지돼 있으면 재생성 불필요 |

카메라 ID, 게시 자격증명, Edge 토큰, 녹화 데이터와 DB를 유지한다. 기존 웹/API 주소 `PUBLIC_BASE_URL=http://192.168.1.10`은 이번 RTSP 복구 범위에서 변경하지 않는다. Wi-Fi 클라이언트에 별도 공개 주소가 필요하면 유선 복구 후 따로 판단한다.

현재 근거상 DEB 재설치·재빌드, 재페어링, 방화벽 추가 개방은 필요하지 않다. 적용 직전 재검사에서 새로운 실패가 관측되면 5절의 분기 기준을 따른다.

## 4. 적용 절차와 단계별 검증

### 1단계: 적용 직전 상태 확인

1. SSH 호스트 키를 검증해 Pi에 접속한다. 기존 확인에 사용한 명령은 `ssh -o StrictHostKeyChecking=yes -o HostKeyAlias=bull-sa-jo.local phoenix@192.168.50.2`다. 호스트 키가 달라지면 검증을 해제하지 않고 장치 동일성을 확인한다.
2. Pi의 주소·경로, 설정의 비밀이 아닌 항목, 세 서비스의 상태와 신규 로그를 읽는다.
3. Pi에서 서버 RTSP TCP 연결을 재검사한다.
4. 서버의 현재 포트 매핑·공개 호스트와 MediaMTX의 두 카메라 수신 상태를 기록한다. 서버의 기존 운영 설정 백업은 `C:\ProgramData\AI_CCTV\secrets\camera-stream-20261115-084200`에 있다.

Pi 점검 예시:

```bash
ip -br -4 addr
ip route get 192.168.50.1
sudo grep -E '^(mode|central_host|central_port|camera_id) *=' /etc/ai-cctv-edge/config.toml
systemctl is-active ai-cctv-edge ai-cctv-edge-control ai-cctv-edge-recovery
python3 -c 'import socket; s=socket.create_connection(("192.168.50.1",8554),4); print("RTSP TCP connected"); s.close()'
```

통과 기준: SSH 성공, 직결 경로 `eth0`, RTSP TCP 연결 성공. 설정이 마지막 검증 때와 다르면 차이를 확인한 뒤 변경한다.

### 2단계: Pi 송출 대상 수정

Pi 내부에 소유권·권한을 보존한 백업을 만들고 `[rtsp]`의 호스트만 변경한다. 아래 치환은 마지막으로 확인한 기존 값에 한정한다. 변경 뒤 TOML 파싱과 값 검증이 성공해야 서비스를 재시작한다.

```bash
backup_path="/etc/ai-cctv-edge/config.toml.bak-$(date +%Y%m%d-%H%M%S)"
sudo cp -a /etc/ai-cctv-edge/config.toml "$backup_path"
sudo sed -i '/^\[rtsp\]/,/^\[/s/^central_host = "192\.168\.1\.10"$/central_host = "192.168.50.1"/' /etc/ai-cctv-edge/config.toml
sudo python3 -c 'import tomllib; c=tomllib.load(open("/etc/ai-cctv-edge/config.toml","rb")); assert c["rtsp"]["central_host"] == "192.168.50.1"; print("central_host verified")'
```

검증 성공 후:

```bash
sudo systemctl restart ai-cctv-edge ai-cctv-edge-control ai-cctv-edge-recovery
systemctl is-active ai-cctv-edge ai-cctv-edge-control ai-cctv-edge-recovery
sudo journalctl -u ai-cctv-edge -n 40 --no-pager
```

통과 기준: 신규 게시 로그가 `rtsp://192.168.50.1:8554/cam-001`을 가리키고 세 서비스가 active다. 단순한 게시 시작 로그만으로 완료 판정하지 않는다. 백업 경로를 작업 결과에 기록한다.

### 3단계: 서버의 Pi 영상 수신 확인

MediaMTX API를 컨테이너 내부에서 조회한다. API 포트를 새로 외부에 공개하지 않는다.

```powershell
docker exec ai-cctv-mediamtx-1 sh -c 'wget -qO- http://127.0.0.1:9997/v3/paths/list'
```

10초 간격으로 두 번 확인한다. `cam-001.ready=true`, `tracks`에 H264, 증가하는 `bytesReceived`가 통과 기준이다. 실패하면 Pi와 MediaMTX의 같은 시각 로그를 대조해 5절에 따라 조사한다.

### 4단계: 데스크톱 카메라 송출 복구

1. 관리 앱이 현재 RTSP 설정을 다시 읽도록 하고, 기존 `720p HD Camera`의 송출을 시작한다.
2. 기존 카메라 등록과 자격증명을 유지해 새 주소로 게시한다. 화면에 이전 값이 남았다는 이유만으로 서버 전체 설정을 재적용하지 않는다.
3. Publisher/FFmpeg 실행과 MediaMTX의 `local-camera` 수신을 확인한다.
4. 시작에 실패하면 종료 코드와 자격증명을 가린 오류를 남긴다. 장치 점유·입력 모드·인코더 중 실제 오류가 지목하는 항목부터 조사한다.

통과 기준: `local-camera.ready=true`, 수신 바이트 증가, 관리 화면 재생. DirectShow 버퍼 포화만을 근거로 해상도나 인코더를 먼저 바꾸지 않는다.

### 5단계: 재생·녹화·안정성 검증

| 검사 | 완료 기준 |
|---|---|
| Pi 게시 안정성 | 10분 동안 게시 유지, 반복되는 resource 오류·Publisher 종료 없음 |
| 실시간 영상 | 관리 화면에서 Pi 영상 3분 이상 연속 재생, 시간에 따라 프레임 변화 확인 |
| HLS | 실제 사용 중인 인증 경로에서 플레이리스트와 영상 세그먼트 정상 수신 |
| 서버 녹화 | 60초 조각 설정을 고려해 2분 이상 관찰, 완료 파일 크기 > 0, 대응 DB 등록 확인 |
| Pi 로컬 녹화 | 재시작 후에도 크기 > 0인 완료 TS 조각이 계속 생성 |
| Edge 관리·복구 | 인증된 상태 조회와 복구 API의 읽기 요청 성공. 실제 복원 작업은 불필요 |
| 데스크톱 카메라 | Publisher 실행 유지, 서버 수신 바이트 증가와 화면 재생 |
| 재시작 내구성 | 위 검사 통과 후 Edge 1회 재시작, 재수정 없이 게시·로컬/서버 녹화 복구 |

컨테이너 healthy, SSH 성공, Edge online 표시만으로 완료하지 않는다. 화면을 직접 확인할 수 없다면 재생 검증을 미완료로 기록한다. 녹화가 비활성화돼 있으면 설정 상태를 먼저 확인하고 필요한 카메라의 기존 녹화 제어 흐름으로 검증한다.

## 5. 실패 지점별 후속 조사

| 최초 실패 | 다음 조사 | 변경 판단 |
|---|---|---|
| SSH·링크 | 전원, 케이블, 양쪽 IP, 인접 장치 상태 | 서버 재생성을 원인으로 단정하지 않음 |
| 새 주소 TCP | Pi 경로, 호스트 바인딩, Windows 방화벽 | 실제 차단 확인 시에만 `192.168.50.2 → 192.168.50.1:8554` 허용 규칙 검토 |
| TCP 성공·RTSP 게시 실패 | Pi GStreamer 로그, MediaMTX 인증·경로·중복 게시 로그 | 인증 거부 확인 후 자격증명 불일치 조사. 무조건 회전하지 않음 |
| RTSP 수신 성공·재생 실패 | 반환 URL, 클라이언트의 캐시된 주소, 인증, nginx/HLS 응답 | 수신 문제와 재생 문제를 구분해 수정 |
| 재생 성공·서버 녹화 실패 | 녹화 enabled, 경로별 record 설정, 저장 공간·권한, 녹화 후처리와 DB 로그 | 실패한 녹화 계층만 수정 |
| 데스크톱 Publisher 실패 | 재시작 종료 코드, 구주소 사용, 장치 중복 점유, 입력 모드·인코더 오류 | 관측한 오류에 필요한 최소 변경 |

새 코드 결함이 확인되면 재현 조건과 최소 수정 범위, 검증 방법을 먼저 정리한다. DEB 업데이트는 Edge 코드 수정이 필요한 경우에 판단하며 현재 계획의 선행 조건으로 삼지 않는다.

## 6. 롤백

Pi 변경으로 캡처·로컬 녹화가 회복되지 않거나 설정 검증이 실패하면 기록한 Pi 백업으로 복원하고 세 서비스를 재시작한다. 복원 후 TS 조각 생성과 관리 API 상태를 확인한다. 구주소 복원은 변경 전 상태로 돌아가는 조치이며 중앙 송출 장애를 해결하지는 않는다.

서버의 직결 RTSP 설정은 이미 TCP 접속이 검증됐다. Pi 게시 실패만으로 서버를 VirtualBox 주소로 되돌리지 않는다. 서버 설정에 실제 회귀가 확인돼 복원해야 한다면 기존 백업과 동일 Compose 프로젝트·env·오버레이를 사용한다. 전체 `down`, 볼륨 삭제, DB 초기화는 이 계획에 포함하지 않는다.

## 7. 작업 결과 기록 및 완료 판정

적용 후 이 문서에 다음을 기록한다: 적용 시각, Pi 백업 경로, 실제 변경 항목, 재시작 서비스, 두 스트림의 수신 바이트 비교, 관찰 시간, 재생·녹화·관리 API·재시작 검증 결과, 남은 오류와 롤백 여부. 비밀번호·토큰·인증 정보가 포함된 URL은 기록하지 않는다.

모든 완료 기준을 통과하면 상태를 `복구 완료`로 갱신한다. 실패 또는 미확인 항목이 하나라도 있으면 `부분 복구` 또는 `미완료`로 남기고 다음 조치를 명시한다.

## 8. 2026-11-15 실행 기록

- 09:16 KST: Pi의 기존 설정을 `/etc/ai-cctv-edge/config.toml.bak-20261115-091613`에 백업하고 `central_host`를 `192.168.50.1`로 변경했다. TOML 파싱과 변경값 확인 후 Edge·control·recovery 서비스를 재시작했다.
- `cam-001`은 MediaMTX에서 `ready=true`, H264로 전환되고 수신 바이트가 증가했다. 관리 화면에서 LIVE 영상과 녹화 중 표시를 확인했다. Pi 로컬 녹화도 계속 생성됐다.
- Pi의 인증된 상태 API와 복구 manifest 요청은 HTTP 200이었다. HLS 플레이리스트와 세그먼트의 수신도 확인했다. nginx 로그에는 일부 세그먼트 요청의 404와 이후 200이 관측돼 장시간 재생 검증을 계속한다.
- 중앙 녹화 MP4가 생성되는데 DB에 등록되지 않는 추가 원인을 발견했다. 설치된 MediaMTX 이미지의 `recording-complete-hook` 첫 줄이 CRLF로 끝나 Linux가 `/bin/sh\r`을 찾으면서 실행에 실패했다. `server/services/mediamtx/Dockerfile`에서 빌드 시 줄 끝을 정규화하도록 수정했고 전체 Dockerfile 빌드를 검증했다.
- 운영에는 기존 이미지에서 해당 스크립트만 정규화한 이미지를 적용했다. 원본 이미지는 `ai-cctv-mediamtx:pre-camera-hook-fix`로 보존했다. MediaMTX 및 nginx 재생성 후 Pi가 재연결됐다. 09:24 KST에 Edge를 다시 시작해 카메라별 녹화 설정과 자동 복구를 확인했다.
- hook 수정 전 완성된 Pi 중앙 녹화 조각은 실제 재생 길이를 측정해 기존 등록 hook으로 다시 등록했다. 수정 후 생성된 새로운 조각이 hook을 통해 자동으로 HTTP 201 및 DB `central/ready`로 등록되는 것도 확인했다.
- 데스크톱 카메라의 기존 관리 앱은 등록된 카메라를 다시 시작할 때 게시 자격증명을 자동 재발급하는 코드 경로를 사용한다. 이 계획의 기존 자격증명 유지 조건과 충돌하므로, 유지하면서 재시작할 수 있는 경로를 확인 중이다. Pi 카메라 자격증명은 변경하지 않았다.
- 09:24:17~09:34:49 KST: Pi는 같은 RTSP 세션에서 `ready=true`, H264를 유지했고 수신량이 약 1.46 MB에서 160 MB로 증가했다. 해당 게시 시작 이후 송출 오류·반복 종료는 관측되지 않았다. 관리 화면은 관찰 중 및 종료 시 `LIVE`, `녹화 중`이었으나 정지된 장면이라 프레임의 시각적 변화는 별도로 확인하지 못했다.
- 서버는 수정 후 매분 중앙 MP4를 완료하고 DB에 `central/ready`로 자동 등록했다. Pi 로컬 TS 조각도 계속 생성됐고 인증된 상태 및 복구 manifest는 HTTP 200이었다. MediaMTX 내부 HLS 플레이리스트와 세그먼트 다운로드에 성공했고 nginx 경유 HLS 요청에도 200이 관측됐다. 재연결 직후 일부 HLS 세그먼트 요청에서 404가 있었으므로 인증 경로의 장시간 연속 재생은 별도 검증이 남는다.
- 기존 `local-camera` 인증 정보는 서버 DB에 해시로만 저장돼 있으며 현재 평문 저장본과 실행 중 Publisher는 확인되지 않았다. 해당 카메라를 다시 시작하는 앱 경로는 게시 자격증명을 재발급한다. 더불어 현재 열려 있는 관리 앱은 이전 RTSP 호스트 `192.168.1.10`을 메모리에 가지고 있어 새 설정을 읽어야 한다. 기존 자격증명 유지 조건을 변경할지 사용자에게 문의했고 답변 전에는 재발급하지 않는다.
