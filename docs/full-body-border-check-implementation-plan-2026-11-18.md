# 대표 이미지 경계 여백 검사와 비전신 분석 생략 구현 계획

작성일: 2026-11-18 KST  
상태: 코드 변경 반영. 단위·통합 테스트와 운영 배포는 환경 의존성 문제로 미완료다.

요구사항 갱신: 경계 여백 검사 미통과 시 `pid:…/gpid:… is not full body` 메시지를 표시하고 analysis 속성 분석은 실행하지 않는다. GPID 확보를 위한 identity 재식별은 유지한다. 아래 본문은 이 요구를 반영한 최신 계획이다.

## 1. 목표와 구현 전제

기존 YOLO 사람 검출 박스와 원본 영상의 경계 사이 거리를 이용해, 화면 끝에서 신체가 잘렸을 가능성이 낮은 이미지를 대표 이미지로 우선 선택한다. 최종 선택 이미지가 여백 조건을 충족하지 못하면 analysis 속성 분석을 생략하고 해당 인물의 이벤트 메시지만 표시한다.

이 기능의 입력은 기존 탐지 결과와 프레임 크기다. 추가 모델 추론은 필요하지 않다. 결과는 전신 노출의 확정 판정이 아니라 **경계 여백 확보 여부**로 정의한다.

다음 사항을 이번 구현의 전제로 확정한다.

1. 좌우 여백은 원본 너비의 각각 2%, 상하 여백은 원본 높이의 각각 3%로 시작한다.
2. 기존 최소 크기·단색 검사에서 유효한 후보를 먼저 고른다.
3. 유효한 후보 중 경계 여백을 확보한 이미지를 우선한다.
4. 여백 조건이 같은 후보끼리는 기존 선명도·면적 점수로 비교한다.
5. 여백을 확보한 후보가 없어도 기존 최선의 후보를 확정한다.
6. 기존 관측 창과 확정 시점을 유지한다. 여백 확보를 기다리기 위해 관측 창을 연장하지 않는다.
7. 경계 판정 결과를 원본 등장 이벤트의 `metadata.observation_selection`에 기록한다.
8. 첫 구현은 두 비율을 코드 상수로 둔다. 환경변수·관리자 GUI·카메라별 설정은 추가하지 않는다.
9. 경계 검사 미통과 시 Data에서 analysis 작업을 생성하지 않는다. 분석 컨테이너가 이미지를 받은 뒤 결과만 숨기는 방식은 사용하지 않는다.
10. identity 작업은 유지한다. GPID가 아직 없으면 `null`로 표시하고 나중에 같은 이벤트의 ID를 갱신한다.
11. 표시 문구는 `pid:{pid}/gpid:{gpid} is not full body`다. 별도 중복 이벤트를 만들지 않고 원본 등장 이벤트의 설명을 이 문구로 표시한다.

2%·3%는 초기 엔지니어링 값이며, 검증된 전신 판별 임계값이 아니다. 카메라별 영상으로 효과를 확인한 뒤 조정한다.

### 성공 기준

- 유효한 중앙 후보와 유효한 경계 후보가 함께 있으면 중앙 후보를 선택한다.
- 유효한 경계 후보와 무효한 중앙 후보가 함께 있으면 유효한 경계 후보를 선택한다.
- 여백을 확보한 후보가 없어도 등장 이벤트와 identity 작업은 유지하고, analysis 작업은 생성하지 않는다.
- 선택한 이미지, bbox, 선택 시각, 경계 판정 메타데이터가 모두 같은 후보를 가리킨다.
- 추가 모델 추론이나 새로운 프레임 복사 경로 없이 기존 관측 창에서 동작한다.
- 미통과 이벤트에 지정한 메시지를 표시하고, PAR 호출·분석 속성·`analysis_completed` 이벤트가 생성되지 않는다.
- 내부 판정은 `border_clear`로 저장한다. 사용자 요청 문구의 `not full body`는 이 휴리스틱의 미통과를 뜻한다.

## 2. 현재 구현과 변경 위치

현재 소스에서 확인한 경로는 다음과 같다.

| 단계 | 위치 | 현재 역할 |
|---|---|---|
| 탐지 결과 생성 | `server/services/preprocessing/processors/detection/yolo.py` | 사람 박스·추적 ID·신뢰도 생성 |
| 좌표 정리 | `server/services/preprocessing/app/objects.py:clip_detections()` | 프레임 밖 좌표를 잘라 유효한 박스로 변환 |
| 대표 후보 점수 계산 | `server/services/preprocessing/app/observation_buffer.py:quality()` | 최소 크기·단색 여부·선명도·면적 계산 |
| 후보 비교·보관·확정 | 같은 파일의 `ObservationBuffer` | 사람별 후보 하나를 유지하고 관측 창 만료 등에 확정 |
| 이미지 저장·등장 이벤트 생성 | `server/services/preprocessing/app/pipeline.py:_publish_observation()` | 선택한 프레임의 크롭 저장 및 선택 메타데이터 기록 |
| JPEG 저장 | `server/services/preprocessing/app/objects.py:save_observation()` | 선택 bbox를 그대로 잘라 모델 입력용 JPEG 생성 |
| 작업 생성 | `server/services/data/app/database/repositories/objects.py:_enqueue_object_jobs()` | 같은 관측으로 identity·analysis 작업 생성 |
| 모델 입력 검증 | `lib/ai_cctv_core/processing/images.py` | JPEG와 bbox 크기 일치 등을 검사 |
| API 초기 상태 | `server/services/data/app/api/events.py:_event_values()` | 현재 관측이 있으면 identity·analysis를 모두 pending으로 초기화 |
| 관리자 이벤트 표시 | `server/desktop/admin/legacy_gui.py`, `application.py` | 등장·분석 완료 메시지와 이벤트 상세 표시 |
| 지연 GPID 갱신 | `server/desktop/admin/video_worker.py` | 현재 분석 완료 이벤트 중 GPID 미확정 건을 재조회 |

현재 `quality()`의 점수는 다음 튜플이다.

```python
(
    int(valid),
    min(sharpness, 500) * min(area / 32768, 1),
    math.log1p(area),
)
```

`ObservationBuffer`는 튜플을 사전식으로 비교하며, 점수가 같은 경우 기존 후보를 유지한다. `pipeline.py`는 `candidate.score[0]`으로 `usable|insufficient`를 기록한다.

`Settings.from_env()`와 Compose의 관측 창 기본값은 1초다. 반면 `Settings` 데이터클래스의 직접 생성 기본값은 0초다. 테스트에서는 원하는 관측 창을 명시하고, 이번 변경에서 이 기존 차이를 수정하지 않는다.

중요한 영향 범위: 선택한 크롭은 인물 재식별에 사용하고, 경계 검사를 통과한 경우에만 속성 분석에도 사용한다. 대표 이미지 선택은 두 작업의 입력에 영향을 주지만, 경계 미통과 시 생략 대상은 analysis다.

## 3. 경계 판정 규칙

### 3.1 입력 좌표

- `bbox = (x1, y1, x2, y2)`
- `W = frame.shape[1]`
- `H = frame.shape[0]`
- 좌표는 `clip_detections()`를 통과한 원본 프레임의 정수 좌표다.
- 기존 계약상 `0 <= x1 < x2 <= W`, `0 <= y1 < y2 <= H`가 보장되는 호출 경로를 사용한다.

모델 내부 추론용 리사이즈·패딩 이미지나 저장된 사람 크롭의 크기를 기준으로 계산하면 안 된다.

### 3.2 네 방향 거리와 임계값

```text
left   = x1
top    = y1
right  = W - x2
bottom = H - y2

margin_x = W × 0.02
margin_y = H × 0.03

border_clear = (
    left   >= margin_x
    and right  >= margin_x
    and top    >= margin_y
    and bottom >= margin_y
)
```

네 방향 모두 충족해야 통과한다. 하나라도 부족하면 `border_clear=false`다.

### 3.3 경계값과 반올림

판정 전에 임계값을 정수로 반올림하거나 버리지 않는다. 정수 거리와 실수 임계값을 그대로 비교한다.

예를 들어 1920×1080에서는 좌우 임계값이 38.4px, 상하 임계값이 32.4px다. 정수 좌표에서는 각 방향 거리 39px·33px부터 통과한다.

문서나 화면에서 보여 주는 약 38px·32px는 설명용 근삿값이다. 계산 기준은 2%·3%다.

| 해상도 | 좌우 계산값 | 좌우 최소 정수 거리 | 상하 계산값 | 상하 최소 정수 거리 |
|---|---:|---:|---:|---:|
| 640×480 | 12.8px | 13px | 14.4px | 15px |
| 1280×720 | 25.6px | 26px | 21.6px | 22px |
| 1920×1080 | 38.4px | 39px | 32.4px | 33px |

오른쪽·아래쪽 거리는 `W - x2`, `H - y2`로 계산한다. 현재 크롭이 `frame[y1:y2, x1:x2]`를 사용하는 계약과 일치시키며, `W - 1 - x2` 방식은 사용하지 않는다.

### 3.4 검사 함수의 형태

preprocessing과 Data가 같은 판정을 사용하도록 `lib/ai_cctv_core/processing/observation_quality.py`에 다음을 둔다. 기존 공용 processing 패키지에 순수 좌표 계산 모듈 하나를 추가하는 범위다.

```python
BORDER_MARGIN_X_RATIO = 0.02
BORDER_MARGIN_Y_RATIO = 0.03

def evaluate_border_margin(bbox, frame_width, frame_height) -> dict:
    ...
```

반환값은 6절에 정의한 `border_check` 객체다. 점수 계산과 최종 메타데이터 생성이 이 함수 하나를 사용한다.

Data도 유효한 `ObjectObservation`의 bbox·원본 크기로 이 함수를 호출해 analysis 허용 여부를 결정한다. 전달된 `border_clear=true` 값만 믿고 작업을 생성하지 않는다. NumPy·OpenCV·torch를 공용 함수의 의존성으로 추가하지 않는다.

- 판정에는 OpenCV·모델·파일 접근이 필요하지 않다.
- 입력 프레임·bbox를 변경하지 않는다.
- `near_edges`는 `left`, `top`, `right`, `bottom` 순서 중 미충족 방향만 담는다.
- 연산량은 후보당 상수 시간이다.
- 호출 경로가 이미 보장하는 박스 유효성을 위한 중복 검증 체계는 만들지 않는다.

## 4. 대표 후보 선택 규칙

### 4.1 새 점수 튜플

기존 점수 앞부분에 경계 우선순위 한 항목을 삽입한다.

```python
(
    int(valid),
    int(valid and border_check["border_clear"]),
    min(sharpness, 500) * min(area / 32768, 1),
    math.log1p(area),
)
```

`valid`의 의미는 현재와 동일하다.

- 크롭의 가로·세로가 각각 16픽셀 이상이다.
- 모든 픽셀이 같은 색으로만 구성된 이미지가 아니다.

선명도와 면적의 계산식·상한·동점 처리도 유지한다.

### 4.2 우선순위의 구체적 의미

| 후보 A | 후보 B | 선택 |
|---|---|---|
| 유효·경계 통과 | 유효·경계 미통과 | A |
| 유효·경계 미통과 | 무효·경계 통과 | A |
| 유효·경계 통과·기존 품질 높음 | 유효·경계 통과·기존 품질 낮음 | A |
| 유효·경계 미통과·기존 품질 높음 | 유효·경계 미통과·기존 품질 낮음 | A |
| 무효·경계 통과 | 무효·경계 미통과 | 기존 선명도·면적 점수로 결정 |
| 모든 점수가 같음 | 나중에 들어온 동점 후보 | 먼저 보관한 후보 유지 |

무효 후보는 두 번째 항목을 항상 0으로 두므로, 무효 후보끼리 비교할 때 기존 순위를 유지한다.

이 방식에서는 유효한 중앙 후보가 다소 흐려도 유효한 경계 후보보다 우선할 수 있다. 이번 요구인 경계 회피 우선 정책의 결과다. 실영상 검증에서 흐린 이미지 선택이 문제가 되면 별도 선명도 하한의 필요성을 평가하되, 첫 구현에 임의의 하한을 함께 넣지 않는다.

### 4.3 후보 저장 방식

- `Candidate`에 추가 프레임이나 후보 목록을 넣지 않는다.
- `score`는 기존처럼 선택 시점에 한 번 계산해 보관한다.
- 후보 교체 때 `frame`, `detection`, `selected_at`, `score`가 함께 바뀌는 현재 구조를 유지한다.
- 경계 메타데이터는 최종 확정 후보의 프레임·bbox로 한 번 다시 계산한다.
- 같은 함수와 상수를 사용하므로 점수 판정과 메타데이터 판정이 일치해야 한다.
- 최종 재계산은 좌표 연산뿐이며 JPEG를 다시 읽거나 모델을 호출하지 않는다.

### 4.4 시나리오 예

관측 창이 1초인 경우:

```text
t=0.0  등장, 왼쪽 경계와 5px 떨어진 유효 후보 A → 임시 보관
t=0.3  왼쪽 여백이 충분한 유효 후보 B → B로 교체
t=0.6  B보다 선명하지만 경계에 붙은 후보 C → B 유지
t>=1.0 기존 만료 처리에서 B 확정 → 저장·이벤트·후속 작업
```

통과 후보가 끝내 없으면 경계 후보끼리 기존 품질 점수로 비교한 결과를 확정한다. 메타데이터에는 실제 선택 후보의 `border_clear=false`를 기록한다. 해당 관측으로 identity 작업만 생성하고, 화면에는 `pid:…/gpid:… is not full body`를 표시한다.

## 5. 관측 창과 수명주기

### 5.1 유지할 동작

| 상황 | 구현 방침 |
|---|---|
| 관측 창 만료 | 현재 보관 중인 최선 후보 확정 |
| 관측 창 0초 | 첫 후보 즉시 확정, 미통과이면 analysis 생략, 추가 대기 없음 |
| 창 종료 전 퇴장 | 기존 경로로 남은 최선 후보 확정 |
| 카메라 재접속·모델 재준비 | 기존 flush 경로에서 후보 확정 |
| 정상 종료 | 기존 drain/flush 경로에서 후보 확정 |
| 후보 메모리 상한 초과 | 기존처럼 오래된 후보부터 확정 |
| 입력 확정 후 더 좋은 프레임 관측 | 기존처럼 확정 이미지를 교체하지 않음 |

현재 `ObservationBuffer._update()`는 기존 후보의 만료를 먼저 처리한다. 정확히 마감 시각에 도착한 새 프레임은 이미 만료된 후보의 품질 비교에 끼워 넣지 않는다. 이번 변경에서도 그 순서를 유지한다.

후보의 `occurred_at`은 최초 등장 시각, `selected_at`은 최종 선택 이미지 시각이다. 후보 교체로 최초 등장 시각이나 창 시작 시각을 뒤로 밀지 않는다.

### 5.2 후보 부재와 검사 미통과의 구별

경계 미통과는 오류가 아니다. 오류 코드·모델 실패·서비스 준비 실패로 처리하지 않는다.

여백 확보 후보가 없다는 이유로 다음을 실행하지 않는다.

- 등장 이벤트 생략
- identity 작업 생략
- 대기 시간 추가 또는 무한 재선택
- 선택 이미지의 bbox 확대·잘린 신체 영역 합성

기존 이미지 저장 실패나 Data 전송 실패 처리에는 경계 검사와 관련된 새 분기를 추가하지 않는다.

analysis 작업 생략은 정책에 따른 정상 결과다. 작업 실패·미설정·모델 오류로 표시하지 않는다. 구체적인 처리와 상태는 6.4절에 정의한다.

## 6. 기록할 메타데이터

### 6.1 저장 위치와 예시

기존 `person_appeared` 이벤트의 `metadata.observation_selection`에 `border_check`를 추가한다.

아래는 원본 1000×1000, 선택 bbox `[10, 100, 200, 900]`의 예다.

```json
{
  "observation_selection": {
    "selected_at": "2026-11-18T03:00:00Z",
    "quality": "usable",
    "window_seconds": 1.0,
    "border_check": {
      "method": "frame_margin_v1",
      "border_clear": false,
      "margin_ratio": {
        "x": 0.02,
        "y": 0.03
      },
      "distances_px": {
        "left": 10,
        "top": 100,
        "right": 800,
        "bottom": 100
      },
      "near_edges": ["left"]
    }
  }
}
```

### 6.2 필드 의미

| 필드 | 의미 |
|---|---|
| `method` | 판정 방식 식별자. 첫 구현은 `frame_margin_v1` |
| `border_clear` | 네 방향 여백 충족 여부 |
| `margin_ratio.x` | 좌우 각각의 원본 너비 대비 임계 비율 |
| `margin_ratio.y` | 상하 각각의 원본 높이 대비 임계 비율 |
| `distances_px` | 선택 bbox에서 원본 영상 각 경계까지의 거리 |
| `near_edges` | 여백 미충족 방향. 모두 충족하면 빈 배열 |

기존 `quality`는 최소 크기·단색 여부에 대한 값으로 유지한다. 따라서 `quality="usable"`이면서 `border_clear=false`일 수 있다.

반대로 최소 크기를 충족하지 못한 중앙 크롭은 `quality="insufficient"`, `border_clear=true`일 수 있다. `border_clear`는 이미지의 전반적 품질이나 전신 노출을 뜻하지 않는다.

`full_body=true|false`, 전신 확률 또는 모델 신뢰도처럼 해석될 값은 추가하지 않는다. 화면 메시지는 사용자가 요청한 `is not full body`를 사용하되, 내부 원인은 `NOT_FULL_BODY`와 경계 검사 근거로 구분해 기록한다.

### 6.3 데이터 계약과 조회 위치

- `ObjectObservation`은 `extra="forbid"`이므로 여기에 새 경계 필드를 넣지 않는다.
- 기존 `EventCreate.metadata`는 확장 가능한 객체이며, 경계 결과는 그 안에 저장한다.
- DB 열이나 테이블을 추가하지 않는다.
- 작업 claim은 현재 이벤트 metadata에서 `object`만 추려 전달한다. 따라서 새 경계 결과가 analysis의 `job`에 자동으로 포함된다고 가정하지 않는다.
- 입력 선택과 Data 작업 생성 단계에서 분석 실행 여부를 확정한다. 분석기 자체의 입력 계약 확대는 필요하지 않다.
- `analysis_completed`는 별도 메타데이터로 생성된다. 경계 결과를 그 이벤트에 자동 복사하지 않는다.
- 선택 근거는 원본 등장 이벤트에서 조회한다. 분석 완료 이벤트에서 접근할 때는 기존 `appearance_event_id` 연결을 이용한다.
- 예전 저장 이벤트에 `border_check`가 없으면 미검사 상태다. `false`로 소급 해석하지 않는다. 새로 수신한 관측은 메타데이터 유무와 관계없이 Data에서 bbox·원본 크기로 판정한다.

### 6.4 analysis 작업 생성 차단

판정 책임은 Data의 작업 생성 경로에 둔다. preprocessing이나 GUI에서 요청을 생략하는 것만으로 구현을 끝내지 않는다.

| 관측 상태 | identity | analysis | 사용자 표시 |
|---|---|---|---|
| `border_clear=true` | 기존대로 생성 | 기존대로 생성 | 기존 등장·분석 완료 표시 |
| `border_clear=false` | 기존대로 생성 | 생성하지 않음 | `pid:…/gpid:… is not full body` |
| 새 관측인데 경계 메타데이터 없음 | 기존대로 생성 | 원본 bbox로 다시 판정 | 판정 결과에 따라 표시 |
| 관측 자체가 없음 | 기존대로 객체 작업 없음 | 생성하지 않음 | 기존 비관측 이벤트 표시 |

구현 순서:

1. `EventCreate`와 `ObjectObservation` 검증 및 경로 정규화는 기존대로 수행한다.
2. `_enqueue_object_jobs()`에서 관측의 bbox·프레임 크기로 공용 경계 함수를 실행한다.
3. 원본 이벤트에 Data가 계산한 경계 근거를 기록한다. 수신 메타데이터와 충돌하면 이 값을 최종 기준으로 삼는다.
4. identity 작업은 기존 생성·pending 기록 경로를 사용한다.
5. 통과이면 analysis 작업을 생성하고 pending을 기록한다.
6. 미통과이면 analysis 작업 행을 생성하지 않고 같은 이벤트 트랜잭션에서 아래 상태를 저장한다.

```json
{
  "analysis": {
    "status": "skipped",
    "updated_at": "2026-11-18T03:00:00Z",
    "result": {
      "reason_code": "NOT_FULL_BODY"
    }
  }
}
```

`skipped`는 이벤트 metadata의 상태다. 현재 `object_jobs.state`는 CHECK 제약으로 `pending/running/complete/failed/unconfigured`만 허용하므로 이 열에 `skipped` 행을 삽입하지 않는다. 새 작업 행을 만들지 않는 방식으로 구현해 이번 요구만으로 DB 상태 열이나 모델 완료 프로토콜을 확장하지 않는다.

`_event_values()`가 두 단계를 무조건 pending으로 초기화하는 부분도 수정한다. analysis 초기화는 실제 작업 생성 결과를 따르게 하고, 미통과인데 pending 상태만 남는 일을 막는다. Repository 직접 호출 테스트에서도 같은 정책이 적용되어야 한다.

analysis 작업이 없으므로 claim 응답에 해당 이벤트가 나오지 않고, PAR의 `process()` 호출·분석 결과 속성·`analysis_completed` 생성도 발생하지 않는다. identity 완료 시 자기 단계 metadata만 갱신하는 기존 동작이 `analysis.status=skipped`를 보존하는지 검증한다.

이 정책은 새로 등록되는 관측부터 적용한다. 이미 실행 중인 추론을 취소하거나 완료된 과거 분석을 지우는 작업은 포함하지 않는다. 배포 전 기존 analysis 대기열을 처리한 뒤 새 정책의 시작 시점을 기록한다. 이전 생산자의 outbox가 재전송하는 관측도 새 등록 경로에서 기하학적으로 재판정하므로 미통과 분석을 새로 예약하지 않는다.

### 6.5 메시지 표시와 GPID 갱신

표시 조건은 `event_type=person_appeared`이면서 `metadata.analysis.status=skipped`이고 `reason_code=NOT_FULL_BODY`인 경우다. 단순히 경계 필드가 없거나 GPID가 없다는 이유로 이 문구를 표시하지 않는다.

```text
PID=12, GPID=307:  pid:12/gpid:307 is not full body
PID=12, GPID 미확정: pid:12/gpid:null is not full body
PID 미확정:         pid:-/gpid:null is not full body
```

- 기존 등장 이벤트 한 건의 설명을 바꾼다. 같은 관측에 `not_full_body` 이벤트를 별도로 만들어 중복 카드·등장 카운트를 발생시키지 않는다.
- 등장 인원 집계와 실시간 박스는 기존대로 동작한다.
- GPID를 얻기 위해 identity 작업은 수행한다. identity까지 생략하면 GPID를 새로 확보할 수 없으므로 생략 범위에 넣지 않는다.
- GPID를 기다리며 메시지를 숨기지 않는다. 우선 `null`로 표시한다.
- identity 완료 시 기존 DB 갱신으로 같은 이벤트의 GPID가 채워진다. 표시 문자열에 GPID를 미리 고정 저장하지 않고 최신 이벤트의 필드로 구성한다.
- `video_worker.py`의 현재 GPID 재조회는 `analysis_completed`만 대상으로 하므로, 비전신 생략 등장 이벤트도 포함하도록 제한적으로 확장한다.
- 기존 조회 간격·최근 이벤트 보관 수를 유지한다. 같은 이벤트 ID의 카드만 갱신하고 카드 추가·등장 수 증가를 발생시키지 않는다.
- identity가 최종 실패해 GPID를 얻지 못하면 `null`을 유지한다. 상태를 확인할 수 있는 경로에서는 identity가 진행 중인 동안에만 주기 갱신하고, 실패·미설정 등 종료 상태에서는 반복 조회를 멈춘다.
- 재조회 병합은 PID/GPID뿐 아니라 최신 identity 상태도 반영한다. 현재 `_refresh_retained_event_ids()`의 ID 중심 갱신만으로는 identity 종료 상태를 알 수 없으므로 필요한 metadata 갱신과 변경 감지도 함께 추가한다.
- `application.py`의 이벤트 렌더 서명에 생략 이유를 반영한다. ID가 같아도 메시지에 영향을 주는 상태가 바뀌면 다시 렌더링한다.
- 상세 화면에는 분석 미실행 사유를 표시하고 성별·나이 등 분석 결과나 완료 문구를 표시하지 않는다.
- 모바일 목록·상세도 같은 이벤트 metadata로 같은 문구를 표시한다. GPID가 갱신된 서버 데이터를 조회하면 문구도 갱신되며, 이 요구만으로 모바일에 새 상시 폴링 구조를 추가하지 않는다.
- 일반 등장·퇴장·정상 분석 완료 메시지는 기존 표시를 유지한다.

서버 응답을 재조회하지 않은 클라이언트에서 GPID가 자동으로 바뀐다고 가정하지 않는다. 기존 API 필드 전달과 실제 클라이언트 갱신 경로를 함께 테스트한다.

## 8. 테스트 설계

이 변경은 후보 비교 순서를 바꾸므로 선택 결과와 후속 입력의 회귀 테스트가 필요하다. 실제 YOLO 가중치·카메라·GPU 없이 검증 가능한 부분을 먼저 검증한다.

### 8.1 경계 계산 테스트

| 번호 | 입력 상황 | 기대 결과 |
|---|---|---|
| B01 | 네 방향 모두 충분한 여백 | `border_clear=true`, `near_edges=[]` |
| B02 | 왼쪽만 부족 | false, `["left"]` |
| B03 | 위쪽만 부족 | false, `["top"]` |
| B04 | 오른쪽만 부족 | false, `["right"]` |
| B05 | 아래쪽만 부족 | false, `["bottom"]` |
| B06 | 여러 방향 부족 | false, 고정 순서의 방향 목록 |
| B07 | 1000×1000에서 좌우 20px·상하 30px 정확히 확보 | 통과 |
| B08 | B07 각 방향을 독립적으로 1px 줄임 | 해당 방향 미통과 |
| B09 | 1920×1080에서 좌우 38px 또는 상하 32px | 해당 방향 미통과 |
| B10 | 같은 해상도에서 좌우 39px·상하 33px | 통과 |
| B11 | 640×480·1280×720·세로 영상 | 원본 축에 맞춰 같은 비율 적용 |
| B12 | `x1=0`, `y1=0`, `x2=W`, `y2=H` 각각 | 접촉한 방향 미통과 |
| B13 | `clip_detections()`가 화면 밖 박스를 경계로 잘라냄 | 잘린 방향 거리 0, 미통과 |
| B14 | 큰 원본 영상 안의 작은 중앙 bbox | 크롭 크기가 아닌 원본 프레임 기준 거리 |

각 테스트에서 네 방향 거리도 함께 검증한다. 테스트 기대값은 직접 계산한 수치를 사용하고, 검사 함수를 다시 호출해 기대값을 만드는 테스트는 작성하지 않는다.

### 8.4 이벤트와 모델 입력 연결 테스트

1. 최종 선택 후보로 `_publish_observation()`을 실행한다.
2. 임시 디렉터리에 모델용 JPEG와 표시용 이미지가 저장되는지 확인한다.
3. JPEG의 가로·세로가 선택 bbox의 차이와 일치하는지 확인한다.
4. JPEG를 디코딩해 선택 후보의 내용을 확인한다. JPEG는 손실 압축이므로 원본과 바이트 단위 동일성을 요구하지 않는다.
5. 이벤트의 `object_observation.bbox`, 프레임 크기, `selected_at`이 선택 후보와 일치하는지 확인한다.
6. `border_check`의 거리·비율·방향 목록이 그 bbox와 일치하는지 확인한다.
7. `candidate.score[0]`에 따른 기존 `quality`가 유지되는지 확인한다.
8. 원본 프레임에 표시용 박스나 ID가 그려져 모델용 크롭이 오염되지 않았는지 확인한다.
9. 같은 테스트를 경계 미통과 대체 선택에도 적용해 등장 이벤트가 생략되지 않는지 확인한다. analysis 작업은 별도 Data 테스트에서 0건임을 검증한다.

### 8.5 Data 저장·호환성 테스트

- 새 `border_check`가 있는 등장 이벤트를 저장하고 조회해 값이 보존되는지 확인한다.
- 통과 관측은 identity·analysis 작업이 각각 생성되고 같은 선택 크롭을 참조하는지 확인한다.
- 미통과 관측은 identity만 생성되고 analysis 작업이 0건인지 SQL과 claim 결과로 확인한다.
- `analysis.status=skipped`, `reason_code=NOT_FULL_BODY`가 저장·조회·identity 완료 이후에도 유지되는지 확인한다.
- 새로 수신한 관측에 경계 메타데이터가 없어도 bbox를 재판정하는지 확인한다.
- 전달된 경계 판정이 true여도 실제 좌표가 미통과이면 analysis가 생성되지 않는지 확인한다.
- 과거 이벤트는 새 메타데이터가 없어도 조회할 수 있고 미통과로 임의 표시되지 않는지 확인한다.
- claim 응답 계약과 `ObjectObservation` 스키마가 바뀌지 않는지 확인한다.
- 분석 완료 이벤트가 원본 등장 이벤트를 `appearance_event_id`로 연결하는 기존 동작을 회귀 확인한다.

## 11. 실영상 검증과 비율 조정

### 11.1 비교 자료 준비

가능하면 카메라별로 서로 다른 사람 등장 구간 50~100개를 초기 검토 표본으로 준비한다. 이 수량은 운영 정확도를 입증하는 통계 기준이 아니라 문제 사례를 찾기 위한 시작점이다.

다음 사례를 포함한다.

- 좌우에서 화면으로 들어오는 사람
- 화면 위·아래 경계에 머리·발이 가까운 사람
- 카메라 가까이 있어 bbox가 큰 사람
- 먼 거리의 작은 사람
- 화면 중앙에서 책상·난간·다른 사람에게 가려진 사람
- 앉은 사람·숙인 사람·옆모습
- 전체 관측 창 동안 경계에 머무는 사람
- 관측 창 안에 경계에서 중앙으로 이동하는 사람
- 관측 창 이후에야 중앙으로 이동하는 사람

### 11.2 공정한 비교 방식

한 번 확보한 프레임·bbox·추적 ID·시각을 같은 순서로 두 정책에 입력한다. 기존 정책은 `(valid, quality, area)`로, 새 정책은 `(valid, border_priority, quality, area)`로 비교한다.

YOLO를 각각 다시 실행해서 서로 다른 추적 결과를 비교하지 않는다. 모델 검출 변화와 선택 정책 효과가 섞이기 때문이다. 운영 시스템에서 비교 이벤트를 두 번 생성하지 않고, 별도 임시 출력으로 선택 이미지와 결과표를 만든다.

### 11.3 기록할 항목

| 항목 | 목적 |
|---|---|
| 카메라·추적 세션·인물 ID·관측 구간 | 같은 사례 비교 |
| 기존/신규 선택 시각·bbox | 어떤 후보로 바뀌었는지 확인 |
| 방향별 거리·여백 통과 여부 | 정책 적용 근거 확인 |
| 두 선택 이미지 | 시각 비교 |
| 사람 검토: 화면 경계 잘림 여부 | 목표 문제 개선 여부 |
| 사람 검토: 가림·흐림·전신 확인 어려움 | 검사 한계와 부작용 구분 |
| 기존/신규 선택 결과의 선명도 | 경계 우선으로 인한 품질 손실 확인 |
| 후속 분석·재식별 결과 | 공유 크롭 변경의 영향 확인 |
| 미통과 건의 analysis 작업·추론·완료 이벤트 수 | 모두 0인지 확인 |
| 미통과 건의 메시지와 GPID 갱신 | PID/GPID 표시와 재식별 유지 확인 |

비교 결과는 `경계에서 잘린 이미지 선택 감소`, `통과 후보가 있었던 비율`, `통과 후보가 없어 대체 선택한 비율`, `중앙이지만 신체가 가려진 사례`를 구분해 집계한다.

신원 정답이 있는 검증 자료가 없으면 Re-ID 정확도 개선이나 악화를 수치로 단정하지 않는다. 속성 정답이 없을 때도 모델 점수 변화만으로 정확도 개선을 주장하지 않는다.

### 11.4 조정 기준

- 정상 전신 이미지가 경계 근처에 있다는 이유로 지나치게 밀리면 좌우 1%·상하 2%를 비교한다.
- 특정 방향의 잘림이 계속 선택되면 해당 축 비율을 늘려 재생한다.
- 좌우·상하 비율을 동시에 여러 차례 바꾸지 않고 변경 효과를 기록한다.
- 비율을 고르는 자료와 최종 확인 자료를 분리해 과도한 사례 맞춤을 피한다.
- 첫 구현은 전역 상수 두 개를 사용한다. 카메라마다 최적값이 크게 다르다는 근거가 확인되면 후속 설정 기능을 별도 계획한다.

좌표 계산 정책의 통과 여부와 실제 전신 노출은 다른 지표다. 카메라가 애초에 상반신만 촬영하거나 신체가 구조물에 가려진 경우, 비율 조정만으로 해결할 수 없다.

## 12. 성능과 운영 적용

### 12.1 예상 비용과 검증

- 추가 연산은 네 방향 거리 계산, 임계값 비교, 작은 메타데이터 객체 생성이다.
- 후보 평가용 추가 프레임 복사·JPEG 인코딩·추가 모델 호출은 없다.
- 최종 이벤트에 경계 결과 몇 개의 필드가 추가된다.
- 프레임 전체를 저장하는 기존 메모리 방식과 후보 상한은 유지한다.

성능 개선이나 고정된 처리시간을 미리 보장하지 않는다. 필요한 경우 동일 입력 재생에서 후보 선택 구간의 시간·프레임 복사 횟수·후보 버퍼 메모리를 비교한다. 특히 새 경계 후보가 더 자주 교체되어 생기는 기존 프레임 복사 비용의 변화는 별도로 관찰한다.

### 12.2 배포 절차

1. 변경 전 preprocessing·Data 이미지 식별자와 관리자·모바일 버전을 기록한다.
2. 관련 테스트를 통과한 소스로 두 서비스 이미지와 표시 클라이언트를 준비한다. 공용 모듈이 두 이미지에 포함되는지 확인한다.
3. 현재 운영이 CPU/GPU 중 어떤 Compose 조합을 사용하는지 확인하고 동일한 조합을 사용한다.
4. preprocessing의 새 관측 생성을 잠시 멈추고 기존 analysis 대기·진행 작업을 처리한다. Data가 이전 생산자의 재전송을 받아도 새 정책을 적용하도록 준비한다.
5. 새 Data의 작업 생성 차단을 먼저 적용하고, 이어서 새 preprocessing을 적용한다. 실제 배포 시 검증된 운영 관리 경로를 따른다.
6. 관리자·모바일의 메시지 표시 버전을 적용한다. 카메라 추적 세션·영상 연결의 재시작 영향과 새 정책 시작 시각을 기록한다.
7. readiness뿐 아니라 실제 카메라 좌표 신선도·이벤트 전송 상태·identity 상태를 확인한다.
8. 새 등장 이벤트에서 Data가 기록한 `border_check`와 analysis의 pending 또는 skipped 상태를 확인한다.
9. 미통과 사례는 지정 메시지와 identity 흐름만 발생하고 analysis 작업·추론·완료 이벤트가 없는지 확인한다.
10. Data의 기존 완료 작업 backfill 기능이 skipped 이벤트에서 분석 완료 이벤트를 만들지 않는지 확인한다.

생산자가 이전 버전이어도 새 Data가 좌표로 판정하므로 미통과 작업 생성이 우회되지 않는다. 이전 생산자의 outbox에서 뒤늦게 등록된 관측도 같은 생성 정책을 따른다.

이 변경만으로 과거 이벤트나 완료된 분석을 다시 처리하지 않는다. 소스 코드 확인만으로 실제 컨테이너가 새 정책을 실행한다고 판단하지 않고 이미지 버전과 새 이벤트를 함께 확인한다.

### 12.3 복원

- 문제가 생기면 기록한 preprocessing·Data 이미지와 관리자·모바일 버전으로 되돌린다. 새 Data의 차단 정책을 제거하면 이후 미통과 분석이 다시 실행될 수 있으므로 복원 후 적용 정책을 명시한다.
- DB 스키마 변경이 없으므로 DB 복원은 필요하지 않다.
- 이미 저장한 새 경계 메타데이터는 그대로 둔다.
- 이전 코드에서 경계 메타데이터 없는 새 이벤트가 다시 생기는 것은 허용한다.
- 코드 복원은 후보 점수·Data 작업 생성 조건·상태 초기화·표시 변경을 함께 검토한다. 실행 중 상수를 0으로 바꾸는 방식을 정식 비활성화 기능으로 취급하지 않는다.
- 이미 skipped로 저장되어 analysis 작업이 없는 이벤트를 복원 과정에서 자동 재분석하지 않는다.

## 13. 범위와 한계

이번 구현은 기존 YOLO 박스를 사용한 대표 이미지 선별, Data의 미통과 분석 차단, 지정 이벤트 메시지 표시다. 모델 추가·재학습·Pose 추정·가림 판별·bbox 확대·재분석·장시간 재선택·GUI 설정 편집 기능은 범위에 포함하지 않는다.

다음 한계는 문서와 검증 기록에 남긴다.

1. 화면 안에서 가려진 다리·머리는 경계 거리로 검출할 수 없다.
2. YOLO가 사람 일부만 박스로 잡았어도 박스가 중앙에 있으면 통과할 수 있다.
3. 큰 전신 인물이 경계에 가깝게 잡히면 미통과할 수 있다.
4. 원본 영상 자체의 검은 테두리·패딩을 제거하는 기능은 없다. 여기서 원본은 preprocessing이 실제 수신한 프레임이다.
5. 고정 관측 창 이후에만 좋은 프레임이 나타나면 이번 선택에는 반영되지 않는다.
6. 중앙 후보 우선이 속성 분석·재식별 정확도 개선을 자동으로 뜻하지 않는다.

## 14. 최종 인수 체크리스트

- [ ] 실제 좌우 2%·상하 3%를 원본 프레임 기준으로 계산한다.
- [ ] 실수 임계값을 임의로 정수 반올림하지 않는다.
- [ ] 네 방향 중 하나라도 부족하면 미통과한다.
- [ ] 유효성 → 경계 우선순위 → 기존 품질 순서로 비교한다.
- [ ] 무효 중앙 후보가 유효 경계 후보를 이기지 않는다.
- [ ] 동점·관측 창·등장 시각·선택 시각의 기존 의미를 유지한다.
- [ ] 미통과 후보만 있어도 최선 후보·등장 이벤트·identity 작업을 유지한다.
- [ ] 미통과 관측의 analysis 작업·PAR 호출·분석 속성·analysis_completed는 모두 없다.
- [ ] 미통과 이벤트는 skipped/NOT_FULL_BODY로 기록하고 오류나 pending으로 표시하지 않는다.
- [ ] `pid:…/gpid:… is not full body`를 표시한다.
- [ ] 지연 GPID 확정 시 같은 카드만 갱신하고 등장 카운트를 늘리지 않는다.
- [ ] 새 관측의 메타데이터가 없거나 잘못되어도 Data의 좌표 판정을 우회하지 않는다.
- [ ] 후보 추가 보관·추가 모델 호출·의도하지 않은 프레임 복사가 없다.
- [ ] 선택 이미지와 메타데이터의 후보가 일치한다.
- [ ] 원본 등장 이벤트에서 검사 근거를 조회할 수 있다.
- [ ] `ObjectObservation`과 작업 claim 계약을 유지한다.
- [ ] 메타데이터 없는 과거 이벤트와 호환된다.
- [ ] 관련 단위·통합·회귀 테스트가 통과한다.
- [ ] 실영상 검증 여부와 아직 확인하지 못한 효과를 구분해 기록한다.
- [ ] 운영 적용 시 실제 이미지 버전·새 이벤트·서비스 상태를 확인한다.
- [ ] preprocessing·Data·표시 클라이언트의 이전 버전과 복원 후 정책을 기록한다.
