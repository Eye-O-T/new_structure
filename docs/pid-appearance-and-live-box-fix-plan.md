# PID 출현 이벤트 및 실시간 바운딩 박스 수정 계획

- 작성일: 2026-11-09 KST
- 범위: GPID 미확정 상태의 출현 표시 지연과 실시간 바운딩 박스 미표시
- 상태: 원인 조사 및 수정 계획 작성. 이번 단계에서는 제품 코드·설정·컨테이너를 변경하지 않았다.

## 1. 기대 동작

추적 PID가 발급된 사람은 GPID와 analysis 완료를 기다리지 않고 `pid:n gpid:null 출현`으로 표시되어야 한다. 같은 시점의 신선한 좌표는 GPID가 없어도 영상 위에 박스로 표시되어야 한다. GPID가 나중에 확정되면 기존 이벤트를 갱신하고, analysis 결과는 기존 분석 완료 카드에 표시한다.

PID의 범위는 카메라·추적 세션이다. 서로 다른 카메라나 세션의 같은 PID를 합치지 않는다. 출현 이벤트는 사람을 처음 탐지하는 추론이 끝난 뒤 생성할 수 있으므로, 추론 시간과 이벤트 저장 이후의 표시 지연을 나눠 평가한다.

## 2. 확인 결과와 원인

### 2.1 GPID null에 대한 표시 차단 조건은 확인되지 않았다

- [TrackState](../server/services/preprocessing/app/event_state.py)는 처음 보는 PID에 즉시 `person_appeared` 전환을 만든다. GPID를 입력받지 않는다.
- [Data 이벤트 저장](../server/services/data/app/database/repositories/events.py)은 GPID 없이 출현 이벤트를 저장하고 후속 identity·analysis 작업을 예약할 수 있다.
- [이벤트 변환](../server/desktop/admin/video_worker.py)은 `person_appeared`를 `appear`로 전달하며, [카드 표시](../server/desktop/admin/legacy_gui.py)는 GPID가 null이어도 PID를 표시한다.
- [박스 표시 함수](../server/desktop/admin/overlay.py)는 GPID로 객체를 걸러내지 않는다. 신선한 1280×720 좌표와 `pid:7, gpid:null`을 입력했을 때 박스 1개와 정상 라벨을 반환하는 것을 직접 확인했다.
- 기존 overlay 검사 6개는 통과했다. Qt 카드 검사는 현재 셸의 Python에 PyQt5가 없어 실행하지 못했다. 실행 중 데스크톱의 실제 버전·환경과 전체 화면 동작은 구현 단계에서 확인해야 한다.

따라서 현재 근거로는 GPID null을 차단하는 조건을 제거하는 방식으로 해결할 수 없다. 영구적인 출현 카드 누락 자체도 이번 조사에서 재현하지 못했으며, 확인된 것은 출현 이벤트의 저장 지연이다.

### 2.2 출현 이벤트가 대표 이미지 선택을 기다린다

[pipeline.py](../server/services/preprocessing/app/pipeline.py)의 `_process_frame()`은 `person_appeared` 전환을 바로 전송하지 않는다. [ObservationBuffer](../server/services/preprocessing/app/observation_buffer.py)가 후보를 확정한 뒤 `_publish_observation()`이 출현 이벤트·crop을 함께 저장한다.

현재 컨테이너의 `OBSERVATION_WINDOW_SECONDS`는 **1초**다. 이 시간의 만료는 독립 타이머가 아니라 다음 추론 결과를 처리할 때 검사한다. 추론이 수 초 걸리면 설정된 1초보다 훨씬 늦게 이벤트가 생성된다. 이후 이미지 저장과 이벤트 전송도 추가된다. 정확한 구간별 지연 비중은 후속 측정이 필요하다.

운영 DB에서 확인한 최근 출현 이벤트의 지연은 다음과 같다. 시각 차이는 `created_at - occurred_at`이며 최초 관측부터 DB 저장까지를 뜻한다.

| 이벤트 ID | PID | 출현 저장 지연 | 후속 상태 |
| --- | --- | --- | --- |
| 15 | 1 | 15.017초 | identity·analysis 완료 |
| 18 | 1 | 8.825초 | identity·analysis 완료 |
| 21 | 1 | 2.808초 | identity·analysis 완료 |
| 24 | 1 | 13.526초 | identity·analysis 완료 |

예를 들어 ID 24는 05:02:25.806 UTC에 관측됐지만 05:02:39.332 UTC에 저장됐다. identity 완료는 05:02:41.207 UTC, analysis 완료는 05:02:41.829 UTC다. 출현 저장은 identity 완료보다 앞서므로 GPID 대기 때문에 생성이 지연되는 구조는 아니다.

현재 DB의 출현 이벤트 8건은 모두 GPID가 후속 반영된 상태다. 현재 값만으로 최초 전송 시 GPID가 null이었던 화면을 복원할 수는 없다.

### 2.3 추론이 좌표 유효기간보다 오래 걸린다

Preprocessing이 마지막으로 중지된 `local-camera` 워커에 보존한 최근 22개 표본은 다음과 같다.

| 항목 | p50 | p95 |
| --- | --- | --- |
| 전체 추론 | 3.545초 | 4.270초 |
| 모델 실행 | 3.478초 | 4.240초 |
| IPC | 0.029초 | 0.043초 |
| 좌표 Data PUT | 0.374초 | 0.820초 |
| DB 잠금 대기 | 0.053초 | 0.308초 |
| DB 트랜잭션 | 0.117초 | 0.169초 |

항목별 백분위는 서로 다른 표본일 수 있으므로 합산하지 않는다. 모델 실행이 가장 큰 지연이라는 점은 확인되지만, CPU 스레드 경합 등 모델 실행이 느려지는 세부 원인은 아직 확정하지 않았다. 별도 Python 조회의 PyTorch 기본값은 intra-op 4·inter-op 4, 이용 가능한 논리 CPU는 8개였으며, 이는 실제 모델 자식 프로세스의 설정 측정을 대신하지 않는다.

좌표에는 추론 전 촬영 시각이 `observed_at`으로 보존된다. [Data 좌표 조회](../server/services/data/app/database/repositories/objects.py)는 이 시각이 **3초**를 넘으면 `stale=true`, `objects=[]`를 반환한다. [CameraView](../server/desktop/admin/camera_view.py)는 stale 응답의 박스를 그리지 않는다. 따라서 최근 표본처럼 추론만 3초를 넘는 결과는 전송이 성공해도 조회 시점에 이미 만료된다.

모든 결과가 만료된 것은 아니다. 마지막 저장 좌표는 05:03:44.555 UTC 관측·05:03:45.145 UTC 수신으로 차이가 약 0.590초였고, 해당 마지막 추론은 약 0.542초였다. 이 한 건은 수신 당시 표시 가능한 나이였지만 과거 수 초짜리 표본의 문제를 해소하지 않는다. 이 좌표가 당시 데스크톱에서 실제로 그려졌는지는 확인하지 못했다.

이전 [바운딩 박스 지연 계획](bounding-box-latency-fix-plan.md)에서 관측 나이·stale 진단은 반영됐지만, 실제 장비에서의 추론 성능 개선과 실시간 표시 인수 검증은 완료되지 않았다. analysis 시작 오류 수정도 이 성능 문제를 해결하지 않는다.

### 2.4 스트림 중단과 조사 한계

최근 로그에는 RTSP 404·401, 디코딩 오류와 재접속이 있다. 의도한 카메라 중지와 실제 가동 중 단절을 구분해야 하며, 이 로그만으로 인증 설정 오류를 확정하지 않는다.

조사 시점 카메라는 `offline`, `stream_requested=0`, `recording_enabled=0`이고 preprocessing은 `idle`, 활성 워커 0개다. 따라서 현재 새 좌표가 없는 것은 정상적인 중지 상태다. 이번 조사는 최근 가동 표본과 저장 데이터·코드에 근거하며, 카메라를 켜거나 실시간 상태를 변경하지 않았다. Preprocessing의 쓰기 전용 토큰으로 좌표 GET을 시도한 요청은 403이어서 공개 API 재현의 근거로 사용하지 않았다.

## 3. 수정 순서

### 1단계: 첫 탐지 결과에서 출현 이벤트 저장

**가장 작은 변경은 기존 관측 창 0초 모드를 기본으로 사용하는 것이다.** 새 API나 DB 스키마를 만들지 않고, 첫 추론의 crop과 출현 이벤트를 함께 저장하는 기존 경로를 사용한다.

1. `ObservationBuffer`의 창 0초 동작이 첫 update에서 후보를 반환하는지 회귀 검사로 고정한다. 창 1초에서는 다음 update까지 대기하는 현재 동작도 확인한다.
2. `Settings.from_env()`, Compose, `.env.example`의 기본 `OBSERVATION_WINDOW_SECONDS`를 0으로 맞춘다. 이미 0인 dataclass 기본값과 불일치를 없앤다.
3. 실제 설치의 Compose env에 명시적인 1초 설정이 있는지 확인하고, 배포 때 실제 적용값이 0인지 검증한다. 비밀값 전체를 로그로 출력하지 않는다.
4. 최초 검출 crop을 사용하는 출현 이벤트가 GPID null 상태로 저장되고 identity·analysis 작업이 각각 한 번만 생성되는지 확인한다. 영상 저장·후속 작업·분석 완료 이벤트의 기존 계약을 유지한다.

**선택에 따른 영향:** 기본 동작에서는 1초 동안 더 선명한 대표 이미지를 고르는 이점이 줄어든다. 즉시 출현 표시를 우선하는 사용자 요구에 맞춘 선택이다. 기존의 명시적인 양수 관측 창 기능은 유지하되, 해당 설정은 추론 주기에 따라 이벤트를 지연시킨다는 점을 문서화한다.

**검증:** 두 번째 추론을 보내지 않아도 첫 탐지 결과 처리에서 출현 이벤트가 생성되어야 한다. 목표는 추론 완료부터 출현 DB 저장까지 p95 1초 이하이며, 같은 출현에 이벤트나 후속 작업이 중복되면 실패다.

### 2단계: 모델 실행 시간을 줄여 신선한 좌표 전달

1. 카메라 가동 전에 기존 저장 이미지 또는 고정 검증 영상을 이용해 동일 모델·입력·해상도 조건을 확보한다. 운영 감지와 별도 벤치마크를 동시에 돌려 경합을 만들지 않는다.
2. 실제 감지 자식 프로세스에서 CPU 스레드 수와 모델 실행 구간을 확인한다. 스레드 1·2·4개와 기존 실행값을 조건별 준비 이후 최소 100회 비교한다. 결과 없이 특정 스레드 수를 정답으로 고정하지 않는다.
3. 가장 작은 유효한 변경을 감지 자식의 초기화 경로에 적용한다. CPU 상대 가중치나 다른 모델의 동시 실행이 병목이라는 측정이 있을 때만 관련 설정을 조정한다.
4. 기본 입력으로 목표를 달성하지 못하면 해상도 조정을 비교한다. 원거리·작은 사람의 누락과 추적 ID 유지, 원본 좌표·crop 일치를 확인한 경우에만 채택한다.
5. 좌표 PUT 지연을 별도로 확인한다. DB 잠금이나 특정 쓰기 경로가 실제 병목인 경우에만 해당 쿼리·트랜잭션을 최소 수정한다.

`observed_at`을 추론 완료 시각으로 바꾸거나, 만료 좌표를 다시 그리거나, 유효기간만 늘리는 방법은 사용하지 않는다. 기존 최신 프레임·최신 좌표 한 건 유지 구조를 활용한다.

**검증 목표:** 정상 실행 추론 p95 1초 이하, 좌표 PUT p95 0.5초 이하, 사용자 API 관측 나이 p95 2초 이하. 가동 준비 이후 5분 동안 좌표 조회의 stale 비율은 1% 미만을 목표로 한다. 사람이 없는 정상 빈 관측도 신선한 좌표 갱신으로 계산한다. 검증 영상에서 새 탐지 누락·추적 단절·좌표 오차가 없어야 한다.

### 3단계: GPID null의 API·화면 회귀 검증

1. identity가 아직 끝나지 않은 입력으로 Data → External → `legacy_event()` → 타임라인을 검사한다. `pid:n gpid:null 출현` 카드와 출현 수가 analysis 완료 전에 나타나야 한다.
2. 신선한 좌표를 GPID null·확정 값 두 경우로 넣어 동일한 박스 좌표와 서로 다른 라벨만 나오는지 확인한다. stale·빈 관측·카메라 중지 때는 박스가 제거되어야 한다.
3. 나중에 GPID가 확정되면 동일 이벤트 ID를 갱신하고 카드 수·출현 수를 늘리지 않아야 한다. 다른 세션의 같은 PID는 별개로 유지한다.
4. 실제 실행 중 데스크톱의 파일 경로·버전·Bounding Box 표시 설정을 확인한다. 서버가 신선한 비어 있지 않은 좌표를 반환하는데도 표시가 빠지는 경우에만 수신 연결·뷰 렌더링을 추가 수정한다.

현재 코드에 없는 GPID 필터를 가정해 UI를 미리 고치지 않는다. Qt 검사는 데스크톱 의존성이 갖춰진 환경에서 실행하며, 의존성 누락을 테스트 성공으로 처리하지 않는다.

### 4단계: 배포와 실제 영상 인수

1. 변경 전 이미지·설정과 현재 기준선 수치를 기록한다. 우선 preprocessing과 해당 관측 창 설정만 반영하며, 추가 병목 수정이 있는 서비스만 별도로 배포한다.
2. analysis의 정상 모델과 기존 이벤트·결과를 보존한다. DB 초기화나 기존 출현 이벤트의 일괄 재생성은 하지 않는다.
3. 실제 카메라 입력이 가능한 상태에서 5분 이상 단일 화면·다중 화면을 확인한다. 좌표 API 응답, UI 수신 시각, 최초 박스·출현 카드 표시 시각을 대조한다.
4. `gpid:null` 단계의 출현·박스 → GPID 후속 반영 → analysis 카드의 순서를 확인한다. 별도 모의 입력 검증과 실제 영상 검증을 기록에서 구분한다.
5. 카메라 중지·재시작·일시 단절에서 이전 세션의 박스가 남지 않고 새 세션 출현이 정상 생성되는지 확인한다. RTSP 401·404가 실제 가동 중에도 반복되면 해당 중단 구간을 따로 진단한다.

카메라가 중지된 상태에서는 합성 입력·고정 영상 검사까지 완료하고, 실제 영상 인수는 미완료로 남긴다. Docker `healthy`만으로 화면 문제가 해결됐다고 판정하지 않는다.

| `server/services/data/app/database/repositories/objects.py` | 좌표 쓰기 병목이 확인될 경우에만 최소 수정 |
| `server/services/preprocessing/tests/` | 최초 결과 출현·지연 창·중복·좌표 시각 보존 검사 |
| `server/services/data/app/database/repositories/test_live_objects.py` 등 | GPID null·만료·후속 작업 및 이벤트 저장 검사 |
| `server/setup/install_helper/tests/test_overlay.py`, `test_multi_camera_view.py`, `test_live_video.py` | GPID null 카드·박스·후속 갱신 검증 |
| `server/desktop/admin/` | 실제 신선한 좌표 수신 후 렌더링 결함이 재현된 파일만 수정 |
| Preprocessing README, 운영 문서, 본 계획서 | 관측 창의 영향·측정치·실제 인수 결과 기록 |

공유 모델 인터페이스·DB 스키마 변경은 현재 확인된 원인을 해결하는 데 필요하지 않다. 설치 도구가 관측 창 값을 별도 생성하는 경우에는 해당 생성 지점도 함께 맞춘다.

## 5. 완료 기준과 되돌림

- 최초 추론 결과에서 GPID null 출현 이벤트와 후속 작업이 중복 없이 생성된다.
- GPID null이어도 신선한 좌표로 실제 화면에 박스가 보인다.
- 동일 조건의 전후 측정에서 추론·전달·첫 표시 목표를 충족하며 새로운 탐지 누락이 없다.
- GPID 후속 갱신과 현재 정상 동작하는 analysis 결과 표시가 유지된다.
- 실제 영상 인수까지 마친 항목과 미검증 항목을 구분해 보고한다.

새 탐지 누락·잘못된 박스·이벤트 중복·기존 분석 표시 회귀가 생기면 해당 서비스 이미지·설정만 변경 전 값으로 복원한다. 관측 창 변경과 성능 변경은 분리해 반영하여 원인을 구분할 수 있게 한다.
