# GPU 처리 전환 작업 계획서

- 작성일: 2026-11-15 KST
- 대상: Windows 호스트의 `ai-cctv` 배포, 파이 `cam-001` 및 `local-camera`
- 상태: 계획 작성 완료. 본 문서의 배포·설정 변경은 아직 실행하지 않았다.
- 근거: [바운딩 박스 및 CPU/GPU 조사 보고서](bounding-box-cpu-gpu-investigation-2026-11-15.md)

## 1. 목적과 기본 방침

**CPU에서 실행 중인 YOLO·OSNet·속성 분석을 GPU로 전환하여, 좌표가 3초 유효기간 안에 도착하고 두 카메라에 바운딩 박스가 표시되도록 한다.** CPU 사용량 감소는 동일 조건의 전환 전후 측정으로 평가한다.

기존 GPU Compose와 모델을 우선 사용한다. 전환 자체를 위해 새 추론 구조나 모델을 도입하지 않는다. 바운딩 박스 유효기간 3초와 관측 시각의 의미는 유지한다. GPU 전환 후에도 지연이 남으면 API/DB·디코딩·화면 출력을 순서대로 분리 조사한다.

사전 가정은 현재 운영 경로가 `C:\ProgramData\AI_CCTV`, 카메라가 두 대이고 GPU가 GTX 1650 Max-Q라는 것이다. 실행 직전에 재확인하며, 조사 당시 상태를 현재 상태로 간주하지 않는다.

## 2. 현재 상태와 목표 구성

| 항목 | 조사 당시 | 전환 목표 |
|---|---|---|
| GPU 모드 | `PREPROCESSING_GPU=false` | `true` |
| 전처리 이미지 | `ai-cctv-preprocessing:0.3.0` | 검증한 GPU 이미지 ID로 고정 |
| 분석 이미지 | `ai-cctv-analysis:0.3.0` | 검증한 GPU 이미지 ID로 고정 |
| Docker GPU 요청 | 두 AI 컨테이너 모두 없음 | 두 컨테이너에 GPU 할당 |
| 탐지 | PyTorch CPU | PyTorch CUDA |
| 인물 연결 | ONNX CPUExecutionProvider | CUDAExecutionProvider 선택 및 실제 추론 확인 |
| 속성 분석 | PyTorch CPU | PyTorch CUDA |
| 좌표 API | `expired`, 빈 객체 목록 | 신선한 좌표 및 실제 탐지 bbox 반환 |

운영 `compose.env`의 목표 값:

```dotenv
PREPROCESSING_GPU=true
INFERENCE_DEVICE=cuda:0
IDENTITY_DEVICE=cuda:0
ANALYSIS_DEVICE=cuda:0
```

GPU 사용을 명시하여 실행 장치와 의도를 일치시킨다. 기존 GPU 모드는 `auto`도 CUDA로 해석하지만, 전환 검증 시에는 명시한 장치를 사용한다. CPU 폴백을 정상 완료로 판정하지 않는다. ONNX의 CUDA provider 선택이 모든 연산의 GPU 실행을 뜻하는 것은 아니므로 실제 모델 실행도 검사한다.

## 3. 작업 범위와 서비스 영향

- 변경 대상은 운영 `compose.env`의 GPU/실행 장치 값과 `preprocessing`, `analysis` 컨테이너다.
- [기존 GPU 구성](../server/compose.gpu.yml)을 사용한다. 설정·의존성의 실제 결함이 재현된 경우에만 해당 부분을 수정한다.
- `data`, `external`, `nginx`, `mediamtx`, 로컬 FFmpeg 및 파이 송출기는 재생성 대상에서 제외한다. 두 카메라 송출·녹화 상태를 작업 전후 대조한다.
- AI 컨테이너 교체 동안 탐지·좌표·분석에 공백이 생기고 추적 세션이 새로 시작된다. 해당 구간의 이벤트 연속성을 보장하지 않으며, 중단 시작·복구 시각을 기록한다.
- DB 스키마, 인물 gallery, 모델 파일, RTSP 주소, 인증값, 보존 정책은 이 전환의 변경 대상이 아니다.

## 4. 단계별 실행 계획

| 단계 | 작업 | 다음 단계 진입 조건 |
|---|---|---|
| A | 기준 측정과 복귀 자료 준비 | 현재 이미지·설정·마운트·지표 확보 |
| B | 운영 교체 전 GPU 접근·모델 검증 | CUDA 연산과 세 모델 시험 실행 통과 |
| C | 전처리 GPU 전환 | 두 카메라 YOLO와 OSNet의 GPU 실행·신선한 좌표 확인 |
| D | 분석 GPU 전환 | 실제 신규 분석 작업 완료 및 GPU 상태 확인 |
| E | 두 카메라 동시 검증 | 지연·표시·안정성·CPU 비교 기준 통과 |

### A. 기준 측정 및 복귀 준비

1. 현재 Compose 프로젝트, 실행 이미지 ID, 적용된 override, 각 서비스 마운트, 카메라 송출·녹화 상태를 기록한다. 태그 이름만으로 현재 이미지 내용을 식별하지 않는다.
2. 운영 `compose.env`, `config.yaml` 및 적용 Compose 파일을 접근이 제한된 작업 백업 폴더에 보관한다. CPU 이미지에는 복귀 전용 태그를 붙여 재빌드로 덮어쓰이지 않게 한다.
3. DB 백업이 필요하면 SQLite 일관성을 보장하는 기존 백업 경로를 사용한다. 실행 중인 `.db` 파일 하나만 복사해 완전한 백업으로 취급하지 않는다. 이번 전환에는 DB 마이그레이션을 추가하지 않는다.
4. 같은 해상도·FPS·Desktop 화면 배치에서 5분간 카메라별 추론 시간, 좌표 관측 나이·stale 비율, timeout 증가량, Docker CPU/메모리, 호스트 CPU 및 GPU 메모리를 수집한다. 사람이 보이는 구간과 빈 장면을 구분한다.
5. `compose.env`의 사본으로 GPU 후보 설정을 준비한다. 아직 운영 파일에는 적용하지 않는다. 전체 resolved Compose는 비밀값이 포함될 수 있으므로 일반 로그에 출력하지 않고 `config --quiet` 검증과 필요한 항목만의 요약을 사용한다.

**산출물:** 전환 전 지표, CPU 이미지 ID/복귀 태그, 백업 경로, GPU 후보 설정, 서비스별 원래 실행 상태.

### B. 운영 교체 전 GPU 검증

1. Windows NVIDIA 드라이버, WSL 2 backend, Docker Engine 연결, GPU 총 VRAM·현재 사용량을 확인한다. 드라이버나 WSL 갱신은 접근 실패·호환성 문제로 필요성이 확인된 경우에 별도 수행한다. [Docker 공식 GPU 요구사항](https://docs.docker.com/desktop/features/gpu/)을 기준으로 확인한다.
2. 후보 설정에 기본 Compose와 GPU override가 함께 적용되는지 확인한다. 기존 push override가 활성화돼 있으면 함께 유지한다. 저장소의 [ComposeAdapter](../server/operations/compose.py)가 선택하는 구성과 일치시킨다.
3. 로컬 GPU 이미지의 ID, PyTorch/torchvision, CUDA·cuDNN·ONNX Runtime 버전을 검사한다. 이미지 태그 존재만으로 적합하다고 판단하지 않는다. 필요한 재빌드는 운영 교체 전에 끝내고 검증한 이미지 ID를 고정한다.
4. 기존 GPU 설정은 전처리 `torch 2.8.0 / torchvision 0.23.0 / cu126`, 분석 `torch 2.13.0 / torchvision 0.28.0 / cu126`을 지정한다. 두 조합은 [PyTorch 공식 설치표](https://pytorch.org/get-started/previous-versions/)에 기재돼 있다. 최신 버전으로 일괄 변경하지 않고 실제 설치 버전·모델 로딩을 대조한다.
5. OSNet용 `onnxruntime-gpu 1.20.2`는 1.20 계열의 CUDA 12.x·cuDNN 9.x 요구와 로더 경로를 확인한다. [ONNX Runtime 공식 호환표](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)를 참조하되, 이 호스트의 실제 세션 생성·추론 통과를 최종 기준으로 한다.
6. 후보 이미지로 GPU를 할당한 임시 컨테이너를 실행한다. 진입점을 진단용 Python으로 바꾸고 서비스 앱·작업 소비기는 기동하지 않는다. 모델은 읽기 전용으로 연결하고 운영 DB에 이벤트나 작업 결과를 쓰지 않는다.
7. `torch.cuda.is_available()`, GPU 이름, CUDA 텐서 연산과 동기화, YOLO warmup, OSNet 세션 생성·시험 추론, PAR 모델 로딩·시험 추론을 검증한다. provider 목록 조회만으로 OSNet 성공을 판정하지 않는다.
8. 시험 컨테이너를 종료한 뒤 VRAM이 해제되는지 확인한다. CPU 운영과 임시 GPU 검증이 겹치는 구간은 짧게 유지하며 해당 부하는 성능 비교 표본에서 제외한다.

**실패 시:** 운영 전환을 진행하지 않고 CUDA 접근, DLL/공유 라이브러리 로딩, 모델·VRAM 문제를 해결한다. 소스/Compose 수정이 필요하면 관련 회귀 검사와 계약 서명을 확인한다. 설치 도구가 계약 불일치 초기화를 요구할 경우 데이터 초기화로 해결하지 않고 변경 원인을 검토한다.

### C. 전처리 GPU 전환

1. A에서 기록한 설정과 서비스 상태를 다시 확인하고 운영 GPU 값을 적용한다.
2. `analysis`를 먼저 정상 중지하여 모델 초기화 시 GPU 경합과 분석 장치의 일시적 혼합을 줄인다. 전처리의 정상 종료에는 이벤트 outbox 정리 시간이 필요하므로 기존 종료 유예를 유지한다.
3. 검증한 이미지로 `preprocessing`만 `up -d --no-deps --force-recreate --no-build --pull never` 방식으로 재생성한다. 같은 Compose 프로젝트·env·override를 사용한다. 단순 `restart`는 이미지·GPU 할당 변경을 반영하는 수단으로 사용하지 않는다.
4. 컨테이너 GPU 요청과 실제 PyTorch CUDA 접근을 확인한다. `/internal/v1/status`에서 두 카메라의 `model_ready=true`, `execution_device=cuda:0`, OSNet의 GPU 실행 상태를 확인한다.
5. 사람이 보이는 조건에서 좌표 API의 `stale=false`, bbox 및 화면 표시를 확인한다. 이 단계가 실패하면 분석 서비스 확대 전환을 진행하지 않는다.

**영향:** 전처리 교체 중 AI 결과가 잠시 중단된다. 송출·녹화 유지 여부는 실제 상태와 녹화 세그먼트 증가로 확인한다.

### D. 속성 분석 GPU 전환

1. 검증한 GPU 이미지로 `analysis`만 C와 동일한 재생성 옵션을 사용해 기동한다.
2. `/health/ready` 본문의 `ready`, `model_ready`, `execution_device=cuda:0`을 확인한다. HTTP 200만으로 완료 처리하지 않는다.
3. 두 카메라에서 새 등장 이벤트를 발생시켜 각 이벤트의 분석 작업과 `analysis_completed`를 확인한다. 오래된 완료 이벤트를 새 전환의 증거로 사용하지 않는다.
4. YOLO 두 워커·OSNet·PAR·로컬 NVENC가 함께 동작할 때 VRAM, 오류, 좌표 지연을 대조한다. 과거 실패 작업의 일괄 재등록은 이 전환과 분리한다.

### E. 최종 검증과 운영 반영

1. 초기 모델 준비 구간을 별도로 기록한 뒤 두 카메라와 Desktop을 켠 상태로 15분 이상 관찰한다. 각 카메라에서 정지·이동·화면 이탈/재등장을 수행한다.
2. 좌표 API를 카메라별 1초 간격으로 관찰하고 정상 빈 장면의 `objects=[]`와 `expired`를 구분한다. API 조회 권한은 External 서비스 또는 정상 로그인 세션의 권한을 사용한다. inference 토큰은 좌표 PUT용이므로 조회용으로 전용하지 않는다.
3. 상태 API의 추론 지연과 타이밍 창, `model_timeouts`, 전달 오류, health 본문을 수집한다. 타이밍 창은 최근 100표본이므로 15분 전체 통계로 오해하지 않는다.
4. 최종 5분의 CPU/GPU 지표를 A와 같은 조건으로 비교한다. GPU 사용률의 높낮이보다 실제 장치 선택과 처리 지연을 우선한다.
5. 최종 이미지 ID·패키지 버전·설정·검증 결과·AI 공백 시각·잔여 문제를 결과 보고서에 기록한다. 런타임/장치 변경이 향후 관리 도구에서도 유지되는지 확인한다.

## 5. 완료 기준

아래 수치는 측정 전 확정 성능이 아니라 이번 작업의 검증 목표다.

| 구분 | 필수 완료 기준 |
|---|---|
| 실제 GPU 실행 | 두 탐지 워커·OSNet·PAR의 준비 성공과 실제 GPU 추론 확인 |
| 좌표 신선도 | 워밍업 이후 카메라별 API 관측 나이 p95 < 2초, 조회 표본의 `stale=false` 비율 ≥ 99%; 3초 기준 초과의 반복/지속 없음 |
| 화면 표시 | 탐지 가능한 사람이 보이는 조건에서 양쪽 카메라의 bbox 표시·이동 갱신 확인 |
| 오류 안정성 | 15분 검증 동안 모델 timeout 누계 증가, CUDA OOM, 모델 재시작, 지속 전달 실패 없음 |
| 이벤트·분석 | 카메라별 신규 등장 이벤트 및 해당 분석 완료 확인 |
| 송출·녹화 | 작업 전후 두 카메라 영상 재생·녹화 상태와 신규 녹화 세그먼트 확인 |
| CPU 비교 | 동일 조건 전환 전후 5분 평균과 p95 보고; 감소가 확인되지 않으면 남은 부하 원인을 기록하고 CPU 개선 완료로 판정하지 않음 |

좌표 API의 관측 나이는 네트워크·화면 출력 지연 전체와 같지 않다. 화면의 실제 표시도 함께 확인한다. 전체 영상 디코딩과 화면 출력은 CPU에 남을 수 있어 CPU 사용량이 0에 가까워지는 것을 목표로 삼지 않는다.

## 6. 실패 분기 및 롤백

| 상황 | 대응 |
|---|---|
| GPU 접근·시험 추론 실패 | 운영 파일 변경 전에 원인 해결. 임시 컨테이너 종료 |
| 전처리 GPU 기동 실패 또는 좌표 만료 지속 | 분석 전환 중단, 전처리 상태/타이밍 확인 후 해결되지 않으면 CPU 복귀 |
| PAR 추가 후 OOM·박스 지연 재발 | 분석을 중지해 전처리 회복 여부 확인. 속성 분석만 CPU로 두는 축소 구성은 측정 후 별도 결과로 명시 |
| 좌표는 신선하고 bbox가 있으나 화면에는 미표시 | GPU 전환 상태를 유지할 수 있는지 평가하고 Desktop 표시 설정·오버레이·화면 스레드를 별도 조사 |
| 송출·녹화 중단 | AI 변경을 중지하고 해당 서비스 연결·마운트·재생 상태 복구 우선 |

롤백 절차:

1. GPU AI 서비스만 정상 중지하고 GPU 자원이 해제됐는지 확인한다.
2. A에서 보관한 운영 env를 복원하여 원래 GPU 모드와 세 장치 설정을 되돌린다. GPU override가 CPU 복귀 구성에 남지 않았는지 확인한다.
3. 복귀 override로 A의 CPU 이미지 태그를 명시하여 두 AI 서비스만 `--no-deps --force-recreate --no-build --pull never`로 재생성한다. 롤백 중 재빌드하거나 가변 태그의 최신 내용을 가져오지 않는다.
4. 서비스 실행 상태를 작업 전 상태로 복원하고, 영상·녹화·CPU 모델 준비·이벤트 처리 상태를 확인한다. CPU 복귀는 변경 전 상태의 회복이며 기존 지연 문제의 해결은 아니다.

전환·롤백 모두 전체 스택의 `down`, 볼륨 삭제, DB/이벤트 초기화, 시크릿 재발급은 사용하지 않는다.

## 7. 예상 소요와 산출물

| 작업 | 예상 소요 |
|---|---|
| 기준 측정·복귀 자료 확보 | 10~15분 |
| 기존 GPU 이미지 검사·시험 추론 | 10~20분 |
| 두 AI 서비스 단계 전환 | 5~10분 |
| 동시 검증·결과 정리 | 20~30분 |

정상 경로는 약 45~75분을 작업 예상치로 잡는다. 이미지 재빌드·대용량 다운로드·드라이버/WSL 복구가 필요하면 별도 시간이 든다. AI 결과 중단은 이 전체 작업 시간보다 짧으며 C~D 단계의 실제 시각으로 기록한다.

최종 산출물은 적용 설정과 이미지 ID, 전환 전후 지표 비교, 두 카메라 박스 표시 결과, 신규 이벤트/분석 결과, 롤백 가능 여부를 담은 실행 결과 보고서다.
