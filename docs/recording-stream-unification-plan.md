# 녹화·송출 시작 및 중지 통합 계획서

작성일: 2026-10-28 · 상태: 코드 조사 완료 / 구현 전

## 1. 목표와 적용 기준

관제 화면에는 상단의 `전체 녹화 시작`, `전체 녹화 중지`와 카메라별 `녹화 시작`, `녹화 중지`만 둔다. 녹화 시작은 영상 송출·화면 표시·중앙 녹화·Edge 로컬 백업 녹화를 함께 시작하고, 녹화 중지는 이들을 함께 종료한다.

앞선 요청에 따라 Edge 로컬 백업 녹화도 중지 범위에 포함한다. 로컬 노트북 카메라와 관리 가능한 Edge의 사용자 동작은 동일하게 맞춘다. 노트북 카메라 사용 옵션과 장치 선택은 설정에 유지하며, 설정에서 일상적인 시작·중지를 수행하지 않는다.

이 계획은 기존의 녹화와 송출 분리 방식을 대체한다. 이번 작업은 계획서 작성이며 프로그램 수정은 후속 구현 범위다.

| 버튼 | 송출 및 화면 | 중앙 녹화 | Edge 백업 녹화 |
| --- | --- | --- | --- |
| 개별 녹화 시작 | 해당 카메라 시작 | 해당 카메라 시작 | 해당 카메라 시작 |
| 개별 녹화 중지 | 해당 카메라 중지·마지막 프레임 제거 | 해당 카메라 종료 | 해당 카메라 종료 |
| 전체 녹화 시작 | 대상별 개별 시작과 동일 | 대상별 개별 시작과 동일 | 대상별 개별 시작과 동일 |
| 전체 녹화 중지 | 대상별 개별 중지와 동일 | 대상별 개별 중지와 동일 | 대상별 개별 중지와 동일 |

중복 시작은 실행 중인 publisher와 녹화 파일을 불필요하게 재시작하지 않는다. 중복 중지도 안전하게 성공해야 한다. 의도적인 중지는 네트워크 장애로 표시하거나 자동 재연결하지 않는다.

## 2. 현재 코드에서 바꿀 지점

| 파일 및 경로 | 현재 문제 | 변경 방향 |
| --- | --- | --- |
| `server/desktop/admin/legacy_gui.py`, `camera_view.py` | 녹화 버튼 외에 송출 중지·재개 버튼과 신호가 존재 | 송출 전용 버튼·신호·배치를 제거 |
| `server/desktop/admin/application.py` | 녹화와 송출의 전체·개별 처리 및 busy 상태가 나뉨 | 카메라별 시작/중지 작업을 공통화하고 전체 작업에서 재사용 |
| 같은 파일의 `_start_local_camera_for_recording()` | 송출 전용 API로 허용 상태를 바꾼 뒤 FFmpeg 실행 | 통합 녹화 시작 API를 호출한 뒤 FFmpeg 실행 |
| 같은 파일의 녹화 중지 경로 | API 호출 후 로컬 publisher와 화면이 계속 동작 가능 | 서버 중지·로컬 publisher 종료·worker 종료·화면 초기화를 한 작업으로 수행 |
| `server/services/external/app/api/cameras.py` | `_apply_camera_recording()`이 송출 중지 시 `CAMERA_STREAM_STOPPED`를 반환 | 녹화 시작 자체가 송출도 허용하도록 수정 |
| 같은 파일의 송출 전용 API | 독립 송출 제어를 유지하여 상태 조합과 호출 경로 증가 | 호출처를 통합 녹화 API로 전환한 뒤 제거 |
| Data의 `recording_enabled`, `stream_requested` | 두 희망 상태가 독립적으로 저장됨 | 녹화 희망 상태를 기준으로 두 값을 함께 기록 |
| Edge의 capture 제어 | 송출과 백업 녹화 플래그를 각각 전달 | 관제 시작/중지에서는 항상 같은 값으로 전달 |

## 3. 상태를 단순화하는 방법

`recording_enabled`를 운영 시작/중지의 기준값으로 사용한다. 사용자 명령을 적용할 때 `stream_requested`도 같은 값으로 한 번의 Data 갱신에 저장한다. 카메라 등록 여부를 나타내는 `enabled`는 별도로 유지한다.

- 시작 희망 상태: `recording_enabled=true`, `stream_requested=true`.
- 중지 희망 상태: 두 값 모두 `false`.
- 실제 연결·파일 기록 상태는 희망 상태와 구분한다. 요청 수락만으로 실제 녹화 완료를 표시하지 않는다.
- 기존 DB 컬럼과 적용된 migration 012는 유지한다. 컬럼 삭제나 새로운 상태 저장 체계는 도입하지 않는다.
- 등록 시에는 두 값 모두 `false`로 초기화하고, 설정 변경·인증값 교체만으로 동작을 시작하지 않는다.
- 기존 불일치 데이터는 업그레이드 시 `recording_enabled`를 기준으로 정리한다. 녹화가 꺼진 채 송출만 켜져 있던 카메라는 중지로 전환된다. 비활성 카메라는 두 값을 모두 `false`로 맞춘다.
- 주기 동기화, 관리 PATCH, 재등록 및 비활성화 경로도 같은 규칙을 적용하여 불일치 상태가 재생성되지 않게 한다.

UI에는 `중지`, `시작 중`, `녹화 중`, `중지 중`, `오류`만 사용한다. 실제 영상 수신과 녹화 상태 확인 전에는 `시작 중`으로 표시한다. 기존 상태 조회와 worker 신호를 활용한다.

## 4. 공통 시작 순서

### 서버와 Edge

1. 권한과 카메라 활성 여부를 검사한다. 송출이 꺼져 있다는 이유로 시작을 거절하는 분기는 제거한다.
2. 카메라별 기존 잠금 안에서 두 희망 상태를 `true`로 함께 저장한다. 중앙 publisher 인증이 먼저 허용되어야 한다.
3. MediaMTX의 해당 경로에 녹화를 활성화한다.
4. 관리 가능한 Edge에는 `stream_enabled=true`, `recording_enabled=true`를 한 번의 capture 제어 요청으로 보낸다.
5. 명령 적용 결과를 반환하고, 실제 영상 도착과 녹화 상태는 잠금을 해제한 뒤 기존 상태 조회로 확인한다. 미디어 인증도 같은 잠금을 쓰므로 영상 도착을 기다리는 동안 잠금을 유지하지 않는다.

### 노트북 로컬 카메라

1. 사용 옵션과 선택 장치를 확인하고, 등록·인증값 준비를 수행한다. 옵션이 꺼진 경우 전체 시작에서는 제외하고 개별 시작에서는 설정 안내를 표시한다.
2. 위의 통합 녹화 시작 API를 호출한다. 별도 송출 허용 API는 호출하지 않는다.
3. FFmpeg publisher를 시작한다. 같은 장치의 publisher가 이미 실행 중이면 재사용한다.
4. HLS 영상 도착을 확인하고 미리보기 worker를 연결한다. 중앙 녹화 상태는 기존 조회로 확인한다.
5. FFmpeg 시작 또는 영상 준비에 실패하면 이번에 시작한 작업을 통합 중지 경로로 정리한다. 원래 정상 동작 중이던 카메라를 중복 시작 요청 실패 때문에 끊지 않는다. 정리 실패도 원인과 함께 표시한다.

송출이 실제로 진행 중인데 녹화 확인만 실패한 경우에는 성공으로 표시하지 않는다. 서버에 저장된 희망 상태와 실제 상태를 재조회하여 오류 및 중지 가능 상태를 유지한다.

## 5. 공통 중지 순서

1. 데스크톱에서 해당 카메라의 자동 worker 재시작을 차단하고 프레임 표시를 중단한다. 늦게 도착한 프레임·이벤트는 기존 worker 식별 검사로 무시한다.
2. 서버는 두 희망 상태를 `false`로 함께 저장한다. 이후 publish/read 인증과 주기 동기화가 중지 의도를 유지하게 한다.
3. MediaMTX 중앙 녹화를 종료하고 Edge에 `false, false`를 적용한다. Edge는 백업 파일을 정상 마감한 뒤 출력을 중지한다.
4. 중앙 publisher 연결을 해제한다. 앞 단계 일부가 실패하더라도 나머지 중지 단계는 계속 시도하고 오류를 모아 반환한다.
5. 로컬 카메라는 서버 API 성공 여부와 관계없이 FFmpeg 종료를 시도한다. worker와 화면의 마지막 프레임·오버레이도 정리한다.
6. 중앙·Edge·로컬 중 확인하지 못한 항목이 있으면 `중지 일부 실패`로 표시한다. 사용자가 같은 중지 버튼으로 다시 시도할 수 있게 한다.

Edge가 네트워크에서 단절되어 있으면 백업 녹화를 즉시 원격 종료할 수 없다. 서버의 중지 희망 상태는 유지하고 Edge 중지 미확인을 표시하며, 연결 복구 시 먼저 중지 명령을 적용한다. 시작 희망 상태에서의 실제 네트워크 장애는 기존 재연결과 Edge 백업 정책을 유지한다.

## 6. 전체와 개별 동작 통합

- 데스크톱의 카메라별 백그라운드 작업에서 로컬 준비/종료와 공통 API 호출을 수행한다. 전체 버튼은 같은 작업을 대상별로 실행하고 결과를 집계한다. 별도의 전체 송출 처리 절차는 두지 않는다.
- 기존 서버 전체 녹화 API는 유지하되, 서버의 동일한 개별 제어 함수를 재사용한다. Windows FFmpeg 실행·종료는 데스크톱이 담당하며 서버 API만으로 완료했다고 보고하지 않는다.
- 전체 시작은 활성 카메라를 대상으로 하며, 노트북 카메라 옵션이 꺼져 있으면 해당 카메라를 제외한다. 이미 동작 중인 카메라는 유지한다.
- 전체 중지는 현재 동작 또는 정리 실패가 남은 카메라와 로컬 publisher도 정리한다. 사용 옵션 변경이나 비활성화 때문에 중지 대상에서 빠지지 않게 한다.
- 카메라 하나의 장치 오류·Edge 오류·서버 오류가 다른 카메라 처리를 중단하지 않게 한다. 서버 전체 녹화 처리에서 누락된 `EdgeControlError`도 카메라별 실패 집계에 포함한다.
- 전체 제어 중에는 개별 제어를 잠그고, 개별 제어가 진행 중이면 전체 제어를 잠근다. 카메라별 작업 상태는 시작/중지에 공통으로 사용한다.
- 성공·실패·제외 결과를 각각 표시하고, 실패 시 실제 조회 결과를 사용한다. 전체 카메라에 요청값을 일괄 덮어써 성공처럼 보이게 하지 않는다.

## 7. 제거와 재사용 범위

제거 대상은 송출 전용 UI 버튼·신호, 데스크톱의 `start_all_streams`, `stop_all_streams`, `start_camera_stream`, `stop_camera_stream` 전용 작업, 송출 전용 DesktopApi 메서드, 사용처 전환을 마친 외부 `/stream` 제어 route와 전용 schema다. 저장소의 CLI·다른 화면·테스트 호출처를 함께 검색하여 녹화 API로 전환한다.

재사용 대상은 로컬 장치 및 인증값 준비, publisher 시작·종료, 영상 도착 확인, 카메라별 잠금, DB 저장, MediaMTX 제어, Edge capture 제어, 중지 상태의 인증 차단과 worker 재시작 차단이다. 중지에 필요한 코드를 송출 전용 메서드와 함께 삭제하지 않고 통합 녹화 경로로 옮긴다.

Edge의 기존 capture 구현과 두 내부 플래그는 유지하고 관제 명령에서 같은 값을 전달한다. GStreamer 파이프라인 재작성이나 물리적인 카메라 전원 제어는 추가하지 않는다. 관리 API가 없는 외부 publisher는 중앙 접근·녹화·화면만 제어할 수 있으므로 실제 장치 송출 종료와 구분하여 결과를 표시한다.

## 8. 구현 순서와 완료 기준

1. **서버 제어 통합**: 녹화 API에서 두 상태 동시 저장, 시작 거절 분기 제거, 중지 단계 통합, 주기 동기화 및 초기값 정리. → 중지된 Edge에 녹화 시작 API만 호출해 송출·녹화가 함께 복구된다.
2. **데스크톱 개별 동작 통합**: 로컬 준비→통합 API→FFmpeg→영상 확인과 공통 종료 절차 연결. → 로컬과 Edge 모두 개별 시작/중지만으로 반복 운용된다.
3. **전체 동작 재사용 및 UI 정리**: 전체 작업에서 개별 작업 재사용, 중복 제어 잠금, 송출 전용 버튼·메서드·API 호출처 제거. → 전체/개별 제어 결과가 같고 전용 송출 버튼이 없다.
4. **기존 상태 전환 및 회귀 확인**: 불일치 데이터 정리와 재시작 경로 점검. → 중지 상태에서 앱·서버·Edge를 재시작해도 송출·녹화가 임의 재개되지 않는다.

## 9. 검증 항목

- 로컬·Edge 각각 `시작 → 영상 표시 및 녹화 → 중지 → 화면 초기화 및 파일 마감 → 재시작`을 반복한다.
- 중앙 파일과 Edge 백업 파일의 생성·증가·마감을 확인한다. 명령 플래그 일치나 Python 컴파일만으로 완료를 판단하지 않는다.
- Edge `central_publish`, `central_pull` 두 모드에서 중지 후 재시작을 확인한다.
- 전체/개별 혼합 제어, 연속 클릭 및 중복 명령에서 publisher·worker 중복과 녹화 불필요 재시작이 없는지 확인한다.
- 한 카메라 실패, 로컬 사용 해제, 장치 미선택, FFmpeg 실패, API 오류, Edge 오프라인에서 나머지 카메라와 중지 정리가 계속 동작하는지 확인한다.
- 의도된 중지 이후 장애 알림·자동 재연결이 발생하지 않고, 시작 상태의 실제 장애에서는 재연결·백업이 유지되는지 확인한다.
- 서비스 재시작과 주기 동기화가 이전 상태를 덮어쓰지 않는지 확인한다.
- 송출 전용 버튼·신호·호출처가 제거되었고 설정에는 사용 옵션과 장치 선택이 남아 있는지 확인한다.

현재 기본 Python 환경에는 `pytest`와 `PyQt5`가 없어 앞선 테스트 실행이 차단되었다. 후속 구현 시 프로젝트 GUI 실행 환경의 Python과 의존성을 먼저 확인하고 해당 환경에서 회귀 테스트와 실제 카메라 검증을 수행한다.
