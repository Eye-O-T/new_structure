# Server GUI의 Edge 연결 인터페이스 수정 계획

작성일: 2026-11-11 (KST)  
상태: **구현 완료. 소스 정적 검사와 Edge ID 단위 테스트 통과. Windows GUI 및 실제 Pi 연결 검증은 남아 있다.**

## 목표와 적용 범위

현재 사용하는 `ai_cctv.ps1 cli manager` 실행 경로에서 신규 Edge 등록, 페어링 설정 전달, 기존 장치 상태 조회까지 진행할 수 있게 한다. 기존 `EdgePanel`, 관제 로그인 세션, Host Helper를 재사용한다.

Server Manager는 서버 서비스·네트워크 운영을 담당하고, Edge 연결과 카메라 관리는 관제 화면에서 수행한다. 별도 실행 파일이나 새로운 CLI 명령을 추가하지 않는다. Edge 캡처·복구 결함의 수정과 실기 검증은 병행할 수 있으며, GUI 계획·구현의 선행 차단 조건으로 두지 않는다.

사용자 실행 경로는 다음으로 통일한다.

```text
ai_cctv.ps1 cli manager
→ 서버 ready 확인
→ CCTV 관제 · Edge 연결 열기
→ 설정에서 관리자 로그인
→ 카메라 등록 · 운영 설정
→ [신규 Edge 연결] 또는 [등록된 카메라]
```

관제 화면만 열 때는 기존 `ai_cctv.ps1 cli admin`을 계속 사용한다.

신규 연결 탭의 자동 페어링은 미설정 Edge를 대상으로 한다. 이미 설정된 Edge를 다른 Server로 옮길 때는 현재의 `configure` 기반 [수동 이전 절차](edge-server-pairing-guide.md#8-기존-edge를-새로운-server로-이전)를 안내한다. 기존 Edge의 이전까지 최초 페어링 API가 지원하는 것처럼 표시하지 않는다.

## 현재 코드에서 연결해야 할 부분

| 현재 상태 | 수정 방향 |
|---|---|
| Server Manager에 `CCTV 관제 화면 열기`가 있다. | 같은 실행 동작을 유지하고 버튼 문구를 `CCTV 관제 · Edge 연결 열기`로 바꿔 진입점을 알린다. |
| 설정 화면은 `CameraManagement`를 열지만 `EdgePanel`을 생성하지 않는다. | 기존 관리 대화상자에 두 탭을 두고 `EdgePanel`을 실제로 배치한다. |
| `EdgePanel`에 별도 계정·암호 입력과 별도 `ServerApiClient` 생성이 있다. | 로그인된 `DesktopApi`를 전달받아 사용한다. 관리자 암호를 다시 입력받지 않는다. |
| 수동 등록 폼에 `edge_mac_address`가 없다. | 등록 탭의 입력 계약에 MAC 주소를 포함하고 기존 수동 등록 진입점도 같은 계약으로 정리한다. |
| 연결 확인 함수가 응답의 장치 ID를 비교하지 않는다. | 응답의 `device_id`, `camera_id`를 선택한 광고와 대조한 뒤 등록을 허용한다. |
| 중앙 등록 뒤 자동 전달 실패 시 게시 계정을 파일로 저장한다. | 중앙 등록 직후 먼저 보호 파일에 저장하고, 자동 전달 실패 시 같은 등록의 후속 작업을 이어갈 수 있게 한다. |

## 화면과 입력 설계

`CameraManagement`에 `신규 Edge 연결`, `등록된 카메라` 탭을 둔다. 기존 장치 목록·상태 조회·수정·화질 변경·게시 계정 재발급은 등록된 카메라 탭에 유지한다. 현재의 새 카메라 등록 버튼은 신규 연결 탭으로 이동하고, 수동 입력은 그 탭의 기존 직접 등록 모드로 통합해 등록 동작을 중복 구현하지 않는다.

신규 연결 탭은 현재 `EdgePanel`의 `Edge 찾기 → 연결 확인 → 선택한 Edge 연결` 흐름과 고급 설정을 재사용한다.

| 입력·정보 | 기본 동작 |
|---|---|
| 관리자 로그인 | 관제 화면의 기존 세션을 사용한다. 세션이 없으면 연결 기능을 비활성화하고 로그인을 안내한다. |
| 발견한 Edge | 이름, 장치 ID, 카메라 ID, IP, MAC을 표시한다. IP만으로 장치를 구별하지 않는다. |
| 카메라 이름 | 사용자가 입력한다. |
| Edge 운영 인증 토큰 | 32자 이상의 ASCII 토큰을 마스킹해 받는다. Pi에서 내보낸 토큰 파일을 선택해 읽는 입력도 제공한다. 값은 로그에 표시하지 않는다. |
| 장치 ID·카메라 ID·MAC·관리/복구 주소 | 검색 결과로 채운다. 직접 등록 모드에서는 필수 입력이며 MAC을 정규화한다. |
| Server HTTP(S) 주소 | 기존 관제 연결 주소를 사용한다. 사용자가 신규 연결 탭에서 다른 서버로 바꾸지 않게 한다. |
| Edge에서 접근할 Server 주소 | 기존 `rtsp_host`를 초기값으로 쓰되 loopback·미지정 주소이면 실제 LAN 주소 입력을 요구한다. |
| RTSP 포트 | 설치된 배포의 `rtsp_port`를 사용한다. 기본은 8554다. |
| 화질 | 발견한 Edge가 광고한 HD/FHD 중 선택한다. 실제 지원과 적용 결과는 이후 상태 조회로 확인한다. |
| 백업 경로 | 기본 `/var/lib/ai-cctv-edge/recordings`; 고급 설정에서 변경한다. |
| 게시 계정 전달 파일 | 데이터 저장소 아래의 장치별 파일 경로를 기본으로 제시하고 기존 보호 파일 저장 함수를 사용한다. |

HTTP(S) API 주소와 RTSP 호스트는 서로 다른 입력이다. 예를 들어 PC의 관리 API가 `http://127.0.0.1`이어도 Pi에 전달할 영상 수신 주소는 `192.168.0.10:8554`와 같은 PC의 LAN 주소여야 한다. `0.0.0.0`은 bind 설정일 수 있으나 Pi에 전달할 접속 주소로 사용하지 않는다.

관제 앱에 이미 전달되는 `server_url`, `rtsp_host`, `rtsp_port`, `storage_root_path`, `ca_file`, `allow_insecure_http`를 그대로 연결한다. `DesktopApi`를 재사용해 HTTPS의 추가 CA와 기존 HTTP 허용 설정이 새 연결 탭에서도 유지되게 한다. 새로 비검증 TLS 클라이언트를 만들지 않는다.

## 페어링 처리 순서

1. 입력, 선택 장치, 게시 계정 저장 경로를 검사한다. Host Helper로 `/health/live`를 조회하고 광고의 두 ID와 응답이 일치하는지 확인한다. 자동 신규 연결은 `status=pairing`인 장치에만 진행한다.
2. 기존 관리자 세션으로 중앙 카메라를 한 번 등록한다. MAC 주소를 포함한 현재 `register_edge` 계약을 사용한다.
3. 응답의 일회성 게시 계정을 `write_publish_credentials`로 먼저 저장한다. 저장에 실패하면 응답을 메모리에 유지하고 저장 재시도를 제공한다. 다시 등록하거나 계정을 자동 재발급하지 않는다.
4. 저장된 응답과 운영 토큰, RTSP 호스트·포트, 화질, 백업 경로를 기존 `pair_edge_via_helper`에 전달한다.
5. Edge의 `configured` 응답을 받으면 설정 전달 완료로 표시하고 등록된 카메라 목록을 갱신한다. 서버의 상태 수집이 반영될 때까지 관리 연결은 대기로 표시할 수 있다.
6. 등록 완료 후 사용자가 `녹화 시작`을 누르면 송출·녹화 상태를 별도로 확인한다. 페어링 과정에서 녹화를 자동 시작하지 않는다.

최소 작업 결과는 `camera_id`, 중앙 등록 완료 여부, Edge 설정 전달 완료 여부, 게시 계정 파일 경로를 구분해서 보관한다. UI에 표시하는 진행 상태는 다음과 같다.

| 상태 | 다음 사용자 동작 |
|---|---|
| 장치 검색됨 | 장치를 선택하고 연결 확인 |
| 연결 확인됨 | 이름·운영 토큰·LAN 주소 확인 후 연결 |
| 중앙 등록 완료 / Edge 설정 전달 대기 | 새로 등록하지 않고 전달을 재시도하거나 기존 전달 파일로 Pi 설정 |
| Edge 설정 전달 완료 / 관리 연결 대기 | 상태 다시 조회 |
| 관리 연결 확인 / 녹화 중지 | 필요할 때 녹화 시작 |
| 영상 수신 확인 | 실제 live 영상과 중앙 녹화 확인 |

전달 요청이 타임아웃되면 먼저 기존 카메라 상태와 동일 Edge의 현재 응답을 확인한다. 설정 적용 여부가 불명확한 동안 완료로 단정하거나 중앙 등록을 반복하지 않는다. Edge가 계속 최초 설정 대기 중일 때만 같은 등록의 설정 전달을 재시도한다. 이미 운영 상태이면 등록된 카메라에서 확인하도록 안내한다.

## 오류·창 수명 처리

- 검색 결과 없음, 장치 ID 불일치, 중앙 인증 실패, Edge 설정 전달 실패를 구분해 원인과 다음 동작을 표시한다.
- 기존 `BackgroundTask`와 Host Helper를 사용한다. 작업 시작 전에 입력을 복사하고 작업 스레드에서 위젯을 읽지 않는다.
- `EdgePanel.busy_changed`를 부모 관리 대화상자에 연결한다. 검색·등록·전달 중에는 중복 요청, 탭 전환으로 인한 입력 변경, 닫기와 Esc 종료를 함께 제어한다.
- 대화상자의 작업과 `pending` 게시 계정 응답이 남아 있으면 부모도 종료를 보류한다. 자식 QWidget의 `closeEvent`만으로 부모 종료를 막을 수 있다고 가정하지 않는다.
- API 오류의 코드와 메시지를 표시하되 토큰·비밀번호가 들어갈 수 있는 원본 payload나 traceback을 그대로 출력하지 않는다. 기존 비밀값 제거 함수를 사용한다.
- 로그아웃이나 서버 변경 뒤에는 이전 세션의 등록 요청을 계속 보내지 않는다. 작업이 끝난 뒤 새 세션으로 다시 열게 한다.

새 DB 스키마, 페어링 프로토콜 버전, 별도 백그라운드 서비스는 필요하지 않다. `desktop/launcher.py`가 이미 전달하는 배포 인수를 우선 재사용한다. 설치 EXE는 기존 Admin·Host Helper 패키지에 해당 모듈이 포함되는지 확인한다.

## 구현 순서와 완료 기준

| 단계 | 구현 | 확인 기준 |
|---|---|---|
| 1 | 화면 연결·컨텍스트 전달·등록 입력 정리 | `cli manager`에서 관제·관리 대화상자·두 탭까지 열리고, 로그인 세션과 LAN/포트 기본값이 유지된다. MAC 누락은 API 요청 전에 표시된다. |
| 2 | ID 검증·중앙 등록·보호 파일 저장·Edge 전달 | 정상 입력은 중앙 등록 1회와 설정 전달로 끝난다. 다른 ID는 중앙 등록 전에 거절한다. |
| 3 | 부분 성공·재시도·상태 표시·종료 처리 | 전달 실패 후 등록 POST가 반복되지 않는다. 저장 실패·작업 중 Esc·부모 창 닫기에서 응답이나 작업을 잃지 않는다. |
| 4 | Windows 실행 및 Pi 연결 검증·문서 동기화 | 소스 실행과 설치 EXE에서 같은 흐름이 열리고, 실제 Pi에서 관리 연결과 녹화 시작 후 영상 수신을 각각 확인한다. |

의미 있는 회귀 시나리오는 정상 신규 등록, MAC 누락, 다른 ID 응답, HTTPS 추가 CA, 명시적 HTTP 배포, 중앙 등록 후 전달 실패, 저장 실패 후 재시도, 중복 클릭, 작업 중 부모 종료다. 기존 관제 영상·이벤트 조회와 카메라 운영 설정이 계속 동작하는지도 확인한다.

화면·요청 흐름 검증에는 테스트 대역을 사용하고, Pi/GStreamer가 필요한 영상 시작·반복 재시작·복구는 별도 실기 결과로 기록한다. GUI가 열리고 설정을 전달한 사실과 실제 영상이 정상인 사실을 구분한다.

## 완료 후 사용자 절차

`cli manager` 실행 → 서버 ready 확인 → `CCTV 관제 · Edge 연결 열기` → 설정에서 로그인 → `카메라 등록 · 운영 설정`의 `신규 Edge 연결` → `Edge 찾기` → 장치·ID 확인 → 토큰과 LAN 주소 입력 → 연결 → `등록된 카메라`에서 상태 확인 → 필요 시 `녹화 시작`.

Pi 준비, 현재 가능한 수동 연결, 오류별 대응은 [Edge–Server 페어링 절차서](edge-server-pairing-guide.md)를 따른다. 관련 코드 조사 결과는 [연결·동작 조사](edge-server-connection-audit-2026-11-11.md)에 있다.

## 구현 결과

- Server Manager 진입 버튼을 `CCTV 관제 · Edge 연결 열기`로 바꾸고 기존 관제 실행 방식을 유지했다.
- 카메라 관리 화면에 `신규 Edge 연결`과 `등록된 카메라` 탭을 연결했다. 신규 연결은 이미 로그인된 `DesktopApi`를 사용한다.
- Edge 토큰 파일 입력, MAC 검증, HTTP health 응답의 장치·카메라 ID 확인, LAN에서 도달할 RTSP 주소 검증을 추가했다.
- 중앙 등록 직후 게시 계정을 보호 파일로 저장한 뒤 Edge에 전달한다. 저장 실패 재시도, 저장된 등록으로 전달 재시도, 등록 응답이 불확실할 때 목록 확인 전 중복 등록 방지를 구현했다.
- `python -m py_compile`과 `test_edge_pairing_identity` 세 시나리오를 통과했다. 기존 MAC 계약 테스트는 실행 환경에 PyYAML 의존성이 없어 시작하지 못했다. 현재 실행 환경에는 PyQt5가 없어 GUI 실행·화면 동작 검증을 하지 못했다.
- 설치 EXE와 실제 Pi의 운영 연결·영상은 대상 Windows/Pi 환경에서 별도 확인해야 한다.
