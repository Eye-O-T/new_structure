# GPID 3 → 2 통합 및 툼스톤 보존 검토

- 작성일: 2026-11-16 KST
- 범위: 코드·기존 DB 사본 검토와 메모리 DB 검증. 운영 DB·설정·실행 코드는 변경하지 않았다.
- 확정된 목표: 서로 다른 GPID의 코사인 거리 `d = 1 - s`가 기준 이하이면 통합한다. 예시에서는 3번의 연결을 2번으로 옮기고, 3번은 재사용하지 않는 툼스톤으로 남긴다.

## 1. 적절성 및 판단 기준

**조건부로 적절하다.** 최초 판정에서 나뉜 동일인을 후속 관측으로 통합할 수 있고, 툼스톤은 과거 ID의 의미와 이동 경로를 보존한다. 다만 거리 하나만으로 GPID 전체를 자동 통합하는 것은 권장하지 않는다. 한 GPID에는 여러 track과 과거 이벤트가 속할 수 있어 오통합의 영향이 최초 track 배정보다 크다.

현재 `resolve_identity`는 같은 특징 공간·차원의 표본에 대해 GPID별 최대 코사인 유사도를 구한다. 같은 규칙을 거리로 표현하면 GPID 사이의 표본 쌍 중 최소 거리다. 현재 유사도 기준 `s >= 0.6`은 `d <= 0.4`와 동치이며 경계값을 포함한다. 이는 **수식상 환산**이고, 0.4가 GPID 전체의 자동 통합에 적합하다는 정확도 검증은 아니다. 코사인 거리의 수학적 범위는 0~2이며 동일인 확률이 아니다.

권장 조건은 다음과 같다.

1. 비교한 표본의 `space_id`와 차원이 같고, 유효한 정규화 벡터여야 한다. 모델이 다르면 직접 비교하지 않는다.
2. 후보 생성에는 현재의 관측시각 기준 1,800초 범위를 유지한다. 표본이 만료되면 원본 crop의 동일 모델 재추론 등으로 근거를 새로 확보한다.
3. 통합될 **두 GPID에 속한 전체 track 사이**에 동일 카메라의 관측 구간 중첩이 없어야 한다. 현재 관측 하나에 대한 `conflicting_global_ids` 검사만으로 대체하지 않는다. 보관 만료로 근거가 부족하면 자동 판정을 보류한다.
4. 한 쌍의 낮은 거리로 우선 후보를 만들고, 자동 통합에는 서로 다른 시점의 독립 표본에서도 일치가 반복되는지 검증한다. 같은 crop의 재추론·재전송은 독립 근거로 세지 않는다. 반복 횟수와 통합용 거리 기준은 실제 동일인·타인 자료로 정한다.
5. 여러 GPID가 경쟁하거나, A-B 및 B-C의 일치만 있고 A-C 근거가 없으면 자동 연쇄 통합하지 않는다. 최종 그룹의 충돌과 근거를 다시 확인한다.

처음에는 후보만 기록하는 모드로 검증하고 확인된 후보를 통합한다. 자동화는 오통합·누락 결과를 검증한 뒤 활성화한다. 기존 최초 배정의 `IDENTITY_MATCH_MARGIN=0`을 이번 작업에서 임의로 변경할 필요는 없다.

## 2. 현재 구조와 실제 사례

기존 track은 `existing_track` 분기에서 기존 GPID를 그대로 반환한다. 현재는 이미 나뉜 GPID를 병합하거나 툼스톤으로 표시하는 기능이 없다. 따라서 margin 변경이나 작업 재실행만으로 3번이 2번으로 합쳐지지 않는다.

기존 분석 사본 `.review/gpid-investigation/ai_cctv_snapshot.db`를 읽기 전용으로 열고 메모리에 백업하여 확인했다. 사본의 이벤트 수는 234건, 최신 관측은 2026-11-16 20:43:01.353 KST이며 `quick_check=ok`다. 아래 값은 이 사본의 최신 gallery 표본끼리 계산한 결과로, 현재 운영 DB 상태나 최초 배정 당시 점수를 뜻하지 않는다.

| GPID 쌍 | 코사인 유사도 | 코사인 거리 | 거리 0.4 이하 |
|---|---:|---:|---|
| 1 ↔ 2 | 0.495644105 | 0.504355895 | 아니오 |
| 1 ↔ 3 | 0.510531795 | 0.489468205 | 아니오 |
| 2 ↔ 3 | 0.706081864 | 0.293918136 | 예 |

사본에서 2번은 `local-camera`, 3번은 `cam-001`의 track 하나씩에 연결되어 있고, 두 그룹 사이에 동일 카메라 관측 중첩은 없다. 따라서 **2·3은 통합 검토 후보로 적합**하다. 이전 조사 기록에는 사용자가 같은 사람임을 확인했다는 전제도 있다. 현재 점수 한 쌍만으로 일반적인 자동 통합 정확도를 주장하지 않는다.

기존 참조 컬럼만 메모리 DB에서 `3 → 2`로 바꾸고 검증한 결과는 다음과 같다.

| 테이블 | 이동 행 수 | 이동 후 2번 참조 수 |
|---|---:|---:|
| `events` | 6 | 14 |
| `person_identity_links` | 1 | 2 |
| `identity_gallery` | 1 | 2 |

각 테이블의 전체 행 수가 유지되고 3번 참조가 0건이 되며, `global_persons.id=3`은 남는 것을 확인했다. 외래 키 검사도 통과했고 rollback 후 3번 이벤트 6건이 복원됐다. 이는 기존 컬럼의 이동 가능성 검증이며 툼스톤 스키마·동시 실행·화면 갱신 구현을 검증한 것은 아니다.

## 3. 툼스톤과 데이터 갱신 방법

`global_persons`에 nullable `merged_into_id`를 추가하는 방식이 단순하다. 활성 ID는 NULL, 통합된 3번은 2를 저장한다. `merged_into_id`는 존재하는 GPID를 참조하고 자기 자신을 가리키지 못하게 한다. 순환 통합은 애플리케이션에서도 막는다. 별도 상태 컬럼 없이 이 값으로 활성 여부를 구분할 수 있다.

| 대상 | 통합 후 상태 |
|---|---|
| `global_persons.id=2` | 활성, `merged_into_id=NULL` |
| `global_persons.id=3` | 툼스톤, `merged_into_id=2`, 원래 생성 정보 보존 |
| `events.global_person_id=3` | 모든 해당 이벤트를 2로 갱신. `analysis_completed`도 포함 |
| `person_identity_links.global_person_id=3` | 2로 갱신. 카메라·세션·로컬 person ID는 유지 |
| `identity_gallery.global_person_id=3` | 2로 갱신. 양쪽 표본과 track 키는 유지 |
| `person_track_presence` | GPID 컬럼이 없으므로 관측 구간을 그대로 보존 |

3번 행을 삭제하거나 빈 행을 다시 생성하지 않는다. 신규 ID는 기존 AUTOINCREMENT 발급 경로를 유지하고 툼스톤을 후보에서 제외한다. 기존 1·2·3만 있다면 다음 신규 ID는 4이며, 다른 ID가 이미 발급됐다면 그 이후 번호다. 3번을 다시 활성 인물에게 할당하지 않는다.

후속 요청에서 과거 3번을 접하면 대표 ID 2로 해석한다. 향후 2번이 다른 ID로 통합되는 경우에도 최종 활성 대표를 찾도록 하고 순환을 차단한다. 통합 방향은 이번 사례의 `source=3, target=2`처럼 명시하며, 번호가 작다는 이유만으로 동일인이라고 판단하지 않는다.

통합 이력에는 source·target·시각·판정 근거·거리 기준·표본 식별 정보·작업 식별자와 **원래 3번에 속했던 행의 키**를 저장한다. 벡터는 기존 비공개 저장 원칙을 유지한다. 기존 이벤트의 최초 `new/matched` 판정 metadata는 당시 기록이므로 덮어쓰지 않는다.

## 4. 실행과 동시성

1. 최신 운영 DB의 일관된 백업과 후보 보고서를 만든다. 후보 보고서에는 점수, 전체 track의 충돌 검사, 영향 행 수를 담는다. 사본에서 얻은 6·1·1건을 운영 적용 수치로 고정하지 않는다.
2. 비싼 벡터 비교는 쓰기 잠금 밖에서 수행한다. 실제 적용은 Data의 기존 `Database.transaction()`에 따른 `BEGIN IMMEDIATE` 안에서 처리한다.
3. 잠금을 얻은 뒤 source·target의 최신 대표, 표본의 변경 여부·유효기간, 전체 track 충돌, 영향 행을 다시 확인한다. 근거가 달라졌으면 재평가한다.
4. 같은 트랜잭션에서 통합 이력과 원래 행 키를 기록하고, 세 참조 테이블을 갱신한 다음 3번에 `merged_into_id=2`를 저장한다. 활성 참조에 3번이 남지 않고 gallery·track 연결이 일치하는지 검사한 뒤 commit한다.
5. 동일 작업 재실행 시 이미 `3 → 2`이면 성공한 무변경으로 처리한다. 3번이 다른 대표로 이동했으면 오래된 제안을 그대로 실행하지 않고 다시 판단한다.
6. identity·analysis 완료 및 늦은 이벤트 저장은 트랜잭션 안에서 최신 track 연결과 대표 ID를 읽게 한다. 통합 전에 임대한 작업이 나중에 끝나도 3번 연결을 되살려서는 안 된다. 현재 gallery의 UPSERT가 GPID를 갱신하지 않는 점도 포함해 참조 일관성을 검증한다.

자동화할 때는 Data가 identity 완료 후 갱신된 표본을 중심으로 후보를 평가하도록 한다. 매 영상 프레임마다 전체 gallery의 모든 쌍을 비교하는 방식은 피한다. 현재 gallery는 특징 공간별 track의 최신 표본 하나를 저장하므로, 반복 관측 검증에는 필요한 최소한의 근거 기록을 별도로 남겨야 한다.

## 5. 화면 반영·배포·원복

실시간 객체 조회는 매번 `person_identity_links`를 결합하므로 통합 후 다음 정상 조회에서 2번을 반환할 수 있다. 반면 이벤트 증분 조회는 `id > after_event_id` 기준이어서 기존 행의 GPID 변경을 새 이벤트처럼 전달하지 않는다. 데스크톱의 5초 보완 조회도 GPID가 NULL인 완료 이벤트를 대상으로 한다. 이미 3번인 이벤트는 별도 갱신이 필요하다.

초기 수동 적용에서는 통합 후 관련 카메라의 이벤트 목록·열린 상세를 다시 조회한다. 자동 통합을 제공할 때는 통합 이력의 증가하는 변경 번호를 조회해 `source → target`을 전달하고, 클라이언트가 보유 이벤트와 열린 상세를 갱신하는 경로를 추가한다. 이를 인물 출현·분석 완료 이벤트로 위장하여 FCM이나 객체 작업을 만들지 않는다.

**배포 선행 조건:** `server/deployment/signature.py`는 마이그레이션 파일을 DB 계약 해시에 포함한다. 설치 GUI에는 계약 불일치 시 `reset_incompatible_deployment`를 호출하는 경로가 있다. 새 툼스톤·이력 스키마를 추가한 뒤 일반 설치 경로로 적용하면 기존 데이터를 초기화하는 경로에 들어갈 수 있다. 이번 변경에 한정된 데이터 보존 업그레이드 경로를 만들고 사본에서 검증해야 한다. 실제 마이그레이션과 검증을 마친 뒤 서명을 갱신하며, 서명만 먼저 바꿔 검사를 우회하지 않는다.

트랜잭션 중 실패는 전체 rollback한다. commit 후 오통합이 확인되면 자동 통합을 중단하고 이력의 원래 행 키로 교정한다. `WHERE global_person_id=2` 전체를 3으로 바꾸면 원래 2번의 이력까지 옮겨지므로 금지한다. 통합 후 새로 2번에 들어온 관측은 원래 어느 그룹인지 별도 판정이 필요하다. 설정 원복만으로 통합을 취소할 수 없다.

## 6. 권장 작업 순서와 완료 기준

| 순서 | 작업 | 검증 |
|---|---|---|
| 1 | 거리 기준·후보 보고서 확정 | 동치 경계, 특징 공간, 전체 track 충돌·근거 부족을 구분 |
| 2 | 툼스톤·이력 스키마와 데이터 보존 업그레이드 | 기존 이벤트·연결·표본·설정이 사본에서 보존됨 |
| 3 | Data의 원자적 통합 기능 | 3개 참조 갱신, 3번 툼스톤, 재실행 무변경, 중간 실패 rollback |
| 4 | 늦은 작업 및 조회 경로 보완 | 통합 후 작업 완료로 3번이 부활하지 않으며 UI의 3이 2로 갱신됨 |
| 5 | 확인된 `3 → 2` 후보 적용 | 최신 영향 행 수 일치, 3번 활성 참조 0, 3번 재사용 없음 |
| 6 | 후보 기록 모드 후 자동화 | 독립 관측·타인 자료·경쟁 후보·연쇄 통합을 검증한 기준 사용 |

필수 검증에는 거리 기준의 미만·동일·초과, 다른 모델, 동일 카메라 구간 중첩, 표본 만료, source/target 부재, 자기 통합·순환, 동시 `3 → 2` 요청, 통합과 identity/analysis 완료 경합, 후속 신규 ID 발급을 포함한다. GPID 논리 참조 세 컬럼에는 현재 SQL 외래 키가 없으므로 `foreign_key_check`에 더해 명시적인 누락·불일치 조회가 필요하다.

권장 적용은 **확인된 3번을 2번으로 원자적으로 옮기고 3번 툼스톤을 보존하는 기능부터 구현한 뒤, 검증된 거리·반복 관측 조건으로 자동화를 확장**하는 순서다.
