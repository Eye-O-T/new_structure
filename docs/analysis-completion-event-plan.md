# 분석 완료 이벤트 및 결과 표시 분리 계획서

- 작성일: 2026-11-06, KST
- 조사 기준: 저장소 `4dd8d14`
- 대상: Data의 객체 분석 완료 처리, Windows 관제 화면의 이벤트 타임라인·상세 창
- 산출물: 조사 및 구현 계획. 이번 작업에서는 제품 코드를 변경하지 않는다.

## 1. 목표와 화면 동작

analysis 컨테이너의 분석이 성공적으로 끝나면 **별도의 분석 완료 이벤트를 자동 생성**한다. 관제 화면은 해당 이벤트를 다음처럼 표시한다.

```text
2026-11-06 15:00:00 KST  pid:7 gpid:null 출현
2026-11-06 15:00:03 KST  pid:7/gpid:42 분석 완료 (성별: Male, 연령: 16-30)
```

전역 ID 판정이 늦으면 완료 항목은 `pid:7/gpid:null 분석 완료 (성별: Male, 연령: 16-30)`(속성 미제공 시 `pid:7/gpid:null 분석 완료`)로 표시한다. analysis 완료 여부는 gpid 판정과 독립적이다.

| 사용자 동작·상태 | 변경 후 동작 |
| --- | --- |
| 사람 등장 | 기존 등장 이벤트 생성·표시 |
| analysis 대기·처리 중 | 분석 완료 이벤트 없음 |
| analysis 성공 완료 | `pid:…/gpid:… 분석 완료` 항목 자동 추가 |
| 분석 완료 항목 클릭 | 해당 분석 결과·pid·gpid·완료 시각 표시 |
| 원래 등장 항목 클릭 | 기존 이벤트 정보·이미지·녹화 표시. 분석 결과 영역과 분석 새로고침 버튼은 표시하지 않음 |
| analysis 실패·재시도·미설정 | 성공을 뜻하는 분석 완료 항목을 생성하지 않음 |

새 완료 항목을 클릭하면 분석 결과를 보는 흐름으로 해석한다. 이 문서는 현재 관제 화면의 동작 변경을 대상으로 하며, 모바일의 분석 상세 기능 추가나 FCM 발송은 포함하지 않는다.

## 2. 현행 코드와 변경이 필요한 이유

1. [Data objects.py:105](../server/services/data/app/database/repositories/objects.py#L105)는 등장 관측 이벤트에 identity·analysis 작업을 함께 만든다. gpid 판정 완료 조건은 없다.
2. [Data objects.py:162](../server/services/data/app/database/repositories/objects.py#L162)의 `complete_object_job()`은 유효한 임대의 결과를 원래 이벤트의 `metadata.analysis`에 저장하고 작업 상태를 바꾼다. 새 이벤트 행은 만들지 않는다.
3. [video_worker.py:233](../server/desktop/admin/video_worker.py#L233)는 최초 최근 이벤트 조회 뒤 `after_event_id`로 새로운 이벤트를 수집한다. 기존 등장 이벤트의 metadata 갱신만으로 타임라인 항목이 추가되지는 않는다.
4. [application.py:1230](../server/desktop/admin/application.py#L1230)는 이벤트 종류와 관계없이 상세 창에 분석 영역과 새로고침 버튼을 만든다. 그 안의 `render_analysis()`가 `metadata.analysis`를 표시한다.

따라서 분석 완료를 타임라인에 자동 표시하려면 **서버에 새 이벤트를 저장하는 처리**와 **상세 창에서 이벤트 종류에 따라 결과를 표시하는 처리**를 함께 변경해야 한다.

## 3. 완료 이벤트의 정의

새 이벤트 유형은 `analysis_completed`로 한다. 단위는 **하나의 원본 등장 이벤트에 연결된 analysis 작업 1건**이다. 같은 숫자의 pid라도 카메라·추적 세션·원본 이벤트가 다르면 별도 작업으로 취급한다.

| 필드 | 저장 규칙 |
| --- | --- |
| `event_type` | `analysis_completed` |
| `camera_id` | 원본 등장 이벤트의 카메라 |
| `person_id` | 원본 이벤트의 pid |
| `global_person_id` | 완료 처리 시점에 Data에 저장된 gpid. 미판정이면 DB null |
| `occurred_at` | Data가 analysis 성공 결과를 수락하는 시각, UTC |
| `created_at` | 새 이벤트 저장 시각, UTC |
| `source_event_id` | 서버 내부에서 원본 등장 이벤트 ID를 바탕으로 생성한 결정적 UUID의 32자리 hex |
| `metadata.appearance_event_id` | 원본 등장 이벤트 ID |
| `metadata.appearance_occurred_at` | 원래 사람이 등장한 시각 |
| `metadata.analysis_job_id` | 완료한 analysis 작업 ID. 이력이 정리된 과거 자료를 복원할 때만 없을 수 있음 |
| `metadata.tracking_session_id` | 원본 추적 세션 ID |
| `metadata.analysis` | 완료 상태·완료 시각·분석 결과의 사본 |

분석 결과는 기존 `metadata.analysis.result`의 구조를 보존한다. 완료 이벤트 자체에 결과를 저장하므로 원본 등장 이벤트가 보존기간 만료로 삭제되어도 완료 항목의 결과를 조회할 수 있다. 대용량 이미지 파일이나 새 크롭은 만들지 않는다.

완료 항목에는 분석 결과를 표시하고, 기존 이미지·현장 녹화는 원본 등장 이벤트에서 조회한다. 분석 완료 시각의 다른 녹화를 해당 인물의 분석 근거로 연결하지 않는다.

## 4. Data 변경 계획

### 4.1 성공 결과와 완료 이벤트를 한 번에 저장

`complete_object_job()`의 기존 트랜잭션 안에서 다음을 수행한다.

1. 현재 `running` 작업의 임대 ID·유효기간을 검증한다.
2. 분석 결과 형식을 검증하고 원본 이벤트 metadata와 작업 상태를 갱신한다.
3. `stage == "analysis"`이고 수락할 결과가 `outcome == "complete"`일 때만 `analysis_completed`를 생성한다.
4. 모든 변경을 함께 커밋한다. 이벤트 삽입이 실패하면 결과·작업 상태 갱신도 함께 취소한다.

완료 이벤트 삽입은 **기존 DB 연결을 인자로 받는 작은 내부 함수**로 구현한다. `create_event()`는 별도 쓰기 트랜잭션을 열기 때문에 이 안에서 그대로 호출하지 않는다. 새 완료 이벤트에 identity·analysis 작업을 다시 만들거나, 사람 등장·퇴장 관측 구간을 추가하거나, FCM 발송 작업을 만들지 않는다.

이 시점의 gpid는 analysis 컨테이너가 보낸 값으로 정하지 않고 원본 이벤트와 Data의 인물 연결에서 읽는다. analysis 컨테이너가 gpid를 지정하지 못하는 기존 검증은 유지한다.

### 4.2 중복 생성 방지

- 결정적 이벤트 키는 고정된 UUID namespace와 원본 등장 이벤트 ID로 만든다. 같은 원본 analysis 작업의 완료를 재전송해도 키가 같다.
- 기존 [007_identity_gallery.sql](../server/services/data/app/database/migrations/007_identity_gallery.sql)의 `(camera_id, source_event_id)` 고유 인덱스를 재사용한다.
- 현재의 `running + lease_id + lease_until` 검사와 쓰기 트랜잭션 직렬화를 유지한다. 이미 완료된 작업의 재보고가 새 항목을 만들지 않게 한다.
- `retry`, `failed`, `unconfigured`, 만료·이전 임대의 결과는 완료 이벤트를 만들지 않는다. 실패 뒤 재시도에서 실제 성공한 경우에는 그 성공에 대해 1건 생성한다.
- 같은 pid가 여러 등장 이벤트를 가진 경우 각 작업의 완료 항목은 각각 생성한다. pid 숫자만으로 중복을 제거하지 않는다.

새 테이블·새 컬럼·DB 초기화 없이 기존 이벤트와 metadata 확장으로 구현한다.

### 4.3 gpid 판정이 늦게 끝나는 경우

분석 완료 이벤트에도 최상위 `camera_id`, `person_id`와 `metadata.tracking_session_id`를 저장한다. 그러면 기존 identity 완료 처리의 같은 카메라·세션·pid 대상 이벤트 갱신에 포함할 수 있다. identity가 먼저 완료된 경우에는 새 항목 생성 시 해당 값을 바로 넣는다.

관제 화면은 gpid가 null인 완료 항목이 현재 보관 중인 목록에 있으면 **5초 간격으로 카메라별 최근 30건을 기존 API로 재조회**한다. 현재 목록에 이미 있는 이벤트 ID의 ID 정보만 갱신하며 신규 이벤트 수집 watermark는 이 재조회로 변경하지 않는다. gpid가 채워지거나 해당 항목이 목록에서 빠지면 이 보완 조회를 중단한다.

동일 이벤트 ID 수신 시 기존 카드를 중복 생성하지 않고 해당 이벤트를 갱신하도록 `_on_event()`를 보완한다. 이 방식은 사람이 이미 퇴장하여 실시간 좌표 목록에 없어도 gpid 갱신을 반영할 수 있다.

### 4.4 이미지·녹화·보존 처리

- 완료 이벤트는 분석 결과 사본을 가지며 원본의 이미지 경로를 복제하지 않는다. 등장 이벤트의 기존 미디어 접근 방식은 유지한다.
- 자동 녹화 연결과 녹화 연결 복구에서 `analysis_completed`를 제외한다. 완료 시각을 현장 관측 시각으로 잘못 사용하지 않게 한다.
- 완료 이벤트의 metadata 원본 ID는 이력 참조로 사용하고, 원본 이벤트 삭제에 따른 연쇄 삭제는 만들지 않는다.
- 기존 이벤트 보존정책을 적용한다. 완료 이벤트에 객체 작업이 재생성되지 않고, 그 결과 보존기간 이후 정리가 막히지 않는지 확인한다.

## 5. 관제 화면 변경 계획

### 5.1 타임라인

- `legacy_event()`가 새 유형과 원래 pid·gpid 및 분석 결과의 성별(`gender`)·연령(`age`)을 전달하도록 한다. 현재의 이벤트 ID 기반 수집을 재사용한다.
- 카드 렌더러에 `analysis_completed` 분기를 추가하여 **`pid:7/gpid:42 분석 완료 (성별: Male, 연령: 16-30)`**(속성 미제공 시 **`pid:7/gpid:42 분석 완료`** 또는 **`pid:7/gpid:null 분석 완료`**)를 표시한다.
- 완료 이벤트의 시각을 KST로 표시한다. 기존 발생 시각·이벤트 ID 정렬에 따라 완료 항목이 제 위치에 추가된다.
- 분석 완료 항목은 등장·퇴장 횟수에 포함하지 않는다. 기존 최근 30건 제한·카메라 선택·스크롤 동작은 유지한다.
- 완료 이벤트가 DB에 커밋된 뒤 기존 0.5초 이벤트 조회 주기의 다음 성공 응답부터 표시한다. 추론시간과 네트워크·서버 응답 지연은 별도로 존재하므로 표시까지의 절대 시간을 보장하지 않는다.

### 5.2 등장 이벤트 상세

- `person_appeared` 상세에는 분석 영역의 제목·상태·분석 결과·분석 결과 새로고침 버튼을 생성하지 않는다.
- 이전에 저장된 등장 이벤트도 같은 규칙을 적용한다. 서버에 기존 분석 metadata가 남아 있어도 해당 상세 화면에는 렌더링하지 않는다.
- 원래 pid·gpid·등장 시각·이미지·관련 녹화는 기존처럼 표시한다.

### 5.3 분석 완료 이벤트 상세

- `event_type == "analysis_completed"`일 때만 분석 결과 영역을 표시한다.
- 완료 이벤트에 저장된 분석 결과를 조회하여 pid·gpid·완료 시각과 함께 표시한다. 원본 등장 이벤트 ID와 등장 시각을 함께 제공해 어느 관측의 분석인지 확인할 수 있게 한다.
- 이미 완료된 결과를 대상으로 하므로 분석 시작이나 완료 대기를 유발하지 않는다. 기존의 분석 대기용 새로고침 버튼은 필요하지 않다.
- 결과 렌더러를 옮길 때 실제 분석기의 저장 구조를 확인한다. 기본 분석기의 `clothing_colors`·`image.quality`와 PAR 분석기의 `attributes` 등 저장된 지원 필드가 결과 창에서 누락되지 않게 한다. 제공되지 않은 값을 생성하지 않는다.

분석 상태와 결과를 원래 이벤트 metadata에 저장하는 기존 내부 흐름은 유지한다. 요청한 변경은 관제 화면에서 결과를 여는 위치와 타임라인 완료 항목의 생성이다.

## 6. 기존 분석 이력 전환

등장 이벤트에서 결과를 숨긴 뒤 과거 분석 결과를 열 수 없게 되는 상황을 막기 위해 **기존 성공 분석의 완료 이벤트를 한 번 보완 생성**한다.

- `person_appeared` 중 `metadata.analysis.status == "complete"`이고 아직 대응 완료 이벤트가 없는 자료를 대상으로 한다. 작업 이력이 남아 있으면 함께 검증한다.
- 새 작업 완료와 같은 이벤트 키·저장 함수를 사용하여 배포·재실행 때 중복을 막는다. 작업 이력이 이미 정리되어도 원본 이벤트 ID로 같은 키를 만들 수 있다.
- 원래 분석 `updated_at`을 완료 시각으로 사용한다. 그 값이 없거나 잘못되었으면 현재 시각으로 꾸미지 않고 해당 건을 보류·기록한다.
- 최대 100건 단위의 트랜잭션으로 처리하고, 분석 재실행이나 FCM 발송은 하지 않는다.
- 보완 생성으로 새 ID가 생긴 과거 이벤트도 기존 타임라인은 `occurred_at`으로 정렬한다. 전체 이력이 현재 시각의 새 완료로 보이지 않게 한다.
- Data의 보완 생성 확인 후 새 관제 화면을 배포한다. 이전 등장 이벤트와 그 분석 metadata를 삭제하지 않는다.

| 7 | 관련 Data·External·데스크톱 테스트 | 아래 검증 표의 회귀 검사 |
| 8 | Analysis·Data·Desktop README, API 설명 원본·`docs/openapi.yaml` | 완료 유형과 결과 조회 위치·metadata 의미·보완 생성 절차 기록 |

기존 `event_type`·metadata는 확장을 허용하므로 새 REST 경로나 새 필수 응답 필드를 추가하지 않는다. External의 기존 카메라 권한 검사와 metadata 미디어 경로 제거 규칙을 유지한다. Analysis 모델·추론 코드와 Preprocessing의 pid 생성·크롭 선택 조건은 변경 대상이 아니다.

새 유형은 공통 이벤트 API에서 모바일에도 조회될 수 있으므로 알 수 없는 유형 처리 호환성을 확인한다. 모바일 분석 상세 구현과 별도 알림 발송은 이번 범위에 넣지 않는다.

## 8. 검증 기준

| 시나리오 | 통과 기준 |
| --- | --- |
| analysis 정상 성공 | 결과 저장·작업 완료·완료 이벤트 1건이 함께 커밋됨 |
| 이벤트 삽입 중 DB 오류 | 부분 완료 없이 전체 롤백, 재보고 성공 시 항목 1건 |
| 동일 완료 결과 재전송·동시 보고 | 항목 중복 없음 |
| 이전·만료 임대 결과 | 완료 항목 생성 없음 |
| failed·retry·unconfigured | 분석 완료 표시 없음 |
| 실패 후 재시도 성공 | 성공 시 완료 항목 1건 |
| 동일 pid가 다른 카메라·세션·등장 이벤트에 존재 | 정확한 작업과 연결되며 오연결·잘못된 중복 제거 없음 |
| identity가 먼저 완료 | 최초 항목부터 확정 gpid 표시 |
| analysis가 먼저 완료 | `gpid:null`로 생성, identity 완료 후 같은 항목의 gpid 갱신, 중복 카드 없음 |
| 사람이 퇴장한 뒤 identity 완료 | 실시간 좌표 유무와 관계없이 보완 조회로 gpid 갱신 |
| 등장 이벤트 상세 | 분석 결과·상태·분석 새로고침 버튼이 없고 기존 미디어는 조회 가능 |
| 완료 이벤트 상세 | 해당 작업의 실제 결과와 완료 시각 표시. 다른 사람·다른 세션의 결과 혼입 없음 |
| 완료 이벤트 처리 | 객체 작업·FCM·등장/퇴장 통계가 추가로 생성되지 않음 |
| 완료 시각과 등장 시각이 크게 다름 | 타임라인은 완료 시각으로 정렬, 해당 시각의 무관한 현장 녹화를 연결하지 않음 |
| 재접속·서버/관제 화면 재시작 | 저장된 완료 항목 조회, 기존 이벤트 수집 watermark로 누락·중복 방지 |
| 과거 이력 보완 생성·중단 후 재실행 | 원래 완료 시각 보존, 중복 없음, 결과를 새 항목에서 조회 가능 |
| 원본 등장 이벤트 보존기간 만료 | 완료 이벤트가 남아 있다면 결과 자체는 계속 조회 가능 |
| API 권한·모바일 호환 | 허용된 카메라의 이벤트만 조회, 새 유형으로 기존 클라이언트가 실패하지 않음 |

Data 트랜잭션·작업 임대·이벤트 수집·데스크톱 상세 분기 테스트를 먼저 수행한다. 이후 실제 컨테이너에서 사람 등장 → analysis 완료 → 새 카드 자동 표시 → 완료 상세 결과 확인 → 기존 등장 상세에서 결과 미표시까지 확인한다.

## 9. 완료·배포 기준

신규 성공 분석과 기존 성공 분석 이력이 모두 완료 항목을 통해 조회되고, 등장 상세에는 분석 결과가 나타나지 않으며, gpid 판정 순서·재시도·재시작 상황에서 중복과 누락이 없어야 한다.

Data를 갱신하고 기존 이력 보완 생성·검증을 마친 뒤 관제 화면을 갱신한다. 독립적인 DB 마이그레이션이나 데이터 초기화는 필요하지 않다. 문제가 생기면 이전 Data·관제 화면으로 복귀할 수 있도록 배포 버전을 기록하고, 생성된 완료 이벤트와 기존 분석 metadata는 보존한다.

이번 작업의 완료 범위는 이 계획서 작성까지다. 위 구현·보완 생성·검증·배포는 아직 수행하지 않았다.
