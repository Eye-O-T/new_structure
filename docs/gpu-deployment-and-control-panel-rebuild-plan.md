# GPU 배포 적용 및 서버 제어판 재빌드 개선 작업 계획서

- 작성일: 2026-11-10 KST
- 상태: 계획 작성. 이번 작업에서는 문서만 추가한다.
- 선행 작업: [GPU 실행 정책 수정 계획](gpu-execution-policy-fix-plan.md)에 따라 작성된 현재 작업 트리의 변경 사항

## 1. 목적과 범위

`compose.env`의 GPU 설정이 실제 GPU 이미지·컨테이너 자원·모델 추론에 반영되도록 한다. 서버 제어판의 ‘빌드 및 시작’은 기본 서비스와 현재 켜진 AI 서비스를 함께 갱신하도록 개선한다. 사용자가 꺼 둔 AI 서비스를 재빌드 과정에서 임의로 켜지 않는다.

이번 계획은 GPU 전환 배포와 제어판의 재빌드 대상 선정까지 포함한다. GPU 모드 전환은 기존 `compose.env`를 사용하고 별도의 장치 설정 화면은 추가하지 않는다. 첫 전환에서 요청한 캐시 없는 빌드는 두 AI 이미지에 한정한다. 전체 Docker 캐시·이미지·볼륨을 삭제하는 기능은 만들지 않는다.

기존 GPU 추론 코드는 이미 작업 트리에 수정되어 있으나 실제 GPU 이미지 빌드와 CUDA 추론 검증은 완료되지 않았다. 해당 변경을 검토·검증한 뒤 배포 대상으로 삼는다. 기존 수정 사항을 덮어쓰거나 구현 완료와 배포 완료를 혼동하지 않는다.

## 2. 확인된 기준선과 원인

아래 값은 2026-11-09에 수행한 직접 조회 기준이다. 실제 작업 직전에 재조회한다.

| 항목 | 확인 결과 |
| --- | --- |
| GPU | GTX 1650 with Max-Q Design, VRAM 4096 MiB |
| 운영 env | `PREPROCESSING_GPU=false`, `INFERENCE_DEVICE=auto`, `IDENTITY_DEVICE=auto`, `ANALYSIS_DEVICE` 미지정 |
| 컨테이너 GPU 할당 | Preprocessing·Analysis 모두 DeviceRequests 없음 |
| 감지 | PyTorch `2.8.0+cpu`, 실제 장치 `cpu` |
| 인물 식별 | OSNet 실제 장치 `cpu`, `CPUExecutionProvider` |
| Analysis | PyTorch `2.13.0+cpu`, CUDA 사용 불가, 분석 완료 이력 있음 |
| 영상 | `local-camera` 온라인, 감지 수행 확인 |
| 부가 경고 | 일부 조회에서 좌표 관측 나이 약 19초와 Preprocessing `degraded` 확인. 이후 첨부 진단에서는 `ready`도 관측됨 |

현재 ‘빌드 및 시작’은 [제어판](../server/desktop/server_manager/application.py)의 `start` 작업을 통해 [서비스 실행기](../server/operations/services.py)의 `docker compose up -d --build --wait`로 연결된다. [기본 Compose](../server/compose.yml)의 두 AI 서비스에는 `profiles: [ai]`가 지정되어 있으나 이 명령은 AI 서비스나 해당 프로필을 명시하지 않는다.

또한 [ComposeAdapter](../server/operations/compose.py)는 `PREPROCESSING_GPU=true`인 경우에만 [GPU override](../server/compose.gpu.yml)를 추가한다. 따라서 현재 GPU 모드가 꺼진 설정에서 재빌드하더라도 CUDA 이미지로 전환되지 않는다. 빌드 캐시 삭제만으로 이 설정·대상 선택 문제를 해결할 수 없다.

## 3. 적용할 동작

| 상황 | ‘빌드 및 시작’의 처리 |
| --- | --- |
| AI 서비스가 모두 꺼져 있음 | 기존 기본 서비스만 갱신. 두 AI 서비스는 켜지 않음 |
| Preprocessing만 켜져 있음 | 기본 서비스와 Preprocessing 갱신. Analysis는 꺼진 상태 유지 |
| 두 AI 서비스가 켜져 있음 | 기본 서비스와 두 AI 서비스를 모두 갱신 |
| AI 컨테이너가 실행 중이나 unhealthy/restarting | 갱신 대상에 포함하고 결과를 실패 또는 정상으로 명확히 표시 |
| AI 컨테이너가 stopped/exited이거나 없음 | 자동 활성화하지 않음. 기존 ‘켜기’ 동작으로 복구·활성화 |
| 서비스 상태 조회 실패 또는 다른 배포로 판단됨 | 대상 추측 없이 중단. 기존 배포 위치 검증 유지 |
| GPU 모드=true | 빌드·실행·조회에 동일한 env와 GPU override 적용 |
| GPU 모드=false | CPU 배포 유지. CUDA 장치 요청이 섞이면 변경 전에 설정 오류로 중단 |

기존 ‘재시작’ 버튼은 원칙적으로 프로세스 재시작을 유지하며 일반적인 소스 재빌드 수단으로 안내하지 않는다. 현재 존재하는 모델 마이그레이션 시 예외 동작은 별도로 회귀 검증한다.

## 4. 작업 순서와 검증

### 1단계: 기존 변경 검토와 배포 기준선 확보

1. Git diff와 기존 GPU 구현을 확인하고 이번 재빌드 동작 변경의 범위를 구분한다.
2. 현재 설치의 env 경로, 실제 Compose 프로젝트, Data 마운트, AI 컨테이너 상태·이미지 ID·이미지 태그·선택 장치·GPU 할당을 기록한다. 토큰·비밀번호·인증 URL은 출력하지 않는다.
3. 두 AI 서비스의 재시작 횟수, 준비 상태, 최근 처리 결과와 카메라 상태를 기록한다.
4. 실제 Docker 실행 경로와 테스트용 Python 환경을 확인한다. 이전 작업용 셸에서 Docker가 PATH에 없었던 사실을 호스트에 Docker가 없다는 뜻으로 취급하지 않는다.

**검증:** 선택한 저장 위치와 실제 컨테이너 마운트가 일치해야 한다. 현재 동작을 훼손하지 않는 읽기 전용 조회로 기준선을 확보한다.

### 2단계: ‘빌드 및 시작’의 AI 갱신 대상 보완

1. 서비스 변경 전에 선택한 프로젝트의 실제 컨테이너 상태를 조회해 현재 켜진 AI 서비스 목록을 확보한다. UI 버튼 문구나 오래된 메모리 상태만으로 판단하지 않는다.
2. 기존 기본 서비스와 켜진 AI 서비스를 함께 빌드·갱신 대상으로 지정한다. `--profile ai`를 무조건 활성화해 꺼진 서비스까지 시작하는 방식은 사용하지 않는다.
3. 기존 배포 위치 검증, 필요한 모델 검사, 제한 시간, 오류 처리 구조를 유지한다. 갱신할 AI 서비스에 필요한 모델 검사를 적용한다.
4. Analysis만 실행 중이고 Preprocessing은 꺼진 등 의존 상태가 불일치하면 사용자에게 상태를 표시하고 일관된 복구 경로를 제공한다. 꺼진 서비스를 임의 활성화하는 동작을 추가하지 않는다.
5. 제어판의 진행·결과 출력에 이번 대상 서비스와 CPU/GPU 모드, 빌드 및 재생성 결과를 표시한다. Docker `healthy`만으로 GPU 사용 완료를 표시하지 않는다.

**검증:** AI 모두 꺼짐/감지만 켜짐/둘 다 켜짐/unhealthy/restarting/중지/조회 실패 조합을 검사한다. 대상 서비스의 변경된 이미지가 실행 컨테이너에 적용되고, 제외한 서비스의 켜짐·꺼짐 상태가 보존되어야 한다.

### 3단계: 캐시 없는 첫 GPU 빌드 절차

1. 일반 ‘빌드 및 시작’은 기존 캐시 사용을 유지한다. 첫 GPU 전환에서는 같은 ComposeAdapter의 env·override 조합으로 `preprocessing`, `analysis`에 한정한 `build --no-cache`를 먼저 수행한다.
2. 별도의 범용 캐시 삭제 기능이나 `docker system prune`, `builder prune`, 볼륨 삭제는 사용하지 않는다.
3. 빌드가 끝나기 전까지 기존 운영 컨테이너를 유지한다. 빌드가 실패하면 교체 단계로 진행하지 않고 오류를 보고한다.
4. 기본 CPU 태그와 GPU 태그가 구분되고, 두 GPU 이미지에 CUDA wheel이 포함됐는지 확인한다. 빌드 중 런타임 사용자 import 검사를 유지한다.

**검증:** GPU Compose 해석 결과의 두 이미지 태그, 빌드 인자, GPU 요청을 확인한다. 새 이미지 ID와 설치 패키지의 CUDA 빌드 정보를 기록한다. 캐시 없는 빌드 자체를 CUDA 추론 성공으로 판정하지 않는다.

### 4단계: GPU 이미지 사전 실행 검증

1. 실제 모델은 읽기 전용으로 마운트하고 검증용 입력·출력 경로를 분리한 임시 GPU 컨테이너에서 모델을 각각 확인한다. 운영 작업 큐나 이벤트·gallery에 시험 결과를 기록하지 않는다.
2. PAR는 격리 실행기의 spawn 경로에서 초기화·warm-up·JPEG 추론을 수행한다. OSNet은 실제 ONNX 세션으로 추론하고 주요 모델 연산의 CUDA 실행을 검증한다. 감지는 고정 입력에서 실제 추론한다.
3. GPU 장치 index, PyTorch CUDA 지원, OSNet provider와 실제 연산 실행을 확인한다. 잘못된 index·GPU 미할당·초기화 실패에서 CPU 성공으로 전환되지 않는지 검사한다.
4. 세 모델을 함께 실행해 4GB VRAM에서 동시 실행, 준비 시간, 메모리 부족 및 프로세스 종료 여부를 확인한다. 임의 CPU 전환이나 모델 교체로 검증 실패를 숨기지 않는다.

**검증:** 각 모델의 실제 CUDA 추론이 성공하고, 동시 실행에서 VRAM 부족이 없어야 한다. 실패 시 운영 전환을 보류하고 필요한 자원·동시 실행 제약을 기록한다.

### 5단계: 운영 GPU 설정 적용과 AI 컨테이너 교체

1. 현재 `compose.env`를 접근 권한이 제한된 위치에 백업한다. 기존 토큰·저장 경로·모델 경로와 사용자별 CPU 예외를 기록한다.
2. 이번 전환의 선택값은 다음과 같이 적용한다.

   ```dotenv
   PREPROCESSING_GPU=true
   INFERENCE_DEVICE=cuda:0
   IDENTITY_DEVICE=cuda:0
   ANALYSIS_DEVICE=cuda:0
   ```

3. 실제 Compose 해석 결과에서 Preprocessing·Analysis의 GPU 이미지와 `gpus` 요청, 세 장치 값이 일치하는지 확인한다.
4. 선행 변경의 계약 서명 마이그레이션을 검증한다. 알려진 이전 배포이고 DB·도메인 계약이 같은 경우에만 비파괴 갱신한다. 서명 오류를 해결하기 위해 DB·시크릿을 초기화하지 않는다.
5. 사전 검증한 GPU 이미지로 기존에 켜진 두 AI 서비스를 재생성한다. 기존 카메라 등록·모델·이벤트·인증 정보는 유지한다. 새 컨테이너의 실제 이미지 ID와 GPU 할당을 확인한다.
6. 제어판에서 변경된 실행기를 확인할 수 있도록 앱 코드 로딩 상태도 확인한다. 제어판 프로세스 재실행이 필요하면 컨테이너 중지와 구분해 처리한다.

**검증:** 두 AI 컨테이너에 GPU DeviceRequests가 있고, 세 모델의 요청·실행 장치가 모두 `cuda:0`이어야 한다. OSNet은 CUDA provider에서 실제 추론해야 하며 PAR와 감지는 CUDA 텐서·커널을 사용해야 한다.

### 6단계: 실제 카메라 인수와 결과 기록

1. 최소 5분 동안 실제 카메라의 감지, 인물 식별, Analysis 결과 생성과 컨테이너 재시작 횟수, GPU 메모리를 관측한다.
2. GPU 사용률은 보조 지표로 사용한다. 낮은 순간 사용률만으로 실패로 보거나, CUDA 사용 가능 여부만으로 모델 추론 성공으로 보지 않는다.
3. readiness·doctor·관리자 진단의 모델별 장치 표시가 직접 조회 결과와 일치하는지 확인한다. 감지 워커가 없으면 실제 영상 감지는 미검증으로 남긴다.
4. 감지 지연, 좌표 갱신 관측 나이, identity·analysis 처리 지연을 기록한다. 좌표 stale로 `degraded`가 반복되면 GPU 전환 결과와 별도 장애로 구분한다.
5. `pid:n, gpid:null` 객체의 출현·박스, GPID 후속 반영과 PAR 결과 표시를 확인한다. GPU 활성화만으로 표시 문제가 해결됐다고 판정하지 않는다.

**검증:** CPU 기준선과 비교해 감지 추론 p95 1초 이하, 사용자 좌표 API 관측 나이 p95 2초 이하를 목표로 확인한다. 미달 항목은 측정값과 남은 원인을 기록한다. 기존 좌표 만료 정책이나 촬영 시각을 바꿔 결과를 정상처럼 보이게 하지 않는다.

## 5. 예상 변경 파일과 검사

| 대상 | 작업 |
| --- | --- |
| `server/operations/services.py` | 실행 중 AI 서비스 확인, 빌드·갱신 대상 포함, 실패·결과 보고 |
| `server/operations/compose.py` | 공통 env·GPU override 조합 사용, 필요 시 대상 지정 빌드 호출 지원 |
| `server/desktop/server_manager/application.py` | 빌드 대상·모드·결과 표시 및 버튼 동작 설명 |
| `server/tests/test_operations_compose.py`, 서비스 실행 관련 테스트 | 활성 AI 포함, 비활성 서비스 보존, 오류 시 교체 중단 검증 |
| 기존 GPU 정책·PAR·OSNet·doctor·서명 테스트 | 선행 구현의 CPU 회귀 및 CUDA 실패 정책 검증 |
| `docs/operations.md`, `docs/deployment-guide.md` | 버튼 범위, GPU 적용, 캐시 없는 AI 빌드, 확인·복원 절차 설명 |
| 운영 `compose.env` | 사전 검증 후 GPU 설정 적용. 작업 트리 소스 변경과 구분 |

기존 테스트를 우선 확장한다. 상태 조회 결과를 바탕으로 올바른 서비스만 명령 대상이 되는지 검증하고, 단순 문자열 복제 테스트로 실제 컨테이너·GPU 인수를 대체하지 않는다. GPU 지원을 모의한 단위 테스트와 실제 CUDA 검증 결과를 따로 기록한다.

## 6. 완료 기준

- ‘빌드 및 시작’이 기본 서비스와 현재 켜진 AI 서비스를 함께 갱신하고 꺼진 서비스는 유지한다.
- GPU 설정이 빌드부터 운영 컨테이너까지 동일하게 적용되며, 세 모델 모두 실제 CUDA 추론에 성공한다.
- 첫 GPU 전환에서 필요한 두 이미지만 캐시 없이 빌드하고 전체 캐시·이미지·볼륨 삭제를 수행하지 않는다.
- CPU 설치와 모델별 명시적 CPU 예외, 기존 켜기·끄기·재시작 동작에 회귀가 없다.
- 빌드·교체·실제 추론 성공을 구분해서 보고하고 GPU 요청 실패를 정상으로 표시하지 않는다.
- 운영 설정·DB·모델·인증·이벤트를 보존하고, 실제 카메라 검증 결과와 미완료 항목을 남긴다.

## 7. 실패 시 복원

빌드나 임시 컨테이너 검증 실패 시 운영 컨테이너를 교체하지 않는다. 교체 후 문제가 발생하면 기록해 둔 이전 이미지 ID·env와 AI 활성 상태로 두 AI 서비스를 복원한다. 복원 중 기존 이미지 태그가 변경됐는지도 확인해 실제 이전 이미지가 실행되도록 한다.

자동 CPU 폴백은 허용하지 않는다. 운영을 이전 CPU 배포로 복원한 경우에는 GPU 전환 실패와 CPU 복원 사실을 명확히 보고한다. 데이터 초기화, 모델 자동 교체, 다른 서비스·볼륨의 삭제는 복원 수단으로 사용하지 않는다.
