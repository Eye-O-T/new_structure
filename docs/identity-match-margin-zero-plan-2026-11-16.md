# 인물 식별 margin 0 적용 작업 계획서

- 작성일: 2026-11-16 KST
- 상태: 적용·기본 검증 완료, 신규 입력에서 판정 확인 대기
- 대상: 현재 설치 환경의 Data 서비스
- 목표: `IDENTITY_MATCH_MARGIN=0`으로 설정하여 1·2위 후보 점수 차이에 의한 매칭 거절을 해제한다.

## 1. 변경 내용과 범위

현재 운영 설정 파일 `C:\ProgramData\AI_CCTV\config\compose.env`의 아래 값 한 개를 변경한다.

```dotenv
# 변경 전
IDENTITY_MATCH_MARGIN=0.05

# 변경 후
IDENTITY_MATCH_MARGIN=0
```

현재 코드는 margin에 0을 허용한다. 후보가 점수 내림차순으로 정렬되므로 1위와 2위의 차이는 항상 0 이상이다. 따라서 margin 0은 점수 차이 조건을 항상 통과시키며, 최고 점수 기준 `IDENTITY_MATCH_THRESHOLD=0.6`으로 연결 여부를 결정한다. 최고 점수가 동일하면 현재 정렬 규칙에 따라 더 작은 gpid가 선택된다.

이번 작업은 현재 설치 환경의 설정 변경으로 한정한다. 새 설치 기본값이나 소스의 margin 기능을 삭제하는 작업은 포함하지 않는다. 같은 카메라의 동시 track 제외, 특징 공간·차원 검사, 후보 보존 기간, 기존 track의 ID 유지 정책은 현재 동작을 따른다. 설정 변경에는 Data 컨테이너 재생성이 필요하며 단순 `restart`만으로는 변경된 환경 변수가 반영되지 않는다.

## 2. 적용 근거와 예상 결과

11월 16일 이벤트 221에서 저장된 원본 crop을 같은 CUDA OSNet 모델로 재추론한 결과는 다음과 같다.

| 후보 | 유사도 |
|---|---:|
| gpid 2 | 0.601942873930674 |
| gpid 1 | 0.5696403351993586 |
| 1·2위 차이 | 0.0323025387313154 |

기존 margin 0.05에서는 차이 조건에 걸려 gpid 3이 발급됐다. margin 0으로 최초 판정을 다시 수행하면 최고 점수 0.601943이 기준 0.6 이상이므로 gpid 2에 연결될 것으로 예상한다.

이미 저장된 gpid 2·3은 이 변경만으로 병합되지 않는다. 변경은 이후 새 track의 식별 판정에 적용된다. 과거 이벤트 재처리와 ID 병합은 별도 작업이다.

## 3. 작업 절차와 단계별 검증

### 단계 1 — 변경 전 상태 확보

1. 운영 env의 margin·threshold를 다시 읽고 컨테이너의 실제 적용값과 비교한다.
2. 실행 중인 Data의 이미지 ID, Compose 파일 목록·적용 순서·프로젝트명, 저장소 mount를 기록한다. GPU 및 자원 제한 override가 있다면 같은 구성을 사용한다.
3. `compose.env`를 원래 접근 권한을 유지하는 운영 설정 백업 위치에 복사한다. 비밀값이 포함될 수 있으므로 백업 전체를 저장소에 추가하거나 출력하지 않는다.
4. Data readiness와 식별 작업 큐 상태를 기록한다.

검증: 원복할 설정과 재생성에 사용할 동일 이미지·배포 구성을 식별할 수 있어야 한다.

### 단계 2 — 운영 DB와 분리된 판정 검증

임시 DB와 저장된 원본 crop을 사용하여 실제 `resolve_identity` 경로를 검증한다. 운영 DB의 이벤트·연결·gallery는 수정하지 않는다. 최초 비교를 재현할 때는 후속 관측으로 덮어쓴 현재 gallery 대신 이벤트 215·218의 최초 crop 특징을 후보로 사용한다.

| 검증 항목 | 통과 기준 |
|---|---|
| 설정값 0 허용 | 설정 검증이 오류 없이 통과 |
| 실제 분리 사례 재현 | margin 0.05에서는 신규 ID, margin 0에서는 gpid 2에 `matched` |
| 1·2위 점수 동률 | 최고 점수 0.6 이상이면 현재 동률 정렬 규칙에 따라 연결 |
| 최고 점수 0.6 미만 | margin 0이어도 신규 ID 발급 |
| 후보 없음 | 신규 ID 발급 |
| 같은 카메라의 동시 track | 충돌하는 gpid가 여전히 후보에서 제외됨 |
| 기존 track | `existing_track`으로 기존 gpid 유지 |

검증: 위 항목이 통과하면 설정 적용 단계로 진행한다. 기능이 바뀌는 조건을 확인하는 데 필요한 검증으로 한정한다.

### 단계 3 — 운영 설정 적용

1. 운영 `compose.env`의 `IDENTITY_MATCH_MARGIN` 값만 `0`으로 바꾼다.
2. 현재와 같은 Compose 파일·override·env를 사용해 구성 검증을 수행한다. 전체 설정 출력 대신 대상 Data의 margin·threshold·이미지·mount만 확인한다.
3. 실제 적용될 margin이 0, threshold가 0.6이고 이미지·mount가 변경되지 않았는지 확인한다. 셸 환경 변수나 override가 env 파일을 덮어쓰지 않는지도 확인한다.
4. 동일 배포 구성을 사용해 **Data 서비스만** 재생성한다. Compose `up`에 `--no-deps --no-build --pull never --force-recreate -d data` 옵션을 사용하여 기존 이미지를 유지한다.

영향: Data 재생성 중 내부 API가 잠시 응답하지 않을 수 있다. 재생성 전후의 작업 상태와 완료 결과를 확인한다.

### 단계 4 — 적용 후 확인

1. Data 컨테이너 환경과 런타임 설정에서 margin 0·threshold 0.6을 확인한다.
2. 재생성 후 120초 이내에 Data의 `/health/ready`가 HTTP 200인지 확인한다.
3. 관련 서비스의 요청 실패가 계속되지 않는지, 식별 작업이 정상 완료되는지 확인한다.
4. 새로운 식별 결과가 발생하면 `metadata.identity.result.match.margin=0.0`인지 확인하고 gpid·판정·유사도를 기록한다. 기존 완료 이벤트의 metadata는 적용 여부를 확인하는 자료로 사용하지 않는다.
5. 새 입력이 없다면 설정 반영과 분리된 판정 검증 결과까지만 완료로 기록하고, 실제 신규 이벤트 확인은 미검증으로 남긴다.

## 4. 완료 기준

- 운영 env와 Data 런타임 설정에서 margin이 0이다.
- threshold는 0.6이고, 기존 이미지·저장소 mount가 유지된다.
- 분리된 임시 DB 검증에서 기존 문제 사례가 gpid 2로 연결되고, 낮은 점수·동시 track 제외 조건도 통과한다.
- Data readiness가 정상이며 재생성으로 인한 요청 실패가 지속되지 않는다.
- 새 이벤트의 margin 기록은 확인 여부를 명시한다. 이 변경으로 일반적인 동일인 정확도가 검증됐다고 간주하지 않는다.

## 5. 원복 조건과 절차

구성 검증 실패, 120초 이내 readiness 복구 실패, 지속되는 요청·식별 작업 오류, 확인된 타인 오연결이 발생하면 원인을 기록하고 이전 margin으로 되돌린다. margin을 0으로 낮추면 근소한 점수 차이도 허용하므로 서로 다른 사람을 잘못 연결할 가능성이 증가한다.

1. 백업을 기준으로 `IDENTITY_MATCH_MARGIN`만 이전 값 0.05로 복원한다. 다른 설정이 중간에 바뀌었다면 파일 전체를 덮어쓰지 않는다.
2. 같은 이미지·Compose 구성으로 Data만 다시 재생성한다.
3. 런타임 margin 0.05, readiness 정상과 작업 재개를 확인한다.

설정 원복은 margin 0 운영 중 생성된 gpid 연결을 되돌리지 않는다. 해당 연결의 교정이 필요하면 적용 시각과 이벤트 ID를 근거로 별도 처리한다. 이번 설정 작업에서는 운영 DB를 과거 사본으로 복원하지 않는다.

## 6. 예상 작업량과 결과물

- 운영 설정 변경·재생성·기본 적용 확인: 추가 약 **1,500~3,000토큰**.
- 실제 crop 재현과 위 경계 조건 검증까지 포함한 전체 실행: 추가 약 **3,000~5,000토큰**.
- 수치는 이 계획서 작성 이후의 추정치이며, 정확한 실측값이나 상한이 아니다.
- 결과물: 변경 전후 설정값, 적용 시각, 이미지 ID, 검증 결과, 새 이벤트 확인 여부를 담은 실행 기록.
