# 바운딩 박스 미표시 수정계획서

- 작성일: 2026-11-09, KST
- 대상: `local-camera`의 Preprocessing → Data → External → 관제 화면 좌표 경로
- 상태: 좌표 신선도 진단·회귀 검사를 구현했다. 활성 카메라에서의 성능 측정과 최종 통합 검증은 남아 있다.

## 실행 기록

- 2026-11-09 KST: Data의 3초 신선도 규칙을 공통 상수로 묶고, 수신 후에도 촬영 시각 기준 경과 시간을 측정해 좌표가 만료되면 Preprocessing readiness를 `degraded`로 표시하도록 했다. External 진단에 카메라별 경과 시간·만료 상태를 추가하고 전송 실패 로그에 카메라·제한된 오류 코드·소요 시간만 남긴다.
- Data의 신규 좌표 회귀 6개와 기존 이벤트·identity 저장 9개, Preprocessing·External 선택 회귀 16개가 통과했다. 격리 추론 진단 테스트의 오래된 `stage=load` 기대를 현재 오류 계약의 `stage=startup`에 맞췄다.
- 합성 1280×720 프레임의 짧은 실행에서 CPU 스레드 2·4가 1·8보다 빠른 결과가 나왔다. 각 조건 2회뿐이고 합성 프레임이므로 이 측정은 후보 비교에만 쓴다. 기본 4개 스레드를 변경하지 않았으며 목표 추론 p95를 검증한 것으로 간주하지 않는다.
- 런타임 DB에서 `local-camera`는 `enabled=1`, `stream_requested=0`, `recording_enabled=0`이고 저장 상태는 `offline`이었다. 현재 Preprocessing에 활성 worker가 없으므로 실제 영상 추론, Data PUT, 화면 표시의 5분 인수 검증은 수행할 수 없다. 카메라 요청 상태를 임의 변경하지 않는다.
- Preprocessing 및 External 이미지를 해당 Compose 서비스에만 빌드·반영했다. 두 컨테이너는 `healthy`; Preprocessing readiness는 Data·identity 준비 완료와 worker 0대 때문에 `idle`이다. External 진단의 모의 만료 응답은 `degraded`, `live_objects_stale=true`, 관측 나이 4.2초를 반환하는 것을 확인했다.

## 1. 원인과 수정 방향

**사람 감지는 성공하지만 CPU 추론에 약 4.5초가 걸려, 촬영 시각부터 3초인 좌표 유효기간을 넘긴 결과만 서버에 도착한다.** Data는 이를 `stale=true`, `objects=[]`로 반환하고 화면은 박스를 숨긴다. 간헐적인 좌표 전송 시간 초과도 지연을 악화시킨다.

기본 수정안은 **관측 시각과 3초 만료 기준을 보존하면서 추론·전송 지연을 줄이고, 좌표가 표시될 수 없는 상태를 진단에 반영**하는 것이다. 3초 기준을 수신 시각 기준으로 바꾸면 5초 이상 지난 위치도 새 좌표처럼 표시할 수 있다. 이번 수정은 실시간 영상 위에 현재 위치를 표시한다는 기존 동작을 전제로 한다.

만료 시간을 늘리거나 `observed_at`을 추론 완료 시각으로 덮어쓰는 방법은 채택하지 않는다. 성능 목표를 만족하지 못하면 복구 완료로 판정하지 않으며, 추가 병목 분석 결과에 따라 구현안을 보완한다. 지연된 좌표를 별도로 표시하는 기능은 이 계획의 범위에 포함하지 않는다.

## 2. 확인한 증거와 아직 확인할 사항

아래는 앞선 2026-11-09 11:35~11:38 KST 조사 결과다. 이번 문서 작성 중 새로 측정한 값은 아니다.

| 컨테이너·모델 | Preprocessing 실행 중, 카메라 `online`, `model_ready=true`, `model_timeouts=0` |
| 감지 | 사람 1명, 유효한 bbox와 약 0.75의 신뢰도가 DB에 저장됨 |

좌표가 만료되는 직접 원인은 확정했다. 반면 **CPU 추론이 느린 세부 원인**은 아직 확정하지 않았다. CPU 스레드 경합, Docker 자원 배분, 모델 실행, 호스트 저장장치 지연을 구분해 측정한다. CPU 사용률만으로 스레드 과다를 확정하거나, CUDA 불가 로그만으로 호스트에 GPU가 없다고 판단하지 않는다. HTTP 499는 클라이언트 연결 종료의 근거이며 DB 잠금만이 원인이라는 뜻은 아니다.

## 3. 수정 순서와 단계별 검증

### 1단계: 실패 재현과 기준선 확보

- 임시 DB와 고정 시계를 사용하는 회귀 테스트로 `observed_at`이 5초 전인 유효한 좌표를 저장한다. 수신 직후에도 `expired`가 되는 현재 동작을 재현한다.
- 미래 시각, 정확히 3초인 경계, 3초 초과, 무관측, 사람 없는 정상 결과, 비활성 카메라를 함께 검사한다. 만료 처리를 없애는 변경이 테스트를 통과하지 못하도록 한다.
- 대상 장비에서 준비 완료 후 5분간 추론·IPC·Data PUT·DB 잠금·트랜잭션·공개 좌표 GET 지연과 `stale_reason` 비율을 수집한다. 모델 파일·프레임 크기·동시 실행 서비스·이미지 ID·장치·스레드 조건을 기록한다.
- 기존 최신 프레임 교체와 최신 좌표 한 건 전송 구조를 유지한다. `analysis_fps=5`는 처리 속도 보장이 아니므로 이 숫자만 조정하고 해결로 판단하지 않는다.

**검증:** 현재 장애를 재현하는 테스트와 같은 조건으로 비교할 성능 기준선이 확보되어야 한다. CPU 성능 측정은 추가 모델을 운영 워커와 동시에 실행해 자원 경합을 만들지 않도록 별도 검증 실행에서 수행한다.

### 2단계: CPU 추론 병목 축소

- 동일 모델·동일 입력으로 PyTorch CPU 스레드 1·2·4개와 기존 기본값을 비교한다. 준비 단계와 정상 실행을 나누고, 정상 실행은 조건별 최소 100회 측정한다.
- 성능이 개선되는 경우에만 필요한 스레드 제한을 감지 자식 프로세스에 적용한다. identity·analysis의 전역 설정까지 일괄 변경하지 않는다. 선택값과 적용 위치는 측정 결과로 결정한다.
- Docker CPU 배분과 다른 서비스의 부하를 대조한다. `cpu_shares: 512`는 경합 시 상대적 가중치이므로, 제거 또는 변경은 실제 개선이 확인된 경우에 한정한다.
- 기본 입력 크기에서 목표를 달성하지 못하면 YOLO 입력 크기 축소를 비교한다. 고정 검증 영상의 원거리·작은 사람·가림 구간에서 탐지 누락과 박스 정확도를 확인하고, 원본 1280×720 좌표와 crop 경계가 유지되는 경우에만 적용한다.
- 기존 GPU 경로는 호스트 NVIDIA 장치와 컨테이너 CUDA 지원이 확인된 경우에만 검증한다. GPU 이미지·장치 전달·실제 `execution_device`를 함께 확인하며, CPU 이미지에 `INFERENCE_DEVICE=cuda`만 지정하는 방법은 사용하지 않는다. CPU 지원은 유지한다.

**검증:** 제안 성능 목표는 정상 실행의 추론 p95 **1초 이하**다. 동일 검증 영상에서 새로운 탐지 누락·ID 단절·좌표 변환 오류가 없어야 한다. 측정 전 특정 스레드 수나 GPU 사용을 해결책으로 확정하지 않는다.

### 3단계: 좌표 전송과 Data 쓰기 지연 축소

- `data_put_seconds`, `db_lock_wait_seconds`, `db_transaction_seconds`를 같은 시간 구간에서 비교한다. API 인증·왕복 통신 지연과 SQLite 쓰기 지연을 분리한다.
- 좌표 PUT의 실시간 좌표 저장과 `note_track_observation()` 갱신, 동시 작업의 쓰기 잠금 점유를 확인한다. 실제 병목 쿼리나 불필요한 쓰기만 최소한으로 수정한다.
- 인물 관측 구간과 identity 충돌 방지 규칙을 보존한다. 기존 WAL 설정을 확인하며, DB 교체·저장소 이전·영속성 완화는 별도 근거 없이 도입하지 않는다.
- 최신 좌표 한 건만 유지하는 전송 정책을 보존한다. 만료된 좌표의 반복 재시도나 대기열 확장은 추가하지 않는다. 2초 전송 제한 증가는 일차 해결책으로 사용하지 않는다.
- 표준 로그에서도 전송 실패의 카메라·오류 코드·소요 시간이 보이도록 제한된 값을 명시한다. 현재 `extra` 필드만으로 원인이 출력되지 않는 부분을 보완하며 토큰·인증 URL·예외 원문은 출력하지 않는다.

**검증:** 좌표 PUT p95 **0.5초 이하**, 통합 5분 검증에서 해당 PUT의 시간 초과와 HTTP 499가 없어야 한다. 최신 관측 우선 저장, 이전 좌표의 늦은 도착, identity 관측 구간 테스트가 통과해야 한다.

### 4단계: 좌표 전달 상태를 readiness에 반영

- `LivePublisher`에 마지막으로 전송에 성공한 payload의 관측 시각을 보존하고, 상태 조회 시 그 관측의 경과 시간을 계산한다. HTTP 성공 시각만으로 좌표가 유효하다고 판단하지 않는다.
- 활성 감지 워커에서 성공적으로 전달한 관측이 3초를 초과하면 `degraded`와 `LIVE_OBJECTS_STALE` 진단을 보고한다. 객체 0개인 정상 관측도 성공적인 갱신으로 취급한다.
- 시작 유예는 첫 관측 전의 기존 준비 제한시간과 연결하고, 성공적인 첫 전달 뒤에는 3초 기준을 적용한다. 카메라 없음·감지 비활성·의도적 중지와 구분하며, 정상 좌표 전달 재개 시 자동 복구한다.
- `/health/live`와 Data 연결 시 readiness HTTP 200을 유지하는 기존 계약은 보존한다. 응답 본문의 `degraded` 사유를 External 진단의 허용 목록에 반영한다. Docker의 `healthy`와 좌표 표시 가능 상태를 구분해 운영 문서에 설명한다.
- 진단 필드가 추가되면 관련 공개 스키마와 생성된 OpenAPI를 함께 갱신한다. 클라이언트는 기존 `stale` 의미와 화면의 수신 중단 시 3초 제거 동작을 유지한다.

**검증:** 프레임 수신·모델 실행·HTTP PUT이 성공해도 5초 전 관측만 전달되는 상황에서는 `degraded`여야 한다. 새 관측, 정상 빈 배열, 초기화, 중지, 복구를 각각 검사한다. 공개 진단에 비밀값이 포함되지 않아야 한다.

### 5단계: 운영 반영과 실제 화면 검증

- 구현 시 변경한 서비스만 빌드·교체하고 이미지 ID와 적용 설정을 기록한다. 기존 소스 변경 사항은 유지하고 이번 수정분을 구분한다. 운영 설정과 기존 이미지 ID는 복원할 수 있게 보관한다.
- 실제 사람의 등장·이동·퇴장과 카메라 재연결을 확인한다. API의 비만료 결과뿐 아니라 관제 화면에서 박스가 해당 사람을 따라가는지 확인한다.
- `pid`와 미판정 `gpid:null`, 이후 gpid 갱신을 확인한다. identity 완료를 기다려 박스 표시가 지연되지 않아야 한다.
- 좌표 전송을 끊는 시험과 의도적으로 느린 추론은 검증 환경에서 수행한다. 오래된 박스 제거와 진단 저하·복구를 확인한다.
- 준비 완료 후 동일 부하로 5분 이상, 공개 API 유효 표본 300개 이상을 수집한다. CPU 경로를 기본 검증하고 GPU를 적용한 경우 그 경로도 별도 기록한다.

**최종 완료 기준:** 공개 API 수신 시 관측 경과 시간 p95 **2초 이하**, 결과 갱신 간격 p95 **1초 이하**, 정상 구간의 `expired` 응답 비율 **1% 이하**, 좌표 PUT 시간 초과 **0건**을 목표로 한다. 미래 시각·만료 좌표의 차단과 영상 위 박스의 실제 위치 일치까지 확인해야 완료다. 수치는 이번 수정의 제안 인수 기준이며 기존에 보장되던 성능이 아니다.

Data 만료 기준 변경, DB 스키마 변경, 화면 레이아웃 변경, 모델 교체, PAR 분석·전역 인물 연결 방식 변경은 기본 범위에 포함하지 않는다. 클라이언트가 정상 좌표를 받고도 표시하지 않는 별도 결함이 재현될 때만 해당 표시 코드를 수정한다.

기존 [관제 표시 계획](monitoring-display-fix-plan.md)은 ID·이벤트·시간 표시에 관한 계획이다. 이번 계획은 11월 9일의 실행 로그로 확인한 실시간 좌표 지연을 대상으로 한다. [PAR 모델 계획](analysis-par-model-fix-plan.md)의 변경도 이 작업과 구분한다.

## 5. 테스트와 복원

- Data 저장소에 실제 `get_live_objects()`와 임시 DB·고정 시계를 사용하는 테스트를 추가한다. 신선함·만료·미래·빈 배열·순서 역전·비활성 카메라를 검사한다.
- Preprocessing 테스트에 촬영 시각 보존, 전송 성공 후 관측 경과 시간, 전송 실패·정상 빈 배열·복구를 추가한다. 시간 경계는 실제 대기 대신 제어 가능한 시계로 검사한다.
- 기존 `test_performance.py`, `test_detection_first_inference.py`, `test_detection_isolation_diagnostics.py`, `test_preprocessing_diagnostics.py`, `test_overlay.py`, `test_multi_camera_view.py` 중 영향받는 검사를 실행한다. GPU 경로 변경 시 장치 정책 테스트도 포함한다.
- 성능은 단위 테스트의 임의 시간 제한으로 통과시키지 않고 대상 장비의 위 통합 인수 측정으로 검증한다. 문서 작성만 한 현재 단계에서는 제품 테스트를 실행하지 않는다.
- 탐지 누락·ID 단절·영상 지연 증가·데이터 쓰기 오류가 생기면 변경한 서비스 이미지와 설정을 기존 값으로 복원한다. 데이터를 초기화하거나 기존 이벤트를 재처리하지 않는다. 복원 후에도 원래 좌표 만료 문제가 남는다는 점을 기록한다.
