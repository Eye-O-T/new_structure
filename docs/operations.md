# 보관·장애 복구·배포 인수 기준

설치·백업 명령은 [상세 안내](guide.md#운영과-백업), API 필드는 [OpenAPI](openapi.yaml)를 따른다. 아래는 현재 코드에 적용된 정책과 실제 배포에서 확인할 기준이다.

## 보관 정책

기본 보관 기간은 `config.yaml`의 `recording.retention_days`(기본 7일)다. Data의 주기적 정리에서 적용하며, 컨테이너에 `DATA_RETENTION_DAYS`를 직접 전달한 구성은 이 값이 우선한다. 기한 변경은 앞으로 실행할 정리에 적용되며 이미 지운 자료는 되돌리지 않는다.

| 자료 | 정리 조건·보호 범위 |
|---|---|
| 중앙·복구 녹화 | 보관 기한을 지난 등록 파일. writing 상태는 제외. 삭제 중 상태를 먼저 남겨 파일 잠금·재시작 뒤 이어서 처리 |
| 이벤트·객체 작업 | 발생·등록 시각이 모두 기한을 지나고 미처리 작업·유효한 푸시·최근 완료 작업·미전송 참조가 없을 때 삭제. 관련 작업은 외래 키로 함께 정리 |
| 오래된 미처리 객체 작업 | 생성 뒤 기본 30일(`DATA_JOB_MAX_AGE_DAYS`)이 지난 pending 또는 임대 만료 running을 `failed`·`OBJECT_RETENTION_EXPIRED`로 전환. 유효한 임대는 만료까지 보호하고 최종 상태를 추가 보관 기간 동안 노출 |
| snapshot·crop·박스 이미지 | 기한을 지나고 DB·outbox 참조가 없는 JPEG만 정리. 생성·이벤트 등록 사이를 보호하기 위해 파일 수정 후 최소 24시간 보존. 알려진 임시 이미지·보호 목록 임시 파일도 같은 유예 적용 |
| 전송 대기·격리 이벤트 | 자동 폐기하지 않음. 큐 상한에 도달하면 추가 감지를 대기시킴. 영구 거부의 원인을 고친 뒤 명시적으로 재시도하거나 폐기 |
| 인물 연결·체류 구간 | 관련 이벤트가 없고 최근 관측도 보관 기한을 지났을 때 정리. 사용 중 연결은 유지 |
| 재식별 gallery | 매칭 시 관측 나이 1,800초·최대 5,000개. 주기 정리에서도 기한이 지난 표본 삭제 |
| 푸시 | 만료된 pending·임대 만료 sending은 취소. sent·failed·cancelled는 마지막 갱신 후 보관 기한이 지나면 정리 |
| 세션·장치 토큰 | access 취소 기록은 만료 후, refresh는 만료 후 보관 기간까지 보존. 장치 등록은 오래되고 유효한 연결 세션이 없을 때 정리 |
| 복구 작업·녹화 삭제 기록 | 완료 또는 시도 소진한 복구 작업은 종료·갱신 후 보관 기간이 지나면 정리. 녹화 삭제 기록은 삭제 후 한 보관 기간 추가 유지 |
| 백업·모델·설정·비밀 파일 | 자동 삭제하지 않음. 운영자가 검증된 복원본과 접근 권한을 관리 |

Preprocessing은 전송 대기·격리 이벤트와 포화 때문에 아직 등록하지 못한 관측의 경로·중복 제거 키를 `/snapshots/.pending-observations.json`에 원자적으로 기록하고 30초마다 갱신한다. 카메라별 포화 대기 참조는 SQLite에 별도 보존하고 다음 큐 등록 성공 시 해제한다. 활성 목록 조회에 성공했고 생산자도 종료된 카메라의 고아 참조는 해제하되 목록 조회 실패나 생산자 종료 대기 중에는 보호한다. 따라서 큐 공간이 생긴 직후에도 미등록 crop이 보존된다. 새 항목은 DB 확정 전에 보호하고, 전달 완료 항목은 DB 삭제 확정 후 보호에서 뺀다. 보호 목록은 `schema_version:2`와 명시적 `complete`를 사용한다. 새 Data는 기존 v1도 읽고 구형 Data는 v2 정리를 보류하므로 먼저 갱신된 Preprocessing의 불완전 목록을 정상으로 오해하지 않는다. Data는 목록이 없거나 손상되거나 120초를 넘거나 `complete:false`이면 이벤트·이미지 정리를 보류한다. 이때 `retention.status=deferred`와 원인을 확인한다. 보호 목록의 상한 초과는 `OUTBOX_MANIFEST_INCOMPLETE`이며 일부 참조를 생략한 목록으로 정리를 계속하지 않는다. 큐 JSON 상한은 이미지 총용량 상한이 아니므로 네 저장소 여유 공간도 함께 감시한다.

SQLite 행 삭제는 재사용 가능한 페이지를 만들며 DB 파일을 즉시 축소하지 않는다. 정리 중 온라인 전체 VACUUM은 실행하지 않는다. 백업 저장소도 자동 삭제하지 않으므로 별도 용량 정책이 필요하다.

## 인증·장치 교체 시 적용되는 규칙

로그아웃은 요청에 실린 토큰 하나가 아니라 같은 로그인 계열(`sid`)의 토큰 전체를 폐기한다. 토큰 갱신과 겹쳐도 이미 회전된 refresh·access로 보호 API나 영상을 다시 열 수 없다. Data의 활성 계열 검사를 통과해야 하므로 Data 인증 상태 조회 장애를 임의 인증 성공으로 처리하지 않는다. 업데이트 전에 발급된 `sid` 없는 access는 401이며, 유효한 기존 refresh가 있으면 새 형식으로 갱신할 수 있다. 갱신 자격도 없다면 다시 로그인한다.

모바일의 로그인·갱신·로그아웃은 저장까지 순서대로 완료하고 서버 주소와 토큰을 함께 적용한다. 이전 저장이 진행 중이면 뒤의 세션 변경이 기다린다. 영상 플레이어 생성 오류에서는 정리 완료와 무관하게 오류 안내와 재연결을 표시하며, 네이티브 정리 대기는 최대 3초다. 이 제한이 네이티브 자원 해제 자체의 성공을 보증하는 것은 아니므로 실기기 인수에서 반복 실패·재연결도 확인한다.

로그인 실패 이력은 최대 10,000개와 유휴 15분을 적용한다(최대 backoff가 더 길면 그 기간). 계정명을 바꾸는 시도에도 주소별 최근 60초의 실패를 최대 20회까지 허용하고, 이후 요청은 429와 Retry-After로 제한한다. 정상 로그인도 이 주소 집계를 초기화하지 않는다. 기본 신뢰 프록시는 `nginx`이며, 직접 접속 상대가 해당 호스트의 확인된 주소와 일치할 때만 Nginx가 덮어쓴 `X-Real-IP`를 사용한다. Uvicorn의 일반 전달 헤더 신뢰는 끈다. 다른 프록시를 사용하는 배포는 External 컨테이너의 `TRUSTED_PROXY_HOSTS`를 실제 프록시에 맞춰야 한다.

새로 생성하는 복구 작업과 연결 장애 이력은 발생 당시 Edge ID를 보존한다. 카메라를 다른 장치에 연결해도 이전 작업은 원래 Edge에서 영상을 요청하며, 관련 작업·이력이 정리되기 전에는 원래 장치 정보를 삭제하지 않는다. migration `009`는 기존 이력에 현재 남아 있는 연결을 채운다. **업데이트 전에 이미 삭제된 과거 장치 정보까지 복원하지는 못하므로** 그런 장애 구간은 백업·장치 기록으로 별도 확인한다.

자동 복구는 작업별 자식 프로세스에서 실행하며 `RECOVERY_JOB_TIMEOUT_SECONDS` 기본 1,800초가 전체 실행을 제한한다. 기존 `RECOVERY_TIMEOUT_SECONDS` 기본 30초는 네트워크 무응답 제한으로 유지된다. 전체 기한 초과나 종료 요청에서는 자식을 정리하고 작업 상태를 기록하므로 느린 응답 하나가 다음 복구를 무기한 막지 않는다. 자식 종료 확인에 최대 약 2.2초와 DB 잠금 대기가 추가될 수 있다. 강제 종료에 실패하면 후속 작업을 차단하고 준비 상태를 503으로 유지하며, 실행 중 파일을 삭제하지 않는다. 대용량 복구는 실제 전송 속도·장애 구간에 맞춰 전체 기한을 조정한다. 수동 복구 CLI의 직접 실행에는 이 자동 작업 기한이 적용되지 않는다.

녹화 파일의 DB 등록과 이벤트 연결은 함께 확정한다. 이전 버전에 이미 남은 연결 누락도 정합성 점검에서 복원하며, 파일이 있다는 사실만으로 연결 완료를 가정하지 않는다.

## 장애 확인과 복구

관리자 웹 또는 `GET /api/v1/system/status`에서 시작한다. Data·Preprocessing·MediaMTX 탐색은 기본 3초, 설정 최대 10초로 제한하며 각 서비스의 안전한 상태 필드만 공개한다. 검사 주소는 내부 운영 설정이다. Analysis 컨테이너의 직접 모델 상태 검사는 포함하지 않는다.

| 증상·코드 | 확인·복구 | 완료 기준 |
|---|---|---|
| 게시 인증 실패 | 등록된 동적 자격 증명 또는 명시적인 정적 계정을 확인. 빈 계정은 거절됨 | 해당 Edge만 게시 가능하고 잘못된 계정은 거절됨 |
| 화질 변경 지연 | Edge 주소·프로필 지원·중앙 재인증을 확인. 프로필 변경 중 게시 인증은 독립 처리 | HD/FHD 변경 응답·중앙 재송출·로컬 녹화가 회복됨 |
| Data DB busy·복구 작업자 오류 | `data.workers` 최근 오류와 DB 디스크·다른 장시간 쓰기 작업 확인. claim 및 실패 기록은 자동 재시도 | 작업자가 살아 있고 `last_success_at` 갱신, 복구 작업이 진행됨 |
| `RECOVERY_JOB_TIMEOUT` | 원래 Edge 응답·다운로드 속도·복구 구간 크기와 전체 기한 확인. 종료 확인 뒤 미완성 `.part`는 정리하고 완료 영상은 보존 | 재시도 진행과 실제 복구 영상 등록 |
| `RECOVERY_PROCESS_DID_NOT_STOP` | 후속 claim이 중지된다. 운영자가 자식 프로세스·디스크를 확인하고 서비스 재시작 | 이전 자식 종료 확인, readiness 200, 새 복구 작업 진행 |
| 모델 초기화·감지 시간 초과 | 모델 경로·호환성·메모리와 카메라 `model_timeouts` 확인. 자식 종료 뒤 자동 재준비 | 모델 준비·새 프레임·추론 시각 갱신, 새 세션의 객체 발행 |
| `frame_stale` | RTSP·카메라 상태, 추론 시간과 CPU 경합 확인 | 실제 최신 영상과 프레임 시각이 진행됨 |
| `EVENT_STORAGE`, `EVENT_OUTBOX_FULL` | snapshot 저장소 권한·용량, Data 연결, 큐 pending/rejected/waiting 확인. waiting은 카메라별 보호 참조이며 이벤트 본문 복원 가능 건수가 아님 | 저장 오류 해소, 큐 감소, 새 이벤트 등록 |
| `EVENT_REJECTED` | 아래 CLI로 격리 목록 확인. 카메라·payload 계약 오류를 해결한 뒤 재시도 | rejected 감소 및 Data의 동일 source_event_id 수신 확인 |
| `OUTBOX_MANIFEST_*` | Preprocessing 생존·공유 snapshot 경로·파일 권한 확인. 목록을 손으로 비우지 않음 | 30초 갱신 재개, `retention.status=ready` |
| 객체 최종 실패 | 이벤트 `metadata.<stage>.status`·`metadata.<stage>.result.error_code`, 임대·모델 상태 확인 | pending으로 잘못 표시되지 않음. 자동 시도 소진과 보관 만료를 구분 |
| 푸시 문제 | 등록 장치·세션·FCM 설정, External worker와 Data 대기열 확인 | 실제 Android에서 새 알림과 연결 녹화 확인 |

소스 저장소 루트에서 실행하는 격리 관리 예시다. 실제 배포 env와 필요한 추가 Compose 파일을 사용한다.

```powershell
docker compose --env-file C:/path/to/compose.env -f server/compose.yml exec preprocessing python -m server.services.preprocessing.app.outbox_admin list
docker compose --env-file C:/path/to/compose.env -f server/compose.yml exec preprocessing python -m server.services.preprocessing.app.outbox_admin retry --sequence 123
```

`discard --sequence 123 --confirm-discard`는 해당 격리 이벤트를 영구 폐기한다. 재시도 가능한 자료에 사용하지 않는다. 이미지 파일은 이 명령에서 직접 지우지 않고 보관 정리에 맡긴다.

## 자원과 배포 기록

Preprocessing은 카메라별 감지 자식을 두고 초기화 기본 30초·프레임 호출 기본 10초를 제한한다. Pipe 전송·수신 대기도 같은 제한에 포함하며 시간 초과 때 자식을 종료한다. `DETECTION_STARTUP_TIMEOUT_SECONDS`·`DETECTION_MODEL_TIMEOUT_SECONDS`로 조절한다. 대표 프레임 선택은 기본 1초·카메라당 32 MiB이며 `OBSERVATION_WINDOW_SECONDS`·`OBSERVATION_BUFFER_MAX_BYTES`로 조절한다. 선택 중 RAM 후보는 강제 종료 시 복원하지 못한다. SQLite 송신 큐에 기록된 항목은 재시작 후 재전송한다.

Compose의 `PREPROCESSING_MEMORY_LIMIT` 기본값은 4 GiB, CPU shares는 512, 프로세스 수 상한은 512다. 메모리 제한은 모델·카메라 수에 맞춰 조정한다. CPU shares는 경합 시 상대 가중치이며 최대 CPU 사용률 보장은 아니다. 실제 부하에서 영상 지연·녹화 누락·DB 지연·추론 p50/p95·큐 증가·RAM을 함께 측정한다. 이 값은 4채널 성능을 실측하여 확정한 예산이 아니다.

검증한 릴리스는 태그만 기록하지 않고 실제 이미지 ID·registry digest·설치된 전이 Python 패키지 버전·모델 SHA-256을 남긴다. [릴리스 기록 도구](../server/tools/README.md#배포-릴리스-기록)는 비밀 env를 출력하지 않는다. 오프라인 현장에는 검증한 이미지를 내보내 전달하고 동일 manifest와 비교한다. 현장에서 새로 `--build`한 결과는 별도 릴리스로 다시 검증한다.

## 버전별 인수·복원 기록

릴리스마다 아래 표를 복사하여 날짜·장비·실행 결과·증거 경로를 채운다. 미실행은 성공으로 간주하지 않는다. 개발 자동 테스트 결과와 실제 배포 인수 결과를 구분한다.

| 항목 | 기록할 결과 |
|---|---|
| 배포 식별 | 소스 revision, release manifest, OS·CPU·RAM, 카메라·단말 모델, UTC 시각 |
