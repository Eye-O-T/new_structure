# 바운딩 박스 지연과 오른쪽 이벤트 누락 분석·수정 계획

작성일: 2026-11-03, Asia/Seoul  
상태: 핵심 수정 구현 및 서버 반영 완료, 카메라 현장 검증 보류

## 1. 전제와 조사 범위

사용자가 바운딩 박스 표시를 확인했으므로, 이전의 감지 모델 오지정 복구 이후에 남은 두 문제를 다룬다. 이번 원인을 이전 모델 로딩 실패와 동일하게 판단하지 않는다.

- 문제 1: 박스의 최초 표시와 움직임 추종이 느림.
- 문제 1의 추가 범위: 호스트 GPU가 있어도 감지가 CPU에서 실행되는 원인을 확인하고 GPU 전환·실제 가속 검증 절차를 마련한다.
- 문제 2: 박스가 표시돼도 오른쪽 이벤트 타임라인에 출현 이벤트가 보이지 않음.
- 오른쪽 목록은 선택한 카메라의 최근 이벤트를 표시하는 것으로 가정한다. 지속해서 보이는 같은 추적 ID에 출현 이벤트를 반복 생성하지 않는 동작은 유지한다.
- 소스와 기존 이벤트·로그를 읽었다. 조사 시점의 Preprocessing은 `idle`, 작업자 0명, outbox pending/rejected/waiting 모두 0이었다. 따라서 현재 실행의 추론 p50/p95는 수집할 수 없었다.
- 이전에 요청한 현장 검증 보류를 유지한다. 카메라 기동·녹화·운영 설정 변경은 수행하지 않았다.

## 2. 문제 1 — 박스가 느린 원인

### 2.1 코드에서 확인한 지연 요인

| 구간 | 확인 내용 | 영향·판단 |
| --- | --- | --- |
| 추론 주기 | `settings.py:101`의 기본 `ANALYSIS_FPS=5` | 최대 처리 목표가 5fps이며 실제 모델이 느리면 달성하지 못함 |
| 좌표 발행 | `pipeline.py:522`에서 0.5초 간격 제한 | 추론이 빨라도 좌표 발행은 최대 2Hz |
| Desktop 조회 | `video_worker.py:220`에서 요청 완료 후 0.5초 대기 | 조회 주기는 HTTP 응답 시간 + 0.5초이며 발행 주기와 지연이 겹침 |
| 동기 후처리 | `pipeline.py:535` 이후 대표 이미지 선택·저장·outbox 등록을 감지 스레드에서 순차 처리 | 출현 시 처리 비용이 다음 프레임 감지를 지연시킬 수 있음 |
| 파일 저장 | `objects.py:36`에서 JPEG 인코딩·fsync·원자 교체. 출현 시 원본·crop·박스 이미지 저장 | 공유 저장소 I/O가 느리면 출현 직후 박스 갱신이 멈출 수 있음 |
| 저장 실패 | `pipeline.py:264`의 crop 저장과 `pipeline.py:145`의 outbox 등록이 재시도 중 감지 생산자를 대기시킴 | 장애 시 지연이 커짐. 현재 이 장애가 발생했다는 증거는 없음 |
| IPC | `isolation.py`가 전체 프레임을 Pipe로 자식에 전달하고 결과를 기다림 | 모델 실행 외 직렬화·프로세스 간 전달 비용 존재. 기여도는 측정 필요 |
| 표시 경로 | Desktop 영상과 박스는 별도 조회 경로. RTSP 실패 시 HLS로 폴백 | 화면의 움직임과 박스 시점 차이가 커질 수 있음. 이번 증상에서 HLS 사용 여부는 미확인 |

발행·조회 제한만으로도 처리된 좌표가 화면에 도달하기까지 상황에 따라 약 1초의 추가 대기가 생길 수 있다. 이 값은 모델 실행·HTTP·UI 지연을 포함한 최종 지연 상한이 아니다. 여러 초 지연을 두 주기만으로 설명할 수 없다.

### 2.2 실행 기록에서 확인한 사실과 한계

로그는 감지 모델이 `requested_device=auto; CUDA unavailable, using cpu`로 실행됐음을 보여준다. CPU 실행은 확인됐지만, CPU가 전체 지연의 가장 큰 원인인지는 당시 timing 자료가 없어 확정하지 않는다.

이벤트 3의 최초 관측은 17:05:36.164이고 대표 프레임 선택 시각은 17:05:44.535로 8.371초 차이다. 설정된 관측 창은 1초다. `ObservationBuffer._update()`는 새 추론 결과가 들어올 때만 후보 갱신과 만료를 처리하며, 만료 확인 전에 후보를 교체한다. 따라서 1초는 독립 타이머가 보장하는 처리 기한이 아니다. 느린 다음 추론·스케줄링 등으로 처리 간격이 벌어지면 실제 선택과 이벤트 생성이 함께 밀린다.

이 기록은 파이프라인 처리 간격이 크게 벌어졌음을 뒷받침한다. 모델 실행, IPC, 이미지 저장 중 어느 구간이 8초의 대부분을 차지했는지는 후속 측정으로 구분해야 한다.

### 2.3 수정 계획

1. **지연의 구간을 먼저 측정한다.** 기존 `capture_to_inference_seconds`, `model_seconds`, `ipc_seconds`, `inference_total_seconds`, `image_persistence_seconds`, `event_persistence_seconds`, `data_put_seconds`를 활용한다. Desktop에 좌표 요청 왕복 시간, 수신 좌표 나이, 실제 화면 반영 시간을 추가 기록한다. 최초 감지 지연·갱신 간격·영상과 좌표의 시점 차이를 별도로 측정한다.
2. **발행·조회 주기를 실제 감지 속도에 맞춘다.** 5fps 처리가 가능한 기준에서는 발행 간격 0.2초, Desktop 조회 간격 0.1~0.2초를 우선 후보로 비교한다. 응답 시간에 따라 요청이 누적되지 않도록 카메라당 동시 조회는 한 개로 유지한다. 카메라 4대에서 API·DB 부하를 함께 확인한 뒤 값을 확정한다.
3. **이미 만료된 후보를 다음 추론 뒤까지 기다리지 않게 한다.** 실제 monotonic 시각으로 추론 시작 전과 완료 후 후보 기한을 확인하고, 기한 지난 후보를 뒤늦은 프레임으로 다시 교체하지 않도록 처리 순서를 정리한다. 블로킹 추론이 남아 있는 한 엄격한 1초 완료를 보장한다고 설명하지 않는다.
4. **GPU 실행 복구와 남은 병목을 확인한다.** GPU 전환은 2.4절의 검증 순서로 진행한다. GPU 실행 전후 모델 시간과 전체 지연을 따로 비교한다. IPC가 지배적이면 전달 데이터 비용을 줄인다. 이미지 저장이 지배적이면 이벤트·이미지 저장을 용량 제한이 있는 작업자로 분리한다.
5. **저장 작업 분리 시 신뢰성을 유지한다.** 카메라·추적 세션·관측 시각·복사된 프레임을 작업에 고정하고, 기존 outbox·파일 보호·종료 시 유실 집계·용량 초과 처리를 유지한다. 좌표는 최신 상태로 교체할 수 있지만 이벤트를 같은 방식으로 버리면 안 된다. 이 변경은 저장 병목이 확인될 때만 적용한다.
6. **영상·UI 비용을 확인한다.** RTSP/HLS 선택과 디코딩 큐 지연을 기록한다. `_render_selected_summary()`는 객체 지표가 갱신될 때마다 이벤트 위젯 전체를 다시 만들므로, UI 측정에서 유의미한 비용이 확인되면 지표 갱신과 이벤트 목록 갱신을 분리한다.

### 2.4 GPU 미실행 원인과 수정 계획

#### 확인한 실제 상태

2026-11-03에 설정·실행 컨테이너·호스트를 읽기 전용으로 확인했다.

| 계층 | 실제 값 | 판단 |
| --- | --- | --- |
| 호스트 GPU | NVIDIA GeForce GTX 1650 with Max-Q Design, VRAM 4096 MiB | 호스트에 NVIDIA GPU가 존재하고 `nvidia-smi`가 조회됨 |
| 호스트 드라이버 | 566.36 | 현재 버전을 기록했으며 CUDA 이미지와의 실제 연산 호환성은 후속 검증 필요 |
| Docker | Linux amd64 엔진 29.8.1 | Linux 컨테이너 실행 중 |
| WSL | 기본 배포 docker-desktop, 기본 버전 2 | WSL2 구성 확인. 일반 권한에서의 조회 거절은 재조회로 해소됐으며 GPU 고장 근거로 취급하지 않음 |
| 설치 env | `PREPROCESSING_GPU=false`, `INFERENCE_DEVICE=auto`, `IDENTITY_DEVICE=auto` | 현재 설치는 GPU 사용을 요청하지 않음 |
| Compose 명령 | 기본 `server/compose.yml`만 포함 | `compose.gpu.yml`이 선택되지 않음 |
| 컨테이너 장치 요청 | `HostConfig.DeviceRequests=null` | 실행 컨테이너에 GPU 할당 요청이 없음 |
| PyTorch | `2.8.0+cpu`, `torch.version.cuda=null` | 설치된 PyTorch 자체가 CPU 빌드 |
| CUDA 인식 | `is_available=false`, `device_count=0` | 현재 컨테이너는 CUDA 장치를 사용할 수 없음 |

**직접 원인:** GPU 비활성 설정 때문에 CUDA 빌드와 GPU 장치 할당이 모두 적용되지 않았고, `auto` 장치 정책이 정상적으로 CPU를 선택했다. 현재 증거만으로 드라이버 고장이나 GTX 1650 미지원으로 판단하지 않는다.

코드 경로는 다음과 같다.

1. `server/operations/compose.py`는 저장 env의 `PREPROCESSING_GPU`가 참일 때만 GPU override를 추가한다.
2. 기본 Compose와 `preprocessing/Dockerfile`은 CPU PyTorch 인덱스를 사용한다.
3. `server/compose.gpu.yml`은 `gpus: all`, PyTorch cu126 빌드 인덱스, GPU ONNX Runtime과 관련 라이브러리 경로를 선택한다.
4. `processors/detection/device.py`의 `auto`는 CUDA 불가 시 CPU로 폴백한다. `INFERENCE_DEVICE=auto`만으로 CPU 이미지를 CUDA 이미지로 바꾸거나 Docker GPU를 할당하지는 않는다.

추가로 수정할 설정 전달 문제가 있다. `installer/configuration.py`는 설치 입력 `request.inference_device`를 YAML에 쓰지만, env의 `INFERENCE_DEVICE`는 이전 값 또는 `auto`로 기록한다. 실행 설정은 환경변수가 YAML보다 우선하므로 설치 화면에서 선택한 장치가 실행에 반영되지 않을 수 있다. 현재 운영값이 `auto`인 직접 경위는 별도 확인이 필요하지만, 이 충돌 경로는 회귀 테스트와 함께 정리해야 한다.

#### 단계별 수정·배포 계획

1. **현재 CPU 실행을 복구 기준으로 보존한다.** 실제 env와 변경할 키, 현재 이미지 ID, 모델 파일, 서비스 상태를 기록한다. 인증값을 로그에 출력하지 않는다. 기존 CPU 이미지를 되돌릴 수 있게 식별하고, GPU 빌드 전에 설정 백업을 만든다.
2. **설치 장치 선택의 전달을 일치시킨다.** 명시적으로 선택한 감지 장치를 YAML·env·Compose가 같은 값으로 전달하게 한다. GPU 선택 시 `PREPROCESSING_GPU`와 CUDA 장치 선택이 함께 반영돼야 한다. 선택을 변경하지 않은 재설정은 저장값을 보존한다. 호스트 GPU 발견만으로 사용자 설정을 자동 변경하지 않는다.
3. **GPU 전용 빌드를 먼저 준비한다.** 저장 env를 기준으로 `compose.gpu.yml`이 포함되고 최종 빌드 인자가 cu126 인덱스를 사용하는지 확인한다. 현재 소스의 PyTorch 2.8.0·torchvision 0.23.0 조합으로 먼저 검증한다. 버전이나 드라이버를 일괄 갱신하지 않는다. 빌드 후 `torch.version.cuda`가 비어 있지 않고 실제 GPU용 wheel인지 확인한다.
4. **카메라 없이 GPU 연산을 검증한다.** GPU 이미지를 일회성 컨테이너로 실행해 `--gpus all`, 장치 개수·이름·compute capability·빌드 아키텍처를 확인한다. CUDA 텐서 생성과 작은 연산 후 synchronize까지 성공해야 한다. 실패하면 장치 전달, 드라이버·CUDA 호환성, wheel 아키텍처, 라이브러리 누락을 구분한다. 컨테이너 안에 Windows용 드라이버를 설치하는 방식으로 우회하지 않는다.
5. **감지만 GPU로 전환한다.** 초기 검증값은 `PREPROCESSING_GPU=true`, `INFERENCE_DEVICE=cuda:0`, `IDENTITY_DEVICE=cpu`로 한다. 4 GiB VRAM에서 감지와 OSNet이 동시에 GPU를 점유하는 영향을 먼저 분리한다. 이 값은 구현 시 백업 후 적용할 계획값이며 이번 조사에서는 적용하지 않았다.
6. **Preprocessing만 재생성한다.** CUDA 빌드와 장치 할당을 적용한 새 컨테이너를 만든다. 단순 restart로 대체하지 않는다. CPU 이미지와 GPU 이미지가 같은 운영 태그를 사용하므로 최종 컨테이너 이미지 ID·실제 wheel·DeviceRequests를 모두 재확인한다. 기존 Data·MediaMTX·nginx 재생성은 필요하지 않다.
7. **명시적 CUDA 실패를 진단에 보존한다.** `cuda:0`이 준비되지 않으면 CPU 성공으로 바꾸지 않는다. 현재 장치 정책의 명시적 CUDA 실패 동작은 유지한다. 격리 프로세스에서 오류가 일반 `DETECTION_STARTUP_FAILED`로 소실되지 않게 GPU 요청·CUDA 빌드·장치 미노출·메모리 부족 등을 정제된 코드로 구분하고, 관리자 진단에 실제 실행 장치를 표시한다.
8. **GPU 할당과 감지 성공을 구분한다.** `doctor.py`는 현재 GPU override 파일의 `gpus:` 문자열과 `gpu_requested` 중심으로 정상 판정을 할 수 있다. 이를 실제 컨테이너 DeviceRequests·CUDA 연산·감지 작업자 상태에 근거하도록 보완한다. 작업자가 0명이면 'GPU 런타임 준비, 감지 미검증'으로 표시하고 `execution_device=cuda:0` 확인을 대체하지 않는다.
9. **GPU 전후 지연을 같은 조건에서 비교한다.** 현장 검증 보류가 해제되거나 사용 가능한 검증 영상이 확보되면 동일 YOLO·입력 크기·프레임·카메라 수로 준비 구간을 제외하고 100회 이상 측정한다. 모델·IPC·저장·좌표 전달·화면 반영의 p50/p95, GPU 메모리, 유효 갱신률을 비교한다. CUDA 연산 성공과 박스 지연 개선은 각각 판정한다.

#### 검증과 완료 기준

- 설정 전달: 설치의 CPU/auto/CUDA 명시 선택, 이전값 보존, GPU override 선택, 누락된 override의 오류 처리를 회귀 테스트한다.
- 실행 구성: GPU가 켜진 최종 Compose와 실제 컨테이너에 GPU 요청이 존재하고, PyTorch는 CUDA 빌드여야 한다.
- 장치 정책: 기존 `test_device_policy.py`의 auto 폴백과 명시적 CUDA 실패 검증을 유지한다. GPU가 없는 테스트 환경은 대역으로 정책만 검증하고 실제 CUDA 성공으로 보고하지 않는다.
- GPU 연산: CUDA 장치 조회뿐 아니라 텐서 연산·동기화까지 성공해야 한다. 드라이버·CUDA·아키텍처 호환성은 이 단계에서 확인한다.
- 실제 감지: 허용된 검증 입력에서 작업자 `model_ready=true`, `requested_device=cuda:0`, `execution_device=cuda:0`와 지속적인 결과 생성을 확인한다. GPU 메모리 부족·재시작·CPU 폴백이 없어야 한다.
- 성능: 모델 시간이 개선됐는지와 전체 박스 지연이 개선됐는지를 각각 보고한다. 발행·조회 제한과 파일 저장 지연은 GPU만으로 해소된다고 간주하지 않는다.
- 복구: GPU 검증 실패 시 기록한 CPU 이미지와 장치 설정으로 Preprocessing만 재생성한다. 이미 복구한 `MODEL_FILE=yolo11n.pt`와 인증키는 유지한다.

현재까지 완료된 것은 GPU 미실행 원인의 확인이다. CUDA 이미지 빌드·GPU 설정 적용·연산 시험·카메라 검증은 수행하지 않았다.

## 3. 문제 2 — 오른쪽 이벤트가 누락되는 원인

### 3.1 데이터로 확인한 지연 저장

다음은 Data API에서 읽은 실제 기록이다. 시간은 한국 시각이다.

| ID | 유형 | 관측·발생 시각 | DB 생성 시각 | 차이 |
| --- | --- | --- | --- | --- |
| 3 | person_appeared | 17:05:36.164 | 17:05:46.130 | 9.966초 |
| 4 | person_disappeared | 17:06:04.908 | 17:06:06.064 | 1.156초 |
| 5 | person_appeared | 17:06:09.885 | 17:06:14.000 | 4.115초 |

출현 이벤트 두 건이 서버에 저장돼 있으므로, 이번 문제 전체를 이벤트 미생성으로 판단할 수 없다.

### 3.2 주요 원인인 조회 조건의 불일치

`video_worker.py:222`의 `poll_events()`는 다음과 같이 동작한다.

1. 시작할 때 현재 시각을 `start`에 넣는다.
2. `from=start`로 이벤트를 검색한다.
3. 페이지 조회를 마치면 요청 시작 시각 `end`를 다음 회차의 `start`로 사용한다.

Data의 검색 조건은 `events.py:209`의 **`occurred_at >= start`**다. 출현 이벤트는 관측 창·다음 추론·이미지 저장·outbox 배달을 거친 뒤 DB에 들어가지만, `occurred_at`은 최초 관측 시각을 유지한다.

예: 17:05:40 조회 시 이벤트 3이 미저장 → 다음 시작 시각을 17:05:40으로 이동 → 17:05:46에 저장된 이벤트 3의 발생 시각은 17:05:36 → 이후 조회 범위에서 제외된다.

이 경로는 늦게 저장된 이벤트를 영구히 누락시킬 수 있다. 실제 데이터의 4~10초 저장 지연도 이 조건과 맞는다. 다만 당시 Desktop의 각 조회 시각이 없어 모든 누락이 이 경로로 발생했다고 단정하지는 않는다.

또한 폴러 시작 전에 저장된 출현 이벤트는 초기 `start=현재시각` 때문에 읽지 않는다. 이미 화면에 있던 사람은 새 추적 전환이 생기기 전까지 출현 이벤트가 추가 생성되지 않으므로, 모니터를 나중에 열면 박스만 보일 수 있다.

### 3.3 박스가 표시돼도 이벤트가 없는 이유

`pipeline.py:522`는 좌표를 먼저 발행한다. 출현 이벤트는 그 뒤 대표 프레임 확정과 이미지 저장을 거친 `pipeline.py:569`에서 생성된다. 따라서 박스 표시가 출현 이벤트의 저장·조회·UI 전달 성공을 뜻하지 않는다. 현재 코드에서는 재식별·속성 분석 완료를 기다려야 이벤트를 표시하는 구조도 아니다.

### 3.4 수정 계획 — 저장 순서로 증분 수신

1. **관측 시각 기반의 폴링 진행을 제거한다.** 기존 이력 검색은 유지하고, 실시간 증분 수신에는 `after_event_id`와 ID 오름차순 조회를 추가한다. 이벤트 ID는 Data에서 `AUTOINCREMENT`로 부여하므로 발생 시각이 과거여도 나중에 저장된 이벤트를 찾을 수 있다.
2. **Data → External → Desktop 계약을 함께 변경한다.** 카메라·사용자 권한 조건을 모든 페이지에 적용한다. 기존 날짜 검색·정렬·커서 의미를 바꾸지 않으며, 새 조회 모드의 허용 조합을 명시한다. OpenAPI·계약 서명·설치 호환성 관련 검사를 함께 갱신한다.
3. **한 조회 회차의 상한과 재시도를 고정한다.** 첫 페이지의 `snapshot_max_id`를 회차 상한으로 사용하고, 페이지 토큰에 필터·정렬·상한을 묶는다. 전체 페이지를 처리하기 전에는 회차 완료로 진행하지 않는다. 실패 시 같은 범위를 재시도하고 이벤트 ID로 중복 표시를 막는다.
4. **초기 표시를 채운다.** 카메라를 열 때 최근 30개 이벤트와 동기화 기준 ID를 함께 확보한다. 이후 새로 저장된 ID를 읽는다. 초기 목록을 읽는 동안 저장된 이벤트도 다음 증분 조회에 포함돼야 한다. 최근 목록은 발생 시각으로 표시할 수 있지만 수신 진행 기준은 저장 ID로 유지한다.
5. **지연·재시작·카메라 전환을 처리한다.** outbox가 수분 뒤 재전송한 과거 발생 이벤트도 수신한다. 카메라별 진행 상태와 UI 세션을 구분하고, 워커 교체 뒤 도착한 이전 신호는 기존 검증으로 제외한다. 삭제된 이벤트·DB 보존 정리로 ID에 빈 구간이 생겨도 진행한다.
6. **폴링과 UI를 마무리한다.** 이벤트 조회를 요청 완료 후 0.5~1초 주기로 조정하되 증분 API 부하를 확인한다. `_on_event()`와 선택 카메라 캐시, `legacy_event()` 유형 변환을 통합 검증한다. 새 이벤트가 없을 때 기존 위젯을 재구성하지 않는다.

단순히 `from`을 10초나 30초 되돌리는 방법은 그보다 긴 outbox 지연에서 다시 누락된다. 이를 최종 복구 방법으로 사용하지 않는다. `occurred_at`을 저장 시각으로 덮어써 조회를 맞추는 방법도 사건 시각을 훼손하므로 사용하지 않는다.

## 6. 구현·배포 결과 (2026-11-03)

- Desktop 좌표 조회 간격을 0.2초, 이벤트 증분 조회 간격을 0.5초로 조정했다. 감지 결과 발행 간격은 0.2초로 바꿨다. 카메라별 요청은 기존 단일 폴링 스레드로 직렬 실행된다.

- 관측 후보는 먼저 만료 여부를 처리하고, 만료된 후보를 다음 프레임으로 다시 교체하지 않도록 했다.
