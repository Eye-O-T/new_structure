# analysis의 PAR 모델 연결 수정계획서

- 작성일: 2026-11-08, KST
- 수정일: 2026-11-09, KST — OpenCV 분석 사용 금지 및 필수 모델 준비 실패 시 종료 정책 반영
- 대상: 실행 중인 `ai-cctv-analysis-1`, 운영 분석기 설정, 관제 화면의 분석 완료 결과
- 요청 범위: 문제 확인 및 수정계획 수립·수정. 운영 설정·제품 코드·DB 변경과 컨테이너 재시작은 아직 수행하지 않았다.

## 1. 결론

**2026-11-08 조사에서 제기된 문제가 확인되었다. 당시 실행 중인 analysis는 전달된 PT 모델 대신 OpenCV 기반 `LocalAppearanceAnalyzer`를 사용하고 있었다.**

`par_serving_exp3.pt` 파일은 정상적으로 마운트되어 있고, 현재 컨테이너에 PT 분석기 구현과 필요한 라이브러리도 이미 있다. 별도 프로세스에서 해당 파일의 로드와 추론이 성공했다. 따라서 우선 수정할 대상은 모델 파일이나 학습 코드가 아니라 **운영 `ANALYSIS_PLUGIN` 선택 설정**이다.

현재 OpenCV 분석기는 사람 크롭의 일부 영역에서 색상 후보와 화질 지표를 계산한다. 성별·연령대·소매·하의 종류·소지품을 예측하지 않는다. 그러므로 의상 정보가 전혀 생성되지 않는다고 단정하기보다는, **제한적인 색상 측정만 생성되고 학습 모델의 외관 속성은 생성되지 않는 상태**로 판단한다.

수정 후에는 **PT 모델을 필수로 사용하고, OpenCV 색상 분석으로 대체하지 않는다.** 모델이 없거나 유효하게 로드되지 않으면 작업 수령 전에 시작을 중단하고 컨테이너 프로세스를 비정상 종료한다. 자동 재시작도 유한하게 제한한다. 따라서 기존 이미지의 설정만 바꾸는 복구안에서, **시작·종료 처리 수정과 analysis 이미지 재빌드를 포함하는 계획**으로 변경한다.

### 2.1 전달된 모델의 호환성 확인

운영 워커와 분리한 컨테이너 내부 프로세스에서 [PersonAttributeAnalyzer](../server/services/analysis/processors/attributes.py)를 직접 생성했다. `torch.load(..., weights_only=True)`와 네트워크 가중치 로드가 성공했다.

- 검사 파일 SHA-256: `e3ec03c516ab6429dada23b285def0509478332028180361bc9ee19404033c69`
- 모델 로드: 약 1.14초
- 임시 합성 JPEG 128×256 입력 추론: 약 0.15초, `outcome=complete`
- 반환 backend: `par_resnet34`, backend version: `exp3`
- 반환 속성: `gender`, `age`, `hat`, `upper_color`, `lower_color`, `sleeve`, `lower_type`, `carrying`
- 단일 선택 속성은 `{value, score}`, 색상·소지품은 그 항목의 목록으로 반환하며 점수 범위 검사를 통과했다.

임시 입력은 사람 사진이 아닌 합성 영상이다. 이 검사는 모델 로드·추론·출력 구조의 연결 가능성을 확인한 것이며, 실제 사람에 대한 정확도나 운영 전체 경로의 성공을 검증한 것은 아니다. 임시 파일은 검사 후 제거했으며 운영 작업 완료나 이벤트 생성 API는 호출하지 않았다.

## 3. 원인

1. 운영 `compose.env`에 분석기 선택값이 없다.
2. Compose가 기본값인 `LocalAppearanceAnalyzer`를 컨테이너 환경에 넣는다.
3. 현재 실행 이미지에서 이 이름은 실제 OpenCV 분석기로 연결된다.
4. 모델 파일을 `/models`에 두는 것만으로 `PersonAttributeAnalyzer`가 선택되지는 않는다.
5. OpenCV 분석도 정상 완료로 저장되므로 작업은 `complete`, 상태 점검은 `ready`가 된다. 이 상태는 원하는 PT 모델이 사용되었다는 증거가 아니다.
6. 저장 결과에 성별·연령 등 속성 자체가 없으므로, 화면의 새로고침이나 표시 코드만 바꾸어 복원할 수 없다.

### 3.1 현재 소스에 이미 준비된 변경과의 차이

작업 폴더에는 이미 다음 변경이 있다. 이 문서 작성 중 새로 구현한 내용은 아니다.

- [analysis 앱](../server/services/analysis/app/main.py)의 기본 플러그인을 `PersonAttributeAnalyzer`로 지정
- [플러그인 패키지](../server/services/analysis/processors/__init__.py)와 [기존 모듈](../server/services/analysis/processors/appearance.py)의 LocalAppearance 이름을 PAR 분석기의 호환 별칭으로 변경
- [.env 예제](../server/.env.example), [설치 설정](../server/installer/configuration.py), [모델 검사](../server/installer/models.py)에 PAR 선택·검증 반영
- [관제 상세 표시](../server/desktop/admin/application.py)에 8개 속성과 점수 표시, [타임라인](../server/desktop/admin/legacy_gui.py)에 성별·연령 요약 처리

하지만 실제 컨테이너 클래스는 여전히 OpenCV 구현이다. **소스에 준비된 변경과 운영 반영 상태가 일치하지 않는다.** 이미 있는 변경을 중복 구현하거나, 소스를 읽었다는 이유만으로 운영 연결이 완료되었다고 판단해서는 안 된다. 실행 중인 관제 프로그램이 이 소스 버전인지도 배포 검증 단계에서 확인한다.

## 4. 수정 목표와 범위

새 사람 관측의 analysis 결과가 `par_resnet34 / exp3`로 저장되고, 해당 `analysis_completed` 항목을 눌렀을 때 모델이 제공한 외관 속성과 점수가 표시되어야 한다.

- 분석 시작은 유효한 크롭을 가진 기존 객체 작업 흐름을 사용한다. gpid 판정을 기다리는 조건을 추가하지 않는다.
- 타임라인은 기존 요구인 `pid:…/gpid:… 분석 완료`를 유지하고, gpid 미판정은 `null`로 표시한다.
- 원래 나타남 이벤트를 눌렀을 때 분석 결과를 표시하지 않는 기존 분리 요구를 유지한다.
- 필수 PT 모델의 부재·형식 오류·가중치 로드 실패 시 analysis는 작업을 수령하지 않고 종료한다. OpenCV 분석이나 빈 성공 결과로 대체하지 않는다.
- 모델을 복구한 뒤 담당자가 analysis를 다시 시작하면 같은 준비 검사를 거쳐 분석을 재개한다.
- 탐지 모델 `yolo11n.pt`, identity용 OSNet 모델, pid/gpid 생성 로직은 이 문제의 변경 대상에 포함하지 않는다.

## 5. 수정 순서와 단계별 검증

### 5.1 분석기와 필수 모델 선택 고정

운영 `C:/ProgramData/AI_CCTV/config/compose.env`를 백업한 뒤 다음 키를 추가한다. 기존 키가 있다면 중복 추가하지 않고 값을 교체한다.

```dotenv
ANALYSIS_PLUGIN=server.services.analysis.processors.attributes:PersonAttributeAnalyzer
```

모델은 검증된 기본 경로 `/models/par_serving_exp3.pt`를 사용한다. 현행 Compose는 `PAR_MODEL_PATH`를 컨테이너 환경에 전달하지 않으므로, 호스트 env에 그 키만 추가하고 적용되었다고 판단해서는 안 된다. 이번 복구에는 기본 파일명과 경로를 사용하면 충분하다.

[Compose 설정](../server/compose.yml)의 analysis 기본 플러그인도 명시적인 `PersonAttributeAnalyzer`로 통일한다. 기존 LocalAppearance 이름을 유지해야 하는 호환 경로는 PAR 분석기에만 연결되도록 하며, 과거 OpenCV 구현이나 미구현 분석기로 우회해 성공 처리하는 경로는 허용하지 않는다.

**검증:** Compose의 최종 해석 결과에서 분석기 선택값과 `/models` 마운트만 확인한다. 시크릿이 포함된 전체 설정을 출력하지 않는다. 적용 후 컨테이너의 환경값과 실제 클래스가 모두 `PersonAttributeAnalyzer`로 연결되는지 확인한다.

### 5.2 모델 준비 실패 시 안전하게 종료

[analysis 앱](../server/services/analysis/app/main.py)의 현재 백그라운드 초기화·30초 무한 재시도 구조를 변경한다. 앱의 시작 수명 주기에서 모델 준비 완료를 기다리고, 성공한 뒤에만 작업자를 실행한다. 백그라운드 작업의 예외만 남기고 HTTP 서버가 계속 살아 있는 상태로 두지 않는다.

시작 순서는 **파일 존재 확인 → 번들·가중치 로드 → 분석기 준비 → 작업 수령**으로 한다. 번들·가중치는 실제 격리 분석기의 초기화에서 검증하며, 사전 검사를 위해 전체 모델을 별도로 중복 로드하지 않는다. 기존 시작 제한시간도 유지해 초기화가 멈추면 종료할 수 있어야 한다.

| 준비 결과 | 동작 |
| --- | --- |
| 정상 모델 로드 | 분석 작업자 시작, 준비 상태 보고 |
| 파일 없음 | `ANALYSIS_MODEL_MISSING` 기록 후 비정상 종료 |
| 잘못된 번들·호환되지 않는 가중치 | `ANALYSIS_MODEL_INVALID` 기록 후 비정상 종료 |
| 초기화 제한시간 초과 | `ANALYSIS_MODEL_STARTUP_TIMEOUT` 기록 후 비정상 종료 |
| 그 밖의 초기화 실패 | `ANALYSIS_STARTUP_FAILED` 기록 후 비정상 종료 |

[공유 격리 실행기](../lib/ai_cctv_core/processing/isolation.py)는 현재 자식 프로세스의 초기화 오류를 일반적인 `startup_error`로 전달한다. 따라서 앱에 `FileNotFoundError` 처리만 추가하는 것으로 오류 분류가 보장되지는 않는다. 부모의 파일 존재 검사와 자식 초기화의 제한된 오류 코드 전달을 연결한다. 예외 원문이나 자격 증명을 전달하지 않으며, 공유 경로의 수정은 기존 identity 동작을 유지하는 최소 범위로 제한한다.

초기화 실패 시 생성 중이거나 생성된 자식 프로세스·파이프·HTTP 클라이언트를 정리하고 주 프로세스까지 종료한다. 초기화가 끝나지 않았으면 작업 임대 요청과 완료 보고는 모두 0건이어야 한다. 실패를 `complete`나 `unconfigured`로 저장하거나 분석 완료 이벤트로 바꾸지 않는다.

가동 중 격리 분석기를 재생성할 때 모델 부재·로드 실패가 확인되어도 새 작업 수령을 멈추고 같은 종료 경로를 사용한다. 이미 임대한 작업은 성공 처리하지 않으며, 가능한 경우 기존 재시도 절차로 반환하고 종료 시 완료하지 못한 임대는 기존 만료·재수령 규칙에 맡긴다. 모델 파일이 로드 후 삭제되었는지 계속 감시하는 기능은 추가하지 않는다.

**검증:** 정상 모델, 파일 누락, 손상 번들, 가중치 불일치, 초기화 시간 초과를 임시 경로에서 재현한다. 실패 시 비영(0이 아닌) 종료 코드, 작업 수령·완료 보고 0건, 자식 프로세스 정리를 확인한다. 운영 모델 파일을 지워서 검사하지 않는다.

### 5.3 자동 재시작 제한과 관제 상태

analysis의 Compose 재시작 정책을 `unless-stopped`에서 **`"on-failure:3"`**으로 바꾼다. 앱 내부의 초기화 무한 재시도도 제거한다. 모델이 없을 때 제한 횟수 이후에는 종료 상태를 유지하고, 파일을 준비한 뒤 담당자가 명시적으로 다시 시작하도록 한다.

종료 후에는 `/health/ready`가 응답하지 않을 수 있다. 관제 화면은 이를 정상·분석 완료로 표시하지 않고, 기존 서비스 상태 조회와 허용된 오류 코드를 이용해 `모델 없음 — 분석 중지`, `모델 로드 실패 — 분석 중지` 등을 표시한다. 원인을 얻지 못하면 `분석 서비스 중지`로 표시한다. 모델 미준비는 서비스 상태이며, 사람별 성공 완료 이벤트를 새로 만들지 않는다.

**검증:** 격리된 Compose 검사 환경에서 PT 모델 부재 시 자동 재시작이 최대 3회로 끝나고 종료 상태를 유지하는지 확인한다. 모델 복구 후 수동 시작하면 준비 상태가 정상으로 전환되는지도 확인한다. 녹화·탐지·identity는 계속 동작해야 한다.

### 5.4 소스 검토·이미지 재빌드 및 운영 적용

이미 준비된 기본 플러그인·호환 별칭·설치 검사 변경을 리뷰하고, 위의 종료 처리와 재시작 정책을 함께 검증한다. 설치 도구가 신규 설치뿐 아니라 **기존 운영 env에도 명시적 PAR 선택값을 반영하는지** 확인한다. `.env.example`이나 설치 코드만 바꾸는 것으로 이미 설치된 env가 갱신되지는 않는다. 설치 도구가 모델 누락을 미리 차단하더라도 컨테이너 자체의 준비 검사도 유지한다.

기존 이미지는 새 종료 정책을 포함하지 않으므로 **analysis 이미지를 재빌드**한다. 단순 환경값 변경이나 기존 이미지 재생성만으로 이번 요구가 완료되었다고 판단하지 않는다.

실행 시에는 현재 배포와 같은 프로젝트명 `ai-cctv`, 운영 `compose.env`, `server/compose.yml`, `server/compose.gpu.yml`을 사용한다. 검증한 새 이미지를 대상으로 analysis만 재생성한다. 다른 서비스를 불필요하게 재시작하지 않는다. 단순 `restart`는 컨테이너 환경값과 생성 설정을 갱신하지 않으므로 사용하지 않는다.

Compose 기본값·재시작 정책 변경으로 [배포 서명 검사](../server/deployment/signature.py)의 Compose 해시도 달라진다. 알려진 기존 Compose 해시에서 이 변경으로 이동하고 DB·도메인 계약 해시가 같은 경우에만 서명을 갱신한다. 다른 계약 불일치는 자동 승인하거나 저장 데이터를 초기화하지 않는다.

**검증:** `/health/ready`의 backend가 명시한 PAR 플러그인이고 `ready=true`, `model_ready=true`여야 한다. 이어서 실제 새 작업의 저장 결과가 `backend=par_resnet34`, `backend_version=exp3`인지 확인한다. 준비 상태만으로 복구를 판정하지 않는다.

### 5.5 결과 저장 및 관제 표시 확인

기존 [작업 완료 처리](../server/services/data/app/database/repositories/objects.py)와 [완료 이벤트 생성](../server/services/data/app/database/repositories/events.py)의 metadata 전달 구조를 우선 재사용한다. PAR 결과가 기존 구조로 저장되는지 검증한 뒤, 누락이 확인되는 부분만 수정한다.

| 검증 대상 | 기대 결과 |
| --- | --- |
| 저장 구조 | `metadata.analysis.result.attributes`에 모델이 반환한 속성과 점수 보존 |
| 성별·연령대 | `gender`, `age`의 `value`와 `score` 표시. 정확한 나이로 바꾸지 않음 |
| 의상·소지품 | 상·하의 색상, 모자, 소매, 하의 종류, 소지품 표시. 여러 후보는 목록 처리 |
| 빈 다중 선택 결과 | 값이 없으면 미제공으로 처리하며 임의의 의상·소지품 값을 생성하지 않음 |
| 분석 완료 이벤트 | 동일 작업에 대해 1회 생성, pid 및 gpid/null 표시 |
| 분석 완료 상세 | `par_resnet34`, 모델 버전, 완료 시각과 결과 표시 |
| 원래 나타남 상세 | 분석 결과 영역을 표시하지 않음 |
| gpid 판정 지연 | gpid가 null이어도 analysis 완료와 결과 조회 가능 |

현재 관제 소스는 속성 표시를 지원하므로 표시 코드를 먼저 재작성하지 않는다. 운영 프로그램에서 결과 필드를 받았는데도 보이지 않을 때, 실행 파일의 버전을 확인하고 필요한 관제 빌드를 반영한다. 기존 KST 시간과 타임라인 정렬도 함께 유지한다.

## 6. 과거 결과 처리

조사 시점의 기존 104건은 실제 OpenCV 분석의 완료 결과다. 플러그인을 바꾸어도 이미 `complete`인 작업이 자동 재실행되지는 않는다. 이 결과의 backend 이름만 PAR로 바꾸거나, 없던 성별·연령 정보를 보충해서는 안 된다.

이번 복구의 적용 대상은 전환 후 새로 처리하는 분석 작업이다. 과거 결과는 기존 backend와 내용으로 보존한다. `unconfigured` 작업 재시도 기능은 이미 `complete`인 이 자료의 재분석 수단이 아니다.

과거 자료의 재분석이 추가로 필요하면 별도 범위로 설계한다. 현행 완료 이벤트는 원본 등장 이벤트별 중복 방지를 하므로, 단순히 기존 작업을 다시 큐에 넣는 것으로 새 모델의 완료 이력까지 올바르게 갱신된다고 가정할 수 없다.

## 7. 완료 기준과 복구 방법

1. 설정 검증: 컨테이너 환경과 실제 클래스가 명시적 PAR 분석기를 가리킨다.
2. 정상 모델 검증: 확인한 PT 파일을 로드하고, 전환 후 새 관측 1건 이상에서 `par_resnet34 / exp3` 결과와 8개 속성 구조가 저장된다.
3. 실패 종료 검증: 모델 누락·번들 오류·가중치 불일치·초기화 시간 초과 시 이유를 기록하고 프로세스가 종료된다. 시작 실패 상황에서 작업 수령·완료 보고·분석 완료 이벤트가 없다.
4. 재시작 검증: 자동 재시작은 최대 3회로 제한되며, 모델 복구 후 담당자의 수동 시작으로 분석이 재개된다. OpenCV로 대체하는 실행 경로는 없다.
5. 화면 검증: 분석 중지와 원인이 표시되고, 정상 완료 항목의 상세에서 성별·연령대·의상 정보를 확인한다. 나타남 상세에는 분석 결과가 없고 gpid 미판정은 null로 보인다.
6. 보존 검증: 기존 분석 결과와 이벤트·녹화 자료가 유지되고 녹화·탐지·identity가 계속 동작한다. 공유 격리 실행기 변경에 대한 기존 identity 회귀 검사도 통과한다.

모델 로드 또는 새 작업 처리에 문제가 생기면 **analysis를 중지한 상태로 유지**하고 모델·설정·이미지를 수정한 뒤 다시 시작한다. 과거 OpenCV 이미지나 플러그인으로 되돌려 분석을 계속하는 복구안은 사용하지 않는다. 이전 버전으로 되돌려야 한다면 PT 필수 검증·실패 종료·재시작 제한을 충족하는 버전만 대상으로 한다. 적용 전 백업은 설정 비교와 데이터 보존에 사용하며, 전환 중 생성된 결과의 실제 backend와 완료 이벤트는 그대로 보존한다.

모델 로드·출력 구조는 2026-11-08 조사에서 확인했다. 실패 시 종료·제한 재시작·상태 표시의 소스 변경은 진행됐지만, **이미지 빌드·기존 설치 서명 갱신·운영 배포와 실제 새 작업·관제 화면 검증은 아직 완료하지 않았다.**
