# 관리자 다중 카메라 시청 개선 계획서

작성일: 2026-10-08 · 상태: 코드 조사 완료 / 구현 전 제안

## 1. 목표와 범위

관리자가 설정 창을 반복해서 열지 않고 카메라를 전환하여 시청하거나, 여러 카메라를 그리드로 동시에 시청하도록 한다.

- 대상은 `server/setup/install_helper/desktop`의 PyQt 관리자 데스크톱이다. 이 경로의 README가 관리자 화면으로 명시하고 있다.
- “개별로 이동”은 카메라 간 화면 전환으로 해석한다. 물리적인 팬·틸트·줌(PTZ) 제어를 뜻한다면 별도 요구사항으로 다뤄야 한다. 조사한 server/edge/mobile/docs 코드에서는 PTZ/ONVIF 제어 경로를 찾지 못했다.
- 1차 제안: 단일 보기 + 최대 4대의 2×2 그리드. 등록 카메라가 4대보다 많으면 목록에서 표시 대상을 바꾸거나 이전/다음 묶음으로 이동한다.
- 3×3 이상, 자동 순환, 드래그 배치, 서버 영상 합성, 모바일 그리드는 1차 범위에 포함하지 않는다. 동시 시청 대수는 사용자 요구와 대상 PC 성능에 따라 최종 확정한다.

## 3. 제안하는 화면 동작

1. 로그인 후 메인 화면에 카메라 목록, 목록 새로고침, 단일/2×2 보기 전환을 제공한다. 목록에는 이름과 ID를 표시한다.
2. 단일 보기에서 목록 선택 또는 이전/다음 버튼으로 카메라를 변경한다. 다른 카메라로 바꾸기 위해 설정 창을 열지 않는다.
3. 그리드에서는 최대 4대의 서로 다른 카메라를 선택한다. 빈 칸은 선택 안내로 표시하고 재생 작업을 만들지 않는다.
4. 타일 클릭은 우측 통계·이벤트 패널의 대상 카메라를 선택한다. 더블클릭은 해당 카메라의 단일 보기로 전환하며, 그리드 복귀 시 이전 배치를 복원한다.
5. 각 타일에는 카메라 이름·ID, 로딩/LIVE/재연결/오류 상태와 해당 카메라 재시도를 표시한다. 한 카메라의 장애는 해당 타일에만 반영한다.
6. 1차 버전의 공용 통계·이벤트 패널은 선택 카메라 기준이다. 대상 이름을 명시하고 전체 카메라 합계로 오인할 수 있는 표시를 피한다. 인물 ID도 카메라 간 단순 합산하지 않는다.
7. 모니터링 시작·중지는 현재 보기에 필요한 시청 연결을 제어한다. 카메라 전환은 중앙 녹화나 로컬 웹캠 송출을 중지하지 않는다. 송출 중지는 명시적인 송출 제어와 앱 종료에서 수행한다.

## 4. 구현 설계와 파일별 작업

### 4.1 카메라별 영상 타일

신규 `server/setup/install_helper/desktop/camera_view.py`에 영상 표시 위젯을 둔다.

- 기존 화면의 영상 비율 유지·여백·객체 오버레이·로딩·오류 표시를 필요한 범위만 옮긴다.
- 타일마다 카메라 ID, 최근 프레임, 객체 좌표와 수신 시각을 보유한다. 카메라 변경 즉시 이전 영상·좌표를 비운다.
- 창 크기 변경 시 최근 프레임을 타일 크기에 맞춰 다시 그린다. 기존 `overlay.py` 좌표 계산을 재사용한다.
- Qt 위젯과 QPixmap 렌더링은 UI 스레드에서 처리한다.

### 4.2 메인 창의 표시 대상과 재생 작업 관리

`application.py`에서 단일 worker 상태를 카메라 ID별 상태로 바꾼다. `legacy_gui.py`에서는 중앙 위젯과 신호 연결에 필요한 부분만 변경한다.

- 유지할 상태: 보기 모드, 그리드 카메라 순서, 선택 카메라 ID, 카메라별 worker·타일·통계·최근 이벤트.
- 화면에 필요한 카메라 집합과 실행 중인 집합을 비교하여 추가된 카메라만 시작하고 빠진 카메라만 중지한다. 두 집합에 모두 있는 worker는 재사용한다.
- 단일 보기에서는 다른 카메라 연결을 해제한다. 그리드 복귀 시 해제했던 카메라는 재연결되므로 무중단 복귀를 약속하지 않는다.
- 신호 연결 시 카메라 ID와 worker 인스턴스 또는 세대 번호를 함께 확인한다. 빠른 A→B→A 전환에서 오래된 프레임·종료 신호가 새 작업에 적용되지 않아야 한다.
- 카메라별 통계·이벤트 캐시는 활성 worker 동안 유지하고, 제거·재시작 시 초기화한다. 선택 변경 시 해당 캐시를 패널에 표시한다.
- 화면에서 쓰지 않는 프레임을 버리더라도 해당 worker의 `acknowledge_frame()`은 처리하여 전송 대기 상태가 남지 않게 한다.
- 정리 중 worker도 별도로 추적한다. 이전 worker가 끝나기 전에 같은 카메라의 후속 worker를 중복 시작하지 않는다.

### 4.3 로그인·설정과 시청 선택 분리

`settings_window.py`의 로그인, 카메라 등록·관리, 로컬 송출 기능은 유지하고 메인 화면에서 기존 `DesktopApi.cameras()`로 목록을 갱신한다.

- 설정에서 선택한 카메라는 초기 선택값으로 사용할 수 있으나 이후 시청 전환은 메인 화면에서 수행한다.
- `save_basic_settings`의 로컬 송출 중지 조건을 검토하여 시청 대상 변경과 송출 중지를 분리한다. 기존 로컬 카메라 등록·게시 계정 재발급 흐름은 시청 전환에 재사용하지 않는다.
- 목록 새로고침으로 삭제·비활성 카메라를 발견하면 관련 재생을 정리하고 선택값을 보정한다.
- 시청 중 계정·서버 세션 변경은 전체 worker 정리 후 수행한다. 단순 카메라 전환은 허용한다.

### 4.4 API 동시 요청과 인증

`api.py`의 전역 요청 잠금은 네트워크 통신 전체가 아닌 토큰 상태 접근과 갱신에 필요한 범위로 줄인다.

- 요청 시작 시 토큰을 읽고 네트워크 요청은 잠금 밖에서 실행한다. 상위 `ServerApiClient._request`도 공유 토큰을 읽으므로 해당 메서드와의 경계를 확인하고 요청에 사용할 토큰을 고정할 수 있게 필요한 최소 수정을 한다.
- 여러 카메라에서 동시에 401이 발생하면 갱신 잠금 안에서 요청에 사용한 토큰과 현재 토큰을 비교한다. 이미 갱신됐다면 새 토큰으로 재시도하고, 필요한 경우 한 번만 refresh한다.
- `media`와 `event_image`의 기존 토큰 비교 패턴을 참고한다. 카메라별로 독립적인 refresh token 복사본을 만들지 않는다.
- 로그아웃과 진행 중인 갱신의 순서를 정의하고, 로그아웃 후 늦게 도착한 응답이 세션을 복구하지 못하게 한다.
- 폴링 요청의 제한 시간과 취소 동작을 명확히 한다. 기존 90초 기본값이 종료를 지연시키지 않도록 시청용 요청에 필요한 범위로 조정한다.

### 4.5 재생 성능과 종료

`video_worker.py`의 RTSP 우선/HLS fallback은 유지한다. 각 worker의 객체 조회는 현재 0.5초, 이벤트 조회는 2초 간격이다. 4대이면 대략 객체 8회/초 + 이벤트 2회/초이며 페이지 추가 조회·영상 요청은 별도다.

- 현재 큐는 카메라당 RGB 프레임 30장이다. 1920×1080×3×30 기준 약 178 MiB, 4대 약 712 MiB이며 디코더·표시 버퍼는 추가된다. 실제 메모리는 stride와 입력 크기에 따라 달라진다.
- 큐 상한과 오래된 프레임 폐기 정책을 조정하고, 필요하면 그리드 표시용 프레임을 축소한다. HLS의 묶음 도착과 재생 간격을 고려하여 기존 재생 테스트로 검증한다.
- UI 표시 FPS 제한은 디코딩 부하까지 낮추지 않으며, 타일 축소는 전송 대역폭을 줄이지 않는다. 성능 부족 시 이 둘을 구분해 판단한다.
- 그리드 진입만으로 `video-profile` 변경 API를 호출하지 않는다. 현재 화질 변경은 원본 송출 및 녹화·분석에 영향을 줄 수 있다. 별도 저해상도 스트림은 측정 결과 필요할 때 후속 검토한다.
- `run()`의 디코딩 스레드 `join(timeout=2)`와 제한 없는 `poller.join()`을 검토한다. worker 종료 신호만 보고 내부 디코더·HLS 브리지가 모두 끝났다고 가정하지 않는다.
- 앱 종료는 모든 재생·폴링·디코딩·브리지 정리 완료 후 로그아웃한다. UI 스레드에서 긴 wait/join을 실행하지 않는다. 강제 QThread 종료로 우회하지 않는다.

### 4.6 서버 변경 여부

1차 기능은 기존 `/cameras`, `/{camera_id}/live`, `/{camera_id}/objects`, `/events?camera_id=...`를 사용한다. DB 스키마·OpenAPI·MediaMTX 설정 변경은 기본 계획에 넣지 않는다. 부하 측정에서 병목이 확인되면 그 원인에 맞춰 별도 변경을 제안한다.

## 5. 실행 순서와 검증 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 영상·오버레이·상태 표시를 타일로 분리 | 기존 단일 카메라 영상, 비율, 객체 좌표, 이벤트 상세가 유지된다. |
| 2 | API 동시 요청·토큰 갱신·worker 종료 보완 | 한 카메라의 느린 요청이 다른 요청을 직렬화하지 않고 동시 401에서도 갱신 경합이 없다. 종료 후 내부 스레드가 남지 않는다. |
| 3 | 메인 목록과 개별 전환 구현 | 재생 중 A→B→A 및 빠른 연속 전환에서 이전 카메라 영상·좌표·통계가 섞이지 않는다. |
| 4 | 2×2 배치·선택·확대·복귀 구현 | 1~4대 독립 재생, 4대 초과 목록 이동, 빈 칸, 대상 삭제, 한 타일 장애를 처리한다. 중복 worker가 생기지 않는다. |
| 5 | 실제 스트림 부하 및 회귀 검증 | 아래 시나리오를 통과하고 대상 PC의 지원 조건과 측정 결과를 기록한다. |

- 기존 `test_live_video.py`, `test_overlay.py`, `test_desktop_event_detail_contract.py`, `test_server_api_policy.py`를 변경 범위에 맞춰 실행한다.
- 신규 테스트는 카메라 간 신호 격리, 오래된 worker 콜백 무시, 표시 집합 차이만 시작·중지, 동시 401 갱신, 느린 요청 격리, 종료 후 내부 스레드·브리지 회수를 검증한다. 테스트 파일은 `server/setup/install_helper/tests/`에 둔다.
- Qt 통합 시나리오: 반복 전환, 단일↔그리드 반복, 전체 중지·재시작, 카메라 삭제·비활성화, 로그아웃/재로그인, 재연결 중 창 닫기, 로컬 웹캠이 포함된 그리드에서 다른 카메라로 전환.
- 실제 환경: RTSP 4대, HLS fallback 4대, RTSP/HLS 혼합, 한 카메라 단절을 각각 확인한다. 서버 녹화 지속과 이벤트 상세·리소스 창 동작도 확인한다.
- 대상 PC와 입력 해상도·FPS를 기록하고 1대/4대 각각 30분 동안 CPU, 메모리, 수신량, 카메라별 표시 FPS·지연, 드롭, UI 응답성을 측정한다. 전환 반복 후 스레드·연결 수가 원래 수준으로 돌아오고 메모리가 계속 증가하지 않아야 한다.
- 지연·FPS의 수치 합격선은 대상 PC와 입력 조건을 정한 후 확정한다. 현재 조사만으로 4대 FHD의 성능을 보장하지 않는다.

## 7. 확정이 필요한 사항

구현 전 확인할 항목은 “이동”이 PTZ를 포함하는지, 1차 최대 동시 시청 대수를 4대로 할지, 성능 검증에 사용할 PC와 카메라 입력 조건이다. 본 계획의 기본안은 화면 전환·최대 4대 동시 시청이며, 우측 패널은 선택 카메라 기준이다.

이번 작업은 계획서 작성이며 애플리케이션 코드는 수정하지 않았다. 위 검증은 구현 시 수행할 항목으로, 현재 실행·통과를 의미하지 않는다.
